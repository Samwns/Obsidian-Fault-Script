Getting Started

Getting Started with OFS

OFS (Obsidian Fault Script) is a hybrid, self-hosted programming language featuring an integrated AST interpreter for instant execution (ofs run) and an LLVM backend for high-performance native binary compilation (ofs build).

The ecosystem includes the compiler, a standard library, command-line tools, and domain-specific web languages (ODL and OES).

1. Installation

Pre-compiled Packages

Official packages and installers are available across major platforms:

  • Debian / Ubuntu:
  sudo dpkg -i ofs-debian-ubuntu-x64-installer-v*.deb
  • Fedora / RHEL / openSUSE:
  sudo rpm -Uvh ofs-fedora-x64-installer-v*.rpm
  • Arch / Manjaro:
  sudo pacman -U ofs-arch-x64-installer-v*.pkg.tar.zst
  • macOS (Apple Silicon / ARM64):
  • Run the installer script provided in the GitHub release assets.
  • Windows (x64):
  • Run the official executable installer: ofs-windows-x64-installer-v*.exe.
  • VS Code:
  • Install the official extension ofs-vscode-extension.vsix for syntax highlighting, diagnostics, and automatic live reload (*Go Live*).

Building from Source (Bootstrap)

To build the compiler from source within the repository: 

git clone https://github.com/Samwns/Obsidian-Fault-Script.git
cd Obsidian-Fault-Script
bash ofs/bootstrap/scripts/bootstrap-minimal.sh

The resulting compiler binary is written to ofs/dist/ofs (or ofs/dist/ofscc).

Termux (Android)

OFS runs on the phone itself, inside Termux (aarch64).

Install (in Termux): 

curl -fsSL https://raw.githubusercontent.com/Samwns/Obsidian-Fault-Script/main/src/packaging/termux/install_termux.sh | bash
# or, with a local package:  bash install_termux.sh ofs-termux-aarch64.tar.gz

The installer runs pkg install -y clang, downloads the latest ofs-termux-aarch64.tar.gz release, extracts it into $PREFIX (bin/ofs and lib/ofs/) and tests ofs --version.

Use: ofs run hello.ofs (interpreted), ofs build hello.ofs -o hello && ./hello (native aarch64, linked with Termux's clang). Tools live in $PREFIX/lib/ofs/tools/ (ofs run $PREFIX/lib/ofs/tools/odlc.ofs).

Limitations: no X11 windows for now (.oll/.oal windows); building an APK on the phone (ofs build --target android) comes later.

3. First Program

Create a file named hello.ofs: 

core main() {
    echo("Hello from OFS!")
}

Direct execution via the AST interpreter: 

ofs hello.ofs
# or: ofs run hello.ofs

Or compiling to a standalone native binary: 

ofs build hello.ofs -o hello
./hello

Output: 

Hello from OFS!

4. Data Types

OFS is statically typed. The compiler infers variable types when initialized with forge.

Primitive Types

  • stone: 64-bit signed integer.
  • crystal: 64-bit floating-point number (IEEE 754).
  • obsidian: UTF-8 encoded string pointer.
  • bool: Boolean (true or false).
  • void: Indicates absence of a return value.

Fixed-Width Integer Types

  • Unsigned: u8, u16, u32, u64
  • Signed: i8, i32

Example: 

core main() {
    forge counter: stone = 10
    forge rate: crystal = 3.14159
    forge active: bool = true
    forge title: obsidian = "Obsidian"

    forge red: u8 = 255
    forge green: u8 = 128
    forge pixel: u32 = (red as u32 << 16) | (green as u32 << 8)

    echo(title)
    echo(pixel)
}

5. Functions

Functions are declared using the vein keyword. The entry point of an executable program is core main(). 

vein add(a: stone, b: stone) -> stone {
    return a + b
}

vein factorial(n: stone) -> stone {
    if (n <= 1) {
        return 1
    }
    return n * factorial(n - 1)
}

core main() {
    forge sum = add(15, 27)
    forge fact = factorial(5)
    echo(sum)
    echo(fact)
}

Functions can compose calls and invoke other functions: 

vein square(n: stone) -> stone {
    return n * n
}

vein sum_of_squares(a: stone, b: stone) -> stone {
    return square(a) + square(b)
}

core main() {
    echo(sum_of_squares(3, 4))
}

Note: Anonymous functions that capture variables are geode (x: stone) -> stone { return x + base } (closures; see the "geode" section of the Reference). The value has the type vein(stone) -> stone and is passed, stored and called like any vein.

6. Data Structures (monolith)

Composite types are defined with monolith, and methods are attached using impl: 

monolith Rectangle {
    width: stone
    height: stone
}

impl Rectangle {
    vein area(self: Rectangle) -> stone {
        return self.width * self.height
    }

    vein perimeter(self: Rectangle) -> stone {
        return (self.width + self.height) * 2
    }
}

core main() {
    forge r: Rectangle
    r.width = 10
    r.height = 5

    echo(r.area())
    echo(r.perimeter())
}

7. Modules and Imports (attach)

The attach keyword imports modules from the installed standard library or local files: 

attach {math}
attach {string}
attach {io}

To import local relative or absolute files, prefix the path with F:: 

attach {F:./modules/helper.ofs}

8. Control Flow

Conditionals (if / else)

core main() {
    forge x: stone = 10
    if (x > 0) {
        echo("positive")
    } else if (x < 0) {
        echo("negative")
    } else {
        echo("zero")
    }
}

Loops (while)

core main() {
    forge i: stone = 0
    while (i < 5) {
        echo(i)
        i = i + 1
    }
}

Multi-Branch Selection

Multi-branch decision logic is written with chained if / else if / else: 

core main() {
    forge status_code = 200
    if (status_code == 200) {
        echo("OK")
    } else if (status_code == 404) {
        echo("Not Found")
    } else {
        echo("Unknown code")
    }
}

When all the conditions compare the same value, match (synonym: assay) is shorter; _ is the default case: 

core main() {
    forge status_code = 404
    match (status_code) {
        200 => { echo("OK") }
        404 => { echo("Not Found") }
        _ => { echo("Unknown code") }
    }
}

Error Handling and Abort (throw)

The throw statement reports a diagnostic error message and cleanly terminates the process with exit code 1: 

vein divide(dividend: stone, divisor: stone) -> stone {
    if (divisor == 0) {
        throw "Division by zero"
    }
    return dividend / divisor
}

core main() {
    echo(divide(10, 2))
}

Note: The tremor { ... } catch (...) { ... } block structure is modeled in the grammar (NK_TREMOR), with non-terminating stack unwinding planned for the upcoming interpreter and runtime stages.

9. The Rift: native system libraries (rift / extern vein)

The Rift is the boundary through which OFS reaches native system libraries (libc, libm, X11, Android JNI, kernel32). rift vein and extern vein declare a function that lives in a native library, called through the system calling convention. There is no C code in OFS: the compiler and the runtime are written in OFS.

The system calling convention is known technically as the C ABI (abi c); it does not involve C code. 

extern vein puts(s: obsidian) -> stone
rift vein strlen(s: obsidian) -> stone bind "strlen" abi c

core main() {
    puts("Message dispatched via libc puts")
}

It works the same in ofs run and ofs build. A module that declares extern/rift vein asks for claim rift at the top (see chapter 17, which also shows callbacks and f32/crystal through the Rift).

10. Web Stack: ODL and OES

OFS provides two native DSLs designed for authoring web applications without writing raw HTML or CSS by hand:

ODL (Obsidian Document Language)

Semantic document structure compiled into HTML5: 

page "OFS Application" "en"
skin "style.css"

flow
  deck.navigation
    title1 "Main Header"
    link.button "Documentation" "#docs"
  stage#content
    band.article
      mark "## Native Content\nFormatted with **Markdown**."
      raw "<div class=\"custom\">Raw HTML when required</div>"
  spark "app.js"

Compile ODL (the odlc tool ships with the standard library and runs on ofs itself): 

# inside the OFS repository (or with tools installed at /usr/share/ofs/tools)
ODLC_INPUT=document.odl ODLC_OUTPUT=public/index.html ofs run ofs/tools/odlc.ofs

OES (Obsidian Effect Scripts)

Visual tokens, layout rules, media queries, and keyframe animations compiled into CSS: 

gem primary "#5b34ea"
gem background "#120e24"

paint .button
  fill "$primary"
  curve "6px"
  space "8px 16px"
  edge "none"

veil "(max-width: 768px)"
  paint .grid
    grid-cols "1fr"

pulse "appear"
  rise
    opacity "0"
  rest
    opacity "1"

Compile OES (same pattern, with the oesc tool): 

OESC_INPUT=style.oes OESC_OUTPUT=public/style.css ofs run ofs/tools/oesc.ofs

Native HTTP Web Server (webserver)

The standard library includes a native HTTP server built into the runtime: 

attach {webserver}

core main() {
    forge html = "<h1>OFS Native Server</h1><p>Running without third-party dependencies.</p>"
    webserver.serve_html_forever(8080, html)
}

11. Low-Level Features

OFS provides explicit machine-level constructs:

  • fracture { ... }: Typed pointer context.
  • abyss { ... }: Unrestricted low-level operations.
  • bedrock: Standard library module for explicit memory allocations, regions, and byte-level memory (and, as a block, the arena of chapter 15).
attach {bedrock}

core main() {
    forge cell = bedrock_cell_new(42)
    echo(bedrock_cell_read(cell))
    bedrock_cell_drop(cell)
}

Chapters 15 and 17 show how to do this safely (seal, the bedrock { } arena, fracture, abyss, stratum/claim/caprock).

12. ofs run vs ofs build: quick to write, quick to run

Both commands take the same program and give the same output. The difference is when the work happens:

  • `ofs run app.ofs` interprets the program right away: no binary, great for writing and testing.
  • `ofs build app.ofs -o app` produces a native executable (LLVM) that you ship and run without ofs.

You do not have to pick ofs build just for speed: ofs run speeds itself up. It counts the calls of each vein; when one gets "hot" (1000 calls by default) it is compiled to native code in the background (crystallization) and later calls use it. A long loop inside main also turns native in the middle of the run. Without clang, the program simply stays interpreted, only slower. 

vein fib(n: stone) -> stone {
    if (n < 2) { return n }
    return fib(n - 1) + fib(n - 2)
}

core main() {
    echo(fib(32))
}

ofs run fib.ofs                       # 2178309, crystallizes by itself (about 0.06 s here)
OFS_CRYSTALLIZE=0 ofs run fib.ofs     # 2178309, interpreted only (about 1.5 s here)
ofs build fib.ofs -o fib && ./fib     # 2178309, native

Use OFS_CRYSTALLIZE=0 to turn the promotion off (handy for debugging) and OFS_VERBOSE=1 to see when it happens. Times depend on the machine; comparable measurements are in PERFORMANCE.md. The full model is in COMPILED_LANGUAGE.md.

13. Live editing: ofs refract

ofs refract app.ofs runs the program and watches the file. Each time you edit a vein and save, it is swapped while the program keeps running, with no restart and without losing global variables. 

claim rift
extern vein usleep(us: stone) -> stone

vein msg() -> obsidian { return "hi" }

core main() {
    forge i = 0
    while (i < 20) {
        echo(msg() + " " + ofs_stone_to_obsidian(i))
        usleep(250000)
        i++
    }
}

ofs refract live.ofs
# ofs refract: observando live.ofs; salve para refratar
# hi 0
# hi 1
# (change "hi" to "yo" in the editor and save)
# ofs refract: 1 vein refratada (msg)
# yo 2

The main loop continues where it was: only the edited vein changes. If the file has an error, the diagnostic is printed and the running version carries on. Changes that cannot be made live (for example changing the type of a global) are refused with a message saying what needs a restart.

On the phone (Android): ofs refract --remote app.oal keeps the app running natively on the device and sends only the veins you edited (over adb). See ANDROID.md to prepare the app and TOOLS.md for the rules and variables. Language reference: Live editing.

14. Contracts: mineral, grain, bearing, settle

Contracts remove the repeated validation if from your code. A `mineral` is a type with a rule (grain); a vein can require something from its caller (bearing) and promise something about its return (settle, where result is the returned value). 

mineral Age = stone grain value >= 0 grain value <= 150

vein divide(a: stone, b: stone) -> stone
    bearing b != 0
    settle result * b + a % b == a
{
    return a / b
}

core main() {
    forge i: Age = 30          // checks the rule
    echo(divide(17, 5))        // 3
    forge zero = 0
    echo(divide(1, zero))      // violates the bearing
}

Output: 3, then on stderr, with exit code 1: 

ofs: [CONTRATO VIOLADO contract.ofs:4:12]: bearing de 'divide' falhou: b != 0 (b = 0)

When the violation is provable at compile time (divide(1, 0), forge i: Age = 200), the compiler reports [ERRO DE CONTRATO] before running.

  • `ofs assay file.ofs` calls the veins that have contracts at the boundary values of their rules and shows what passes:
$ ofs assay half.ofs
assay half(n: stone)
  --   half(-1): fora do bearing n >= 0
  ok   half(0)
  ok   half(1)
assay: 2 caso(s) ok em 1 vein(s); 1 fora das regras de entrada
  • `ofs build --release` (or OFS_CONTRACTS=0) removes the run-time checks from the binary; compile-time checks stay.

Reference: Contracts and refined types and `ofs assay`.

15. Safe cleanup: seal and the bedrock { } arena

seal: runs on scope exit

seal { ... } (or anchor, the same thing) registers an action that runs when the scope ends, by any path: end of block, return, shatter/erode. Use it to close files, free memory and undo state without repeating the cleanup at every return. 

vein process(name: obsidian) -> stone {
    echo("open " + name)
    seal { echo("close " + name) }
    if (name == "x") { return 1 }
    echo("working on " + name)
    return 0
}

core main() {
    echo(process("a"))
    echo(process("x"))
}

open a
working on a
close a
0
open x
close x
1

Several seals run in reverse order (the last registered runs first). Reference: `seal` and `anchor`.

bedrock { }: a memory arena

A bedrock { ... } block that allocates (text, Array, ofs_alloc) uses an arena: everything it allocates is released at once when the block ends. It is the simplest way to process lots of temporary data without leaking memory. 

core main() {
    forge total = 0
    forge last = ""
    forge i = 0
    while (i < 1000) {
        bedrock {
            forge parts: Array<obsidian> = []
            ofs_array_push(parts, "item" + ofs_stone_to_obsidian(i))
            total = total + ofs_str_len(parts[0])
            last = parts[0]           // the text is copied out
        }                             // the whole arena is freed here
        i++
    }
    echo(total)    // 6890
    echo(last)     // item999
}

Golden rule: `obsidian` text is copied out of the arena automatically; an Array, monolith or pointer that "escapes" the block is an [ERRO DE ARENA] at compile time, with a hint to allocate outside the block. There is also an [AVISO DE VAZAMENTO] (leak warning) for an ofs_alloc that is never freed. Reference: `bedrock { }` arena.

16. Veins as values: vein(T) -> R and geode

The name of a vein is a value with a function type, written with the same word: vein(stone) -> stone. You can store it in a variable, Array or field, pass it as an argument and return it. 

vein twice(x: stone) -> stone { return x * 2 }
vein thrice(x: stone) -> stone { return x * 3 }

vein apply(f: vein(stone) -> stone, x: stone) -> stone { return f(x) }

core main() {
    forge f: vein(stone) -> stone = twice
    echo(f(21))                 // 42
    echo(apply(thrice, 4))      // 12
    forge ops: Array<vein(stone) -> stone> = [twice, thrice]
    echo(ops[1](10))            // 30
}

A `geode` is an unnamed vein that captures variables from the outer scope (what other languages call a closure or lambda). The capture is a copy of the value at the moment the geode is created. 

vein adder(base: stone) -> vein(stone) -> stone {
    return geode (x: stone) -> stone { return x + base }
}

core main() {
    forge plus10 = adder(10)
    forge plus1 = adder(1)
    echo(plus10(5))    // 15
    echo(plus1(5))     // 6
}

Reference: Function types and vein values and `geode`.

17. Low level, with guard rails

OFS lets you touch raw memory and assembly, but it separates where and what, and each module declares what it uses.

fracture and abyss blocks

*p (read/write through a pointer) and &x (address) are only valid inside a low-level block. fracture { } is the typed pointer block; abyss { } is the raw, unrestricted one (function addresses, fault_call, quartz). 

core main() {
    forge x = 5
    fracture {
        forge p: *stone = &x
        *p = *p + 1
    }
    echo(x)    // 6
}

Outside the block, the same code is a compile error. Full rules: Rules for `fracture`, `bedrock`, `tectonic` and `abyss`.

stratum, claim and caprock: per-module permissions

At the top of a file, the module declares its stratum (how much low level it uses) and its claims (which). Whoever attaches the module sees what it asks for, and the main program can impose a ceiling with caprock. 

// raw_io.ofs
claim rift                 // this module declares extern vein

extern vein getenv(name: obsidian) -> obsidian
vein home() -> obsidian { return getenv("HOME") }

// main.ofs
caprock crust              // no attached module may ask for low level
attach {F:raw_io.ofs}

core main() { echo(1) }

Running main: [ERRO DE PERMISSAO ...]: o modulo raw_io.ofs pede 'rift', mas o caprock do programa principal libera so: nada (caprock crust). And a file with stratum crust accepts neither &x nor extern: 

[ERRO DE ESTRATO stratum.ofs:5:24]: endereco '&x' num arquivo 'stratum crust' (sem baixo nivel)

Reference: Stratum and per-module permissions.

The Rift: native system functions

The Rift is the crack through which OFS calls the system's native libraries (libc, libm, X11, Android JNI). There is no C code in OFS: the compiler and the runtime are written in OFS. Declare the function with rift vein (or extern vein) and ask for claim rift. It works the same in ofs run and ofs build. 

claim rift

rift vein strlen(s: obsidian) -> stone bind "strlen" abi c
extern vein puts(s: obsidian) -> stone

core main() {
    echo(strlen("obsidiana"))    // 9
    puts("written by libc")
}

A vein or a geode without captures can be handed to the system as a callback (for example the comparator of qsort); f32 and crystal also cross the Rift. Reference: `extern vein` and `rift vein`.

quartz: inline assembly

quartz { ... } writes machine instructions inside the vein, AT&T syntax by default. It is only valid in abyss and is architecture-specific (the example is x86-64). 

claim abyss, quartz

abyss vein add(a: stone, b: stone) -> stone {
    forge total: stone = 0
    quartz {
        "movq $1, $0"
        "addq $2, $0"
        in "r" a
        in "r" b
    } -> total "=&r"
    return total
}

core main() {
    echo(add(20, 22))    // 42
}

In ofs run, a vein with quartz becomes native automatically (it needs clang on the first run). Reference: `quartz`.

18. Loading OFS at run time: magma.cast

A program can compile a mod written in OFS while it runs and call its veins: plugins, game scripts. Since new code enters the process, the file needs claim magma. 

// mods/forge.ofs
vein forge_it(n: stone) -> stone { return n * n + 1 }

attach {magma}
claim magma

core main() {
    forge m = magma.cast("mods/forge.ofs")
    if (!magma.cooled(m)) {
        echo(magma.crack(m))       // the compiler's message
        return
    }
    forge forge_it: vein(stone) -> stone = magma.vent(m, "forge_it")
    echo(forge_it(10))             // 101
    magma.release(m)
}

A mod error does not bring the program down: magma.cooled gives false and magma.crack returns the message. Reference: `magma.cast`. Repository example: ofs/examples/magma_cast_demo.ofs.

19. Everyday tools

All the tools below are programs written in OFS that ofs compiles the first time and caches. The full list is in TOOLS.md.

ofs fmt and ofs polish: format

Fixes indentation and spacing without changing the program. ofs polish is the same command under another name. 

ofs fmt messy.ofs          # rewrites in place
ofs fmt --diff messy.ofs   # only shows the difference
ofs fmt --check src/       # in CI: lists what would change and exits with 1

// before                          // after
vein sum(n:stone)->stone {         vein sum(n: stone) -> stone {
  forge t=0                            forge t = 0
  ...                                  ...

ofs test and ofs twin: verify

ofs test [folder] runs every x.ofs that has an x.expected beside it and compares the output. ofs twin x.ofs runs interpreted and native and confirms they give the same result. 

printf '55\n' > count.expected     # the expected output of count.ofs
ofs test .        # ok    count.ofs  /  resumo: 1 ok, 0 falha(s), 1 teste(s)
ofs twin count.ofs                 # iguais: count.ofs

ofs doc: documentation from the code

Comment each declaration with // right above it and ofs doc generates a reference site (one page per module, search and coverage). 

// Sums the first n numbers.
// @param n how many numbers to sum
// @returns the sum from 1 to n
vein sum(n: stone) -> stone { ... }

ofs doc count.ofs -o docs_api   # generates docs_api/index.html
ofs doc --check                 # only the coverage and the functions cited in .md files that do not exist

ofs fossil: record a run and travel back in time

ofs fossil runs the program and records, in a .fossil file, everything that comes from outside and changes each time (clock, random, input, files, network). replay repeats the run with the recorded values, without touching the world, and lets you stop at any point. 

claim rift
extern vein rand() -> stone
extern vein time(t: stone) -> stone

core main() {
    echo(rand() % 1000)
    echo(time(0) > 0)
}

ofs fossil rec.ofs                      # 383, true  (records rec.fossil)
ofs fossil replay rec.fossil            # 383, true  (the same, always)
ofs fossil replay rec.fossil --to L7    # stops at line 7 and shows locals and globals
ofs fossil replay rec.fossil --dig      # interactive mode, with step back

(The random number changes on every recording; replay always returns the recorded one.)

ofs quarry: packages

ofs quarry installs community libraries so that attach finds them with no configuration. 

ofs quarry search colors             # searches the registry
ofs quarry add terminal-colors       # installs and records in ofs.claim / ofs.lode
ofs quarry list                      # what is installed

4. Functions and intents

Regular functions

vein soma(a: stone, b: stone) -> stone {
    return a + b
}

Default parameter values: vein escala(x: stone, k: stone = 2) -> stone. The default is a literal (number, text, bool, null or -number) and parameters with defaults come last ([ERRO SEMANTICO] otherwise). A call that omits the last arguments gets the default (escala(5) = escala(5, 2)), the same natively and interpreted; it also works for impl methods. A function type vein(...) does not keep defaults: a call through a vein value passes every argument. Under Fault Refract, adding a parameter with a default to a vein in use is an accepted swap (old calls get the default).

Program entry

core main() {
    echo("ok")
}

vein square(x: stone) -> stone intent pure {
    return x * x
}

Accepted intents:

  • pure
  • impure
  • fractal

Functions can call other functions and support direct recursion: 

vein quadrado(n: stone) -> stone {
    return n * n

vein soma_quadrados(a: stone, b: stone) -> stone {

core main() {

Function types and vein values

A declared vein is also a value: its name (without calling it) has the function type vein(T1, T2) -> R, written with the same word that declares functions. Without -> R the return is void. The type works for variables, parameters, returns, monolith fields and Array<...>, and it needs no low-level block: it is safe and typed. 

monolith Operacao {
    nome: obsidian
    calc: vein(stone, stone) -> stone
}

vein dobro(x: stone) -> stone { return x * 2 }
vein triplo(x: stone) -> stone { return x * 3 }
vein soma(a: stone, b: stone) -> stone { return a + b }

// vein as argument and as return
vein aplicar(f: vein(stone) -> stone, x: stone) -> stone { return f(x) }
vein escolher(grande: bool) -> vein(stone) -> stone {
    if (grande) { return triplo }
    return dobro
}

core main() {
    forge f: vein(stone) -> stone = dobro   // or: forge f = dobro
    echo(f(21))                  // 42
    echo(aplicar(triplo, 4))     // 12
    echo(escolher(true)(10))     // 30

    forge op: Operacao
    op.calc = soma
    echo(op.calc(3, 4))          // 7

    forge ops: Array<vein(stone, stone) -> stone> = [soma]
    echo(ops[0](6, 7))           // 13

    echo(f == dobro)             // true
    echo(f)                      // dobro
}
  • Value: the name of a module vein, of ns.vein, of a method (Rect__area) or of an extern/rift vein (with bind, the native symbol) is a value of its signature's type. A variadic extern (printf) cannot become a value (clear error).
  • Call: f(x) with f a variable, parameter, global, field (s.cb(x)), element (a[i](x)) or result (escolher(true)(10)) is a typed indirect call. typeck checks the arity and the arguments with the conversions of section 2 (f(5) with a crystal parameter means f(5.0)); an argument with no defined conversion (obsidian where the type asks for stone) is an [ERRO DE TIPO], not a warning. The result has type R.
  • Exact signature: storing a vein in a place of function type (forge, =, argument, return, field, push) requires the same signature, parameter by parameter and in the return; the error says what differs (retorno: obsidian onde o tipo pede stone). null fits any function type and is the initial value of a variable or field without an initializer.
  • Equality: == and != between values of the same signature or with null. Two values of the same vein are equal in both modes.
  • `echo` and text: echo(f) and "x" + f give the vein's name (dobro; ns.f for ns__f), null if null and <vein> for an address that came from C and has no name in the program. Same in both modes.
  • Calling `null`: runtime error ofs: chamada de vein nula (o valor de vein e null) on stderr and exit code 1, in both modes.
  • Native: the value is the function pointer (ptr @dobro) and the call is call R (T1, T2) %f(...) with the exact LLVM signature of the type, crystal included.
  • Interpreter (`ofs run`): the value of an interpreted vein is the vein itself (direct call, no trip through C). When the value goes to C (argument of an extern/rift vein) it becomes the callback trampoline of section 11; when it comes from C (an extern return, a callback parameter, raw memory) the type's signature picks the Rift trampoline. A trampoline that comes back from C is recognized as its original vein.
  • Raw address: f as stone, f as *u8, address as vein(...) and fault_addr(f) convert between a vein value and an address; only inside abyss (section 12). fault_call(f, args...) with f of function type checks the signature and means f(args...).
  • In the tree the type is an NK_TYPE_FN whose val is the canonical text without spaces (vein(stone,crystal)->stone), the same type_str as every expression of that type; the indirect call is an NK_CALL __vein_call with the vein in c0.
  • Tests: ofs/tests/regress/vein_type_*.ofs.

geode: a vein that captures (closure)

geode (parameters) -> R { body } is an expression: an unnamed vein that reads variables from the enclosing scope. Its value has the function type vein(T...) -> R above and is used like any vein value: store it in a variable, field or Array, pass it, return it and call it. Without -> R the return is void. The name comes from the geode, the hollow stone that keeps what it captured. 

vein somador(base: stone) -> vein(stone) -> stone {
    return geode (x: stone) -> stone { return x + base }
}

core main() {
    forge k = 10
    forge mais_k = geode (x: stone) -> stone { return x + k }
    k = 100
    echo(mais_k(5))            // 15: k was copied when the geode was born
    forge s7 = somador(7)
    echo(s7(1))                // 8
    echo(mais_k)               // <geode>
}
  • Capture by value. Every local variable (or parameter) from outside that the body reads becomes a capture, copied when the geode is created; changing the variable later does not change the geode. Globals are not captured (the geode reads the current global, like a vein). A geode inside a geode captures transitively.
  • What the copy means: the same as passing the variable as a vein argument. Numbers, bool and strata tags are copied; obsidian is an immutable value (the copy is the text); Array and monolith are the same object (the geode sees later pushes and field changes, and what it changes in elements/fields is visible outside). For an independent monolith, copy it first (forge c: P = m) and capture c.
  • Assigning to a capture inside the geode (n = n + 1, n++, &n) is [ERRO DE GEODE]: the capture is a copy and the assignment would not change the outer variable. Use a local (forge v = n) or return the value. shatter/erode in the body outside a loop of the geode itself is also an error (the body is another vein).
  • Equality and text: each creation of a capturing geode is a distinct value (== is true only with itself); a geode without captures is always the same value. echo(g) and "x" + g give <geode> in both modes.
  • Rift (C): a geode without captures is an ordinary vein and goes to C as a callback (qsort(v, n, 8, geode (a: *stone, b: *stone) -> i32 { ... })). A capturing geode cannot go to C (C only calls a function address): passing a capturing geode literal to an extern is [ERRO DE GEODE] at compile time; if it reaches C through a variable, or becomes an address (as stone, fault_addr), the program stops with ofs: geode com captura nao pode ir para o C (Rift) nem virar endereco; ... on stderr and exit code 1, in both modes.
  • How it works: the typeck finds the captures and lifts the body into a vein __geode_<vein>_<k>(captures..., parameters...) at the end of the program. Natively, without captures the value is ptr @__geode_...; with captures it is a heap environment [adapter, mark, capture 0, ...] (8 bytes each) and the value is that address with bit 0 set; an indirect call tests the bit (only in modules that have a capturing geode, so other programs' IR is unchanged) and calls adapter(environment, args). In the interpreter the value is the body vein plus an environment (an interpreted array with the captures). The environment lives until the program ends.
  • Crystallization and Fault Refract: in a program with geodes, a vein that handles vein values (or calls one that does) stays interpreted; a geode body is an ordinary vein and can crystallize. In ofs refract, editing a geode body (same captures and parameters) swaps live, including geodes already created; if the captures change, geodes already created keep the old body and new ones use the new body.
  • Tests: ofs/tests/regress/geode_*.ofs, the geode case in ofs/tests/refract/run.sh.

Contracts and refined types (mineral, grain, bearing, settle)

A `mineral` is a type with a rule: a base type plus one or more `grain` clauses (inside the rule, value is the value being checked). A vein can have `bearing` (precondition: the caller guarantees it) and `settle` (postcondition: holds for the return; result is the returned value), as many as needed, between the signature and the body. 

mineral UserId = stone grain value > 0
mineral Email = obsidian grain contains("@")
mineral Nota = stone grain value >= 0 grain value <= 10

vein dividir(a: stone, b: stone) -> stone
    bearing b != 0
    settle result * b + a % b == a
{
    return a / b
}
  • Compatibility: a mineral is its base type for the type checker, llvmgen and the interpreter. Base → mineral checks the rule (forge x: UserId = e, x = e, x += e, x++, a monolith field of mineral type obj.f = e, an argument for a mineral parameter, return from a -> UserId vein); mineral → base is free. Array<UserId>, *UserId, as UserId and vein(UserId)->T behave as the base, unchecked.
  • Mineral of a mineral: mineral Small = UserId grain value < 100 adds the rules (the base ones first).
  • `grain` shorthand: a call with no value among its arguments gets value as the 1st argument; contains/len with no vein of that name are the text ones: contains("@") = ofs_str_contains(value, "@"), len() >= 2 = ofs_str_len(value) >= 2.
  • `result` is only valid in settle (in bearing it is an error). In settle, parameters have their entry values even if the body changes them. In a vein without a return value, settle is checked at each return and when falling off the end.
  • `mineral`, `grain`, `bearing`, `settle`, `value` and `result` are contextual words, not reserved: they still work as names elsewhere.

A value proven correct at compile time gets no run-time check. A contract failure is not a throw: tremor/catch does not catch it. Leaving through ? (propagation) does not check settle.

Boundary cases: `ofs assay file.ofs`. For each vein with a contract and only integer parameters (stone, iN, uN or a mineral with an integer base), it generates cases at the rule boundaries: each comparison of a parameter with a constant (b != 0, n <= 10, grain value > 0) yields the boundary value and ±1; a parameter with no bound uses -1, 0 and 1 (up to 64 cases per vein). Cases outside the bearing/grain are only listed (--); the others are called (ok) and settle checks the result. The first violation stops with the contract message and exit code 1. A rule that depends on anything other than constants and parameters leaves the vein out (pulada). impl veins, non-integer parameters and loop ranges are future work.

forge nums = [1, 2, 3]
echo(nums[0])

Example passing a function: 

vein map_array(arr: Array<stone>, fn: vein(stone) -> stone) -> Array<stone> {
    forge result: Array<stone> = []
    cycle (n in arr) {
        ofs_array_push(result, fn(n))
    }
    return result
}

Indexing is zero-based and has bounds checking at run time: 

forge nums = [10, 20, 30, 40, 50]
forge primeiro = nums[0]   // 10
nums[2] = 99               // changes an element

Out of bounds (nums[7], ofs_array_get/ofs_array_set), the program stops with exit code 1 and a message on stderr, the same in both modes: 

ofs: indice 7 fora do limite do array (tamanho 5)

The check applies in ofs run, in the default ofs build and in ofs build --release: the inline fast path of arrays (A6) already compares the index with the size before the direct access and falls into the runtime when out of bounds. Measured cost (A5.4, bench/): no noticeable difference in the 6 benchmark programs (sort 14 × 13 ms); in a loop that only reads and writes a[k] (100 million accesses) 137 × 126 ms (~9%). That is why release keeps the check (the release IR does not change).

Multi-branch selection

Multi-branch selection is done with chains of if / else if: 

if (code == 200) {
    echo("ok")
} else if (code == 404) {
    echo("nao encontrado")
} else {
    echo("erro")
}

Or with match (synonym: assay), which compares the value with each case using ==; _ is the default case: 

match (code) {
    200 => { echo("ok") }
    404 => { echo("nao encontrado") }
    _ => { echo("erro") }
}

Error handling and interruption (throw)

The throw statement displays a diagnostic message and ends execution with exit code 1: 

vein dividir(dividendo: stone, divisor: stone) -> stone {
    if (divisor == 0) {
        throw "divisao por zero indefinida"
    }
    return dividendo / divisor
}

core main() {
    echo(dividir(10, 2))
}

Note: The syntax tremor { ... } catch (e: obsidian) { ... } is recognized by the grammar (NK_TREMOR), with structured stack unwinding and runtime capture planned for the interpreter and runtime evolution layers.

strata (variant enumerations)

strata Status { Idle, Running, Failed }

Note: a variant is a numeric tag (v as stone) and can be stored in a strata type (forge c: Status = Idle, parameters, return values, Array<Status>). echo(c) prints the name (Idle) in both modes. The payload of Ok(7) is not stored by native code yet (see ? propagation).

? propagation

expr? unwraps a result variant:

  • Solid(v)? and Ore(v)? evaluate to v.
  • Crack(e)? and Barren? leave the current vein immediately (pending anchors run), propagating the failure. Failure variants are the ones named Crack and Barren; any other variant counts as success.

The propagated value is the same in both modes:

  • In the native build variants are payload-less i64 tags: the tag is the variant's position in declaration order across all strata of the program (with strata Outcome { Solid, Crack } declared first, Crack = 1). A vein ... -> stone that propagates Crack returns that tag, and echo prints 1 in both modes. With an obsidian return you get the tag as text; with crystal, the number; in core main it becomes the exit code.
  • In the interpreter, if the declared return type is the strata type itself (-> Outcome), the whole variant (with payload) is returned.
  • Since native code keeps no payload, x? over an expression that is not a direct constructor (e.g. f()?) evaluates to the success variant's tag, not its payload.
strata Outcome { Solid, Crack }

vein ok() -> stone {
    forge v = Solid(7)?      // 7
    return v
}

vein bad() -> stone {
    forge v = Crack("boom")? // returns 1 right here
    return v
}

core main() {
    echo(ok())   // 7
    echo(bad())  // 1
}

Test: ofs/tests/regress/question_propagation.ofs.

break and continue

cycle (forge i = 0; i < 100; i++) {
    if (i == 50) {
        break       // leaves the loop
    }
    if (i % 2 == 0) {
        continue    // skips even numbers
    }
    echo(i)
}

break and continue work in cycle and in while. while is syntactic sugar for a cycle with only a condition.

seal and anchor (run on scope exit)

seal { … } and anchor { … } are the same thing (the same token): they register an action that runs when the current scope ends, on any exit (end of block, return, break/shatter, continue/erode, ? propagation). Several actions run in reverse order (the last one registered runs first). seal is the thematic name ("seals the resource on exit"); anchor remains valid. They accept a block or a single command. 

vein copiar(origem: obsidian) -> stone {
    forge f = fopen(origem, "r")
    seal { fclose(f) }          // runs on any return below
    anchor echo("fim de copiar") // same as seal; runs before fclose (LIFO)
    if (f == null) { return 1 }
    // ...
    return 0
}
  • The action is evaluated on exit, with the values of that moment.
  • return, break, continue and throw inside seal/anchor are forbidden (error E0042).
  • Works the same in native code and in ofs run. Test: ofs/tests/regress/seal_defer.ofs.

11. extern vein and rift vein

The Rift is the boundary through which OFS reaches the native system libraries (libc, libm, X11, Android JNI, kernel32). extern vein and rift vein declare a function that lives in a native library. There is no C code in OFS. (The system calling convention is technically known as the C ABI; it involves no C code.)

extern vein

extern vein puts(s: obsidian) -> stone

rift vein

rift vein ofs_window_create(title: obsidian, w: stone, h: stone) -> void abi c

Link metadata

rift vein text_size(s: obsidian) -> stone bind "strlen" abi c

Function address and indirect call (fault_addr, fault_call)

The typed way to pass a vein to C is the function type (section 4): declare the rift vein parameter with the signature and pass the vein's name, without abyss: 

rift vein c_qsort(base: *stone, n: stone, size: stone, cmp: vein(*stone, *stone) -> stone) -> void bind "qsort" abi c

core main() {
    forge v: Array<stone> = [42, 7, 19]
    c_qsort(ofs_array_data(v), ofs_array_len(v), 8, crescente)   // crescente: below
}

The raw case still exists: get the address of a vein as a stone and call an address using the system calling convention. This is useful for native function tables (JNI) and for older code whose parameter is declared as stone (ANativeActivity, ALooper, AChoreographer). 

rift vein c_qsort(base: *stone, n: stone, size: stone, cmp: stone) -> void bind "qsort" abi c

vein crescente(a: *stone, b: *stone) -> stone {
    forge x = 0
    forge y = 0
    fracture { x = *a; y = *b; }
    if (x < y) { return -1 }
    if (x > y) { return 1 }
    return 0
}

core main() {
    forge buf = ofs_alloc(64)
    // ...fills 8 values...
    abyss {
        c_qsort(buf, 8, 8, fault_addr(crescente))
        forge r = fault_call(fault_addr(crescente), buf, fault_step(buf, 1))
    }
}
  • fault_addr(nome) → stone: address of the vein. Accepts a module vein, ns.vein, and extern/rift vein (with bind, it returns the native symbol). In IR: ptrtoint ptr @simbolo to i64. fault_addr(f) with f a vein value means f as stone. Anything else is a semantic error.
  • fault_call(endereco, args...) → stone: indirect call using the system calling convention (inttoptr + call i64). Integer, pointer and obsidian arguments; the return value is read as i64 (void functions return garbage, ignore it). No float/double. When the first argument has a function type (fault_call(f, a, b) with f: vein(...)), the signature is checked (arity and arguments, as in f(a, b)) and the call is the typed one, returning R.
  • The vein used as a callback must have parameters compatible with the system calling convention: stone for integers (32-bit integers arrive with undefined upper bits; mask them with & 4294967295) and *stone for pointers.
  • In the interpreter (ofs run), fault_addr of an extern/rift vein returns the native address and fault_addr of an interpreted vein returns a native trampoline that re-enters the interpreter (the qsort above works the same). See "In the interpreter (ofs run): the Rift".
  • Test: ofs/tests/runtime/test_fault_addr_qsort.ofs.

Important fields:

  • bind "..." sets the actual native symbol
  • abi c selects the system calling convention
  • ... is accepted in a native variadic function

In the interpreter (ofs run): the Rift

ofs run calls the same native system library functions the native build would link, with no C code and no libffi:

  • Resolved at load time. Every extern vein/rift vein called by the program (or passed to fault_addr) becomes an address via dlsym(RTLD_DEFAULT, "symbol"), using bind when present. The interpreter first opens libm (the build links -lm) and the libraries in OFS_FFI_LIBS (libfoo.so:/path/libbar.so); if a symbol is missing it also tries libX11/libXft (ofs build links both when present). A missing symbol gives the linker's error (undefined reference to 'x') before running, with exit code 1. An extern that is declared but never called does not need to exist (as in the link).
  • OFS runtime. ofscc is linked with -rdynamic, so ofs_alloc, ofs_echo_color etc. are found too. Veins defined in stdlib/runtime/*.ofs (pulled in with attach) run the native version linked into ofscc, like the builtins, when the signature fits the Rift; OFS_RUN_RUNTIME=interp turns this off.
  • Conversion. stone, bool, integers (i8..u64, narrowed to width and sign), pointers and obsidian (the value's own char*) go as i64; crystal goes in an FP register. The return follows the declared type: char* becomes obsidian without a copy (as in native code, where obsidian is the pointer; NULL becomes null), *T becomes the address (it can go back to the native function, be compared with null, converted with as and dereferenced), monolith the block and Array the ofs_array itself.
  • Trampolines. The call goes through __ofs_ffi_dispatch, generated by llvmgen inside ofscc: one case with the exact LLVM type per signature class (up to 4 arguments with any stone/crystal mix and an integer or crystal return; up to 12 integer-only; variadics with 1 to 3 fixed and up to 4 extra). Any other class is a clear error.
  • Variadics (printf, snprintf, open...): the ones llvmgen knows by name; extras use the declared type (or the value's type), with the right convention (%al on x86-64).
  • fault_addr(extern) returns the native address and fault_call(address, ...) calls it with arguments in the value's type (as in native code). fault_step adds to a native pointer.
  • Raw memory (F2). The interpreter runs natively, so a pointer is a real address. *p and *p = v read and write with the width of the pointee type (u8/i8/u16/i16/u32/i32/u64/i64/stone/f32/f64/crystal/bool (4 bytes)/obsidian/*T), using the typeck static type (the same one llvmgen uses); narrow integers are sign-extended (iN) or zero-extended (uN), as in native code. A null p faults like native code (address 0). fault_memcpy/fault_memset use real memcpy/memset of any size; fault_step(p, i) adds i * sizeof(*p) with the static type of p.
  • `as` follows the llvmgen rule: same LLVM type only retags; ptrtoint/inttoptr (including obsidian, which is the char* itself); fptosi; sitofp from iN/stone and uitofp from uN ((255 as u8) as crystal is 255.0); fpext/fptrunc (f32 rounds); trunc if the source is wider, otherwise sext from iN and zext from uN/bool ((0 - 1) as i8 as stone is -1). forge x: u8 = 300 and x = v into a u8/i32/f32 truncate like the native store.
  • `&x`. The address of an interpreter variable is real: on the first &x the variable moves into an 8-byte raw-memory slot (the native function can read and write it: sscanf(s, "%d", &n), strtol(s, &end, 10), modf(x, &whole)), freed when the variable goes out of scope, like the native alloca. &x of a monolith is the block itself. Only variables have an address (native code has no &s.field/&a[i] either: use (&s) as stone + offset); &x of an Array variable is a clear error.
  • `monolith` with system layout. Instances live in raw memory with the llvmgen.struct_layout layout (the same as native code: fields in order, each aligned to its own size, up to 8; bool takes 4 bytes; Array and nested monolith take 8). s or &s passed to a native function (memcpy, qsort of structs...) sees the same bytes as the native build. As in native code, a monolith passed to a vein is by reference and forge y: T = x/y = x copy. An Array field holds the interpreter's array (the native function should not read it).
  • `Array` and strings. An Array passed to a native function is the native ofs_array itself ([data, len, cap, elem_size] header + data) of the interpreter's value column; the native function writes elements in place and the length is synchronized on return. Elements of a single type (integers/pointers, crystal, bool, obsidian or monolith); mixed types are a clear error. An Array returned by a native function uses the same block, without copying. obsidian already is the char*. Use ofs_array_data(a) to pass only the data (e.g. qsort).
  • Native → OFS callbacks. fault_addr(vein) of an interpreted vein binds the vein to one of 16 native trampolines (__ofs_cb_0..__ofs_cb_15, generated by llvmgen inside ofscc); the library calls the trampoline, which re-enters the interpreter, including inside a native call made by the program itself (qsort inside qsort, fault_call of another callback). The same vein reuses its slot. Up to 6 parameters that are integers, pointers, obsidian, bool or monolith (by pointer), with an integer/pointer return. A callback with crystal/f32 (parameter or return) uses another table, __ofs_cbx_0..__ofs_cbx_15, which also receives the floating-point registers (up to 6 integers and 8 crystal/f32; wave 4). More than 16 different veins or parameters beyond those limits give a clear error with exit code 1 (use ofs run --native); on Windows x64 (positional registers) a crystal/f32 callback keeps the clear error. The same trampoline serves a vein value passed in a vein(...) parameter (section 4), and crystallization uses both to call interpreted veins back. f32 in the Rift (parameter and return, like sqrtf/powf) works in both modes.
  • fracture and abyss do not change execution in either mode (native code is the same inside them); the typeck requires them for raw-memory operations (see section 12, "Rules"). A bedrock that allocates is also an arena (section 12); in the interpreter, the ofs_alloc written in the block comes from the runtime arena and what may leave it is decided at compile time, as in native code. The bedrock cells and regions (stdlib) use the raw memory above.
  • Tests: ofs/tests/regress/ffi_*.ofs, ptr_widths.ofs, tests/parity/cases/ (ptr_*, libc_*, monolith_memcpy, qsort_fault_addr, fault_call_basic, bedrock_block).

Direction of interoperability

extern vein is the current surface of the Rift, best suited to runtime symbols and native system libraries. The roadmap widens this to: boundaries with native objects and libraries, bridges to other ecosystems, Python embedding and target-specific assembly escapes. These items are roadmap, not features implemented today.

Hybrid pattern

Mixing high and low level in the same file is valid and recommended:

  • business logic in ordinary veins;
  • calls to native libraries through the Rift (rift vein);
  • machine-close work in bedrock;
  • explicit storage with bedrock.ofs.

12. Low-level blocks

fracture

Typed low-level layer.

abyss

Raw and unrestricted layer.

fractal

Special layer tied to intent/effects.

bedrock

OFS vocabulary for memory, regions, lanes, packets and fault_* intrinsics. As a block it unlocks the low-level operations (F4) and, when the block itself allocates, it is an arena (below).

Example: 

attach {bedrock}

core main() {
    forge region = bedrock_region_new(4)
    bedrock_region_write(region, 0, 10)
    bedrock_region_write(region, 1, 20)
    echo(bedrock_region_read(region, 1))
    bedrock_region_drop(region)
}

bedrock { } arena (A5.3)

A bedrock { ... } block (also tectonic bedrock { } and bedrock vein f() { }, which makes the whole body a block) in which the block's own code allocates is an arena: everything it allocates comes from a region that is released at once when the block exits, on any exit (end, return, shatter/erode, ?), after the block's seal/anchors. It still unlocks the F4 low-level operations. A bedrock that allocates nothing is just the low-level block (same code as before). 

core main() {
    forge total = 0
    forge ultimo = ""
    forge i = 0
    while (i < 100000) {
        bedrock {
            forge partes: Array<obsidian> = []
            ofs_array_push(partes, "k" + ofs_stone_to_obsidian(i))
            forge buf: *stone = ofs_alloc(1024)
            fracture { *buf = ofs_str_len(partes[0]) }
            fracture { total = total + *buf }
            ultimo = partes[0]          // text leaves as a copy
        }                               // the whole arena is released here
        i++
    }
    echo(total)
    echo(ultimo)
}
  • What comes from the arena: what the code written in the block allocates: concatenation and conversions to text, [...] and the growth of an Array created in the block, forge m: Monolith, ofs_alloc/ofs_realloc and the runtime's text and Array builtins. ofs_free of an arena block does nothing (it leaves with the region). The arena is lexical: a vein called from inside the block allocates on the normal heap (the compiler turns the arena off during the call), and an outer Array that grows inside the block stays on the heap. A bedrock inside another opens its own arena, which closes before the outer one.
  • Escape (rule): a value that may live in the arena and goes outside it is handled like this: `obsidian` text is copied to the heap automatically (only if it really is in a live arena); `Array`, `monolith`, pointer and geode are [ERRO DE ARENA arquivo:linha:col] at compile time. "Outside" means: return from inside the block, assignment to a variable declared outside the block (local, parameter or global), a field or element of an outer object, push/set into an outer Array, an argument of a vein that keeps the parameter (per-vein analysis, the same idea as A6), of a vein value or of an unknown function, and runtime functions that keep the pointer (the window title). Copying a monolith with only numeric fields into an outer variable is allowed (it is a copy by value). C functions (extern/rift) do not keep their arguments (C convention); if one does, allocate outside the bedrock. Inside abyss { } the error is not raised: the programmer takes the risk.
[ERRO DE ARENA app.ofs:5:17]: valor alocado na arena do bedrock e guardado fora dele (a arena e liberada na saida do bloco)
  dica: aloque fora do bedrock o que precisa sair dele (so texto obsidian e copiado para fora automaticamente), ou use abyss { } para assumir o risco
  • In both modes: the rule is decided at compile time (ofscc/sediment.ofs, after the typeck), the same for native code, the interpreter, crystallization and Fault Refract. Natively, ofs_arena_open() on entry and ofs_arena_close() as a synthetic anchor; the runtime (stdlib/runtime/reservoir.ofs) carves blocks out of 64 KB chunks that double (zeroed like calloc) and keeps the largest one for the next arena. In the interpreter, the ofs_alloc written in the block comes from the same runtime arena and text copied out goes through the same function (ofs_arena_lift).
  • Measured (200 thousand iterations with 16 strings in an Array, a monolith and 1 KB of ofs_alloc per iteration, native -O2): with bedrock 1.9 MB and 0.38 s; the same loop in a plain block (with ofs_free of the buffer) 258 MB and 0.37 s.
Leak warning

A forge p = ofs_alloc(n) (or malloc, calloc, realloc, ofs_realloc) outside an arena whose pointer never reaches a seal/anchor, ofs_free, a call (owner), return, assignment, field, Array or geode produces a warning (not an error) on stderr, in both modes; a bare ofs_alloc(n) whose result is discarded too. OFS_LEAK_WARN=0 silences it.

The typeck requires a low-level block for operations that touch raw memory. The rule is the same in ofs build and ofs run (it comes from the typeck):

  • A whole vein can be marked: fracture vein read(p: *u8) -> stone { return *p }, abyss vein call(f: stone) -> stone { return fault_call(f) } (also inside namespace and impl). The body counts as the block. Code that must build with an ofscc older than this rule (the compiler itself, because of the seed, and the stdlib) uses a fracture { } block inside the vein, which every compiler understands.
  • In the tree the block is an NK_BLOCK with the name in val ("fracture", "abyss"...); llvmgen and the interpreter run it as a plain block (same IR).

fault_* intrinsics

The bit ones work anywhere; fault_step, fault_memcpy and fault_memset require fracture/bedrock/abyss, and fault_addr/fault_call require abyss (table above):

  • fault_count(stone) → count of 1 bits (popcount)
  • fault_fence() → memory barrier
  • fault_prefetch(*stone) → memory prefetch for the pointer's target
  • fault_trap() → machine trap
  • fault_lead(stone) → leading zeros
  • fault_trail(stone) → trailing zeros
  • fault_swap(stone) → byte swap
  • fault_spin_left(stone, stone) / fault_spin_right(stone, stone) → bit rotation
  • fault_step(*stone, stone) → typed pointer advance, in elements
  • fault_addr(vein) → address of the vein as a stone (see section 11)
  • fault_call(endereco, args...) → indirect call using the system calling convention (see section 11)
  • fault_cut(value, shift, width) → extracts a bit field
  • fault_patch(base, shift, width, insert) → replaces a bit field
  • fault_weave(mask, left, right) → mixes the bits of left and right according to mask
  • fault_unreachable() → marks the path as unreachable (generates llvm.trap + unreachable)
  • fault_memcpy(dst, src, len) → block memory copy (llvm.memcpy); dst and src are pointers
  • fault_memset(dst, val, len) → fills memory with the byte val (llvm.memset); dst is a pointer

Exact semantics (the same in the native build and in the ofs run interpreter):

  • Everything is 64-bit, two's complement: fault_count(-1) = 64; fault_lead(0) = fault_trail(0) = 64; fault_lead(-1) = 0.
  • fault_spin_left/fault_spin_right: 64-bit rotation (llvm.fshl/llvm.fshr); the distance is taken modulo 64 (fault_spin_right(6, 65) = 3).
  • fault_weave(mask, left, right) = (left & mask) | (right & ~mask): the bit comes from left where mask has 1 and from right where it has 0.
  • fault_trap() and fault_unreachable() end the process with SIGILL (the interpreter does the same with raise(SIGILL)).
  • fault_fence()/fault_prefetch() do nothing in the interpreter.
  • In the interpreter pointers are real addresses: fault_memcpy/fault_memset copy/fill any size, and fault_step, fault_addr and fault_call work as in native code (see "In the interpreter (ofs run): the Rift").
  • Test: ofs/tests/regress/fault_intrinsics.ofs.

These intrinsics cover operations that assembly already has and give OFS its own machine-oriented vocabulary.

quartz: inline assembly

quartz emits assembly directly into the LLVM IR, with a side effect (sideeffect) by default. It is only allowed in abyss { ... } or abyss vein; fracture and bedrock alone do not authorize assembly. asm remains the CLI command ofs asm, which generates a .s file. 

abyss vein somar(a: stone, b: stone) -> stone {
    forge total: stone = 0
    quartz {
        "movq $1, $0"
        "addq $2, $0"
        in "r" a
        in "r" b
    } -> total "=&r"
    return total
}

core main() {
    echo(somar(20, 22)) // 42 (x86-64)
}
  • No output: quartz { "nop" }. With output: quartz { ... } -> variable "=r"; declare the scalar variable beforehand. The output constraint is optional (=r by default) and goes on the same line as the destination. +r reads and writes the destination; =&r marks an early-clobber output, which cannot share a register with an input.
  • Inputs: in "r" expression, in "{rdi}" expression or in "m" variable (memory of a scalar variable). A single scalar output can be bound to a register. $0 is the output, when there is one; the following inputs are $1, $2, etc. With no output, the first input is $0.
  • Clobbers: put melt "rdx" "memory" after the instructions and inputs to declare altered registers and memory. LLVM does not discover these effects from the text; declare every additional effect.
  • The default dialect is AT&T; quartz att { ... } is explicit and quartz intel { ... } selects Intel. A literal $ is written $$: "shlq $$32, %rdx".
  • The text is architecture-specific. OFSCC_TARGET selects the target but does not translate x86-64 instructions to AArch64/Android. Use assembly appropriate to the target.
  • In ofs build, LLVM compiles the snippet. In ofs run, the vein that contains quartz is loaded as native code in the same process; see Execution model.

Live editing: ofs refract (Fault Refract)

ofs refract app.ofs runs the program interpreted and, while it is open, swaps the veins you edit and save. The unit of swapping is the vein:

  • The swap happens between calls: the next call of the vein uses the new version. A loop running in an edited vein (including the while of main) swaps at the next header (OSR, wave 4): the new loop continues with the local variables as they are, and the rest of the vein after it is also the new one; a new variable before the loop gets its initial value at swap time. If a variable before the loop changed type (or the loop is inside cycle/match/bedrock), the loop ends on the old version and the new one applies on the next call. Outside a loop, the running call ends on the old version.
  • State carries on: existing globals keep their value (the initializer does not run again), and live arrays and objects do not change. A new global is created with its initial value.
  • A crystallized (native) vein or one with quartz is recompiled into a new .so, together with the native veins that call it; the new version runs interpreted until the .so is ready (those with quartz, which cannot run interpreted, are compiled before the swap).
  • The whole new program is checked first (syntax and types): with an error, nothing changes.
  • A compatible signature swaps even with the vein in use: a new parameter at the end with a default value; the same return, which was void, a narrow integer where it was stone, f32 where it was crystal.
  • A `monolith` with live instances migrates: a new field gets the type's default value, a removed field disappears, the order may change and a numeric field may change type (the value is converted). Instances are rewritten in place.
  • Need a restart (the swap is refused and the program continues with the old version): changing the signature incompatibly in a vein that a running vein still calls, or of a vein handed to C as a callback or used as a value; removing a vein that something running still calls; changing a live monolith field to a type that does not convert (e.g. stone → obsidian) or growing the monolith by more than 64 bytes; changing the type of a global; changing an extern; removing or reordering strata variants (adding at the end is allowed).

Example: ofs/examples/refract_demo.ofs. Command, messages and variables: TOOLS.md. Mechanism: COMPILER_ARCHITECTURE.md.

Compiling and loading OFS at runtime: magma.cast (Idea 5)

A program (under ofs run and as an ofs build binary) compiles a mod written in OFS while it runs and calls its veins: plugins, game scripts, mods. A mod is an OFS file with veins only (no core main; stdlib attach works). Stdlib module: attach {magma}. 

attach {magma}
claim magma                       // loading code at runtime is a permission

core main() {
    forge m = magma.cast("mods/forja.ofs")      // a path, or the source itself (text with \n)
    if (!magma.cooled(m)) {
        echo(magma.crack(m))                    // the compiler message; the program keeps going
        return
    }
    forge forjar: vein(stone) -> stone = magma.vent(m, "forjar")
    echo(forjar(10))
    forge erro: vein(crystal) -> stone = magma.vent(m, "forjar")
    if (erro == null) { echo(magma.crack(m)) }  // the mod's signature differs from the requested one
    magma.release(m)
}
  • magma.cast(source) → a stone handle (always ≥ 1). A source with a line break is the code itself; otherwise it is a file path. Syntax, type, permission or load errors never take the program down: magma.cooled(m) is false and magma.crack(m) holds the compiler message (text sources show up as <fonte>).
  • magma.vent(m, "name") → a typed vein value (F6). The type is the one of the place that stores the value (forge f: vein(T) -> R = ..., =, argument, return): the compiler passes it as the requested signature, and at runtime it is checked against the one declared in the mod (the .so manifest). Mismatch or missing vein: the value is null and magma.crack(m) says what differs. With no destination type (forge f = magma.vent(...)) it is a [ERRO DE TIPO]. Namespace veins use the program name ("lava.grau").
  • magma.veins(m) lists name: signature; magma.release(m) stops the mod from handing out veins (the code stays loaded: vein values, strings and addresses already handed out may be stored, the same caution as Refract wave 4); magma.caprock("crust") is the ceiling for the next mods ("rift", "rift, abyss"…; "" removes it).
  • Globals: the mod does not see the program's globals and vice versa; they talk through arguments, return values and vein values (a mod may receive a program vein as a callback). The mod's globals are its own and start at load time. The same source (same generated code) gives the same .so and the same module (shared state); an edited mod is another .so, and the old version stays valid for whoever kept its veins.
  • Boundary: signature types are the F6 ones (scalars, obsidian, Array<T>, vein values, monolith by name: both sides must declare it the same way). Rift limits under ofs run: up to 12 integer parameters, or up to 4 with crystal.
  • Security: calling magma.cast requires claim magma at the top of the file; it is always an error ([ERRO DE PERMISSAO], no migration). In a stratum crust file it is [ERRO DE ESTRATO]; stratum abyss counts as claim magma. The magma module declares claim rift, abyss, magma, so a caprock without magma forbids attaching it. The mod is compiled in strict mode (OFS_STRICT_FAULT=1) with the magma.caprock ceiling applied to all of it (including the mod file and its attaches).
  • How it works: the mod is compiled by ofscc in a separate process (OFSCC_MODE=cast: the ir output plus the @__magma_manifest), turned into a .so by clang (-shared -fPIC -O2 -Wl,-Bsymbolic) in a cache keyed by the hash of the generated IR (expanded source with its attaches, clang and system; OFS_MAGMA_CACHE, $XDG_CACHE_HOME/ofs/magma or ~/.cache/ofs/magma) and opened with dlopen (RTLD_LOCAL); the mod's globals are initialized once (__ofs_init_globals). The mod uses the program's runtime (same heap, stdout and strings): under ofs run the ofscc is already linked with -rdynamic; ofs build links programs that use magma.cast with --export-dynamic (linking by hand: -rdynamic; without it, magma.crack says how).
  • Compiler and clang: OFS_MAGMA_OFSCC; under ofs run, the running ofscc itself; otherwise $OFSCC, the ofscc next to the ofs on PATH, ~/.local/lib/ofs/ofscc, ofscc on PATH, /usr/local/bin, /usr/lib/ofs. The mod's stdlib: OFS_STDLIB_PATH or the folder next to ofscc. clang: OFS_MAGMA_CC (or OFS_QUARTZ_CC), else clang. If one is missing, the error comes back in magma.crack. OFS_VERBOSE=1 shows the .so and whether it came from the cache. Linux and macOS (on Windows, magma.crack says it does not exist yet).
  • Example: ofs/examples/magma_cast_demo.ofs (mod in ofs/examples/magma_mods/forja.ofs). Tests: ofs/tests/regress/magma/ and magma_err_*.ofs.

OFS: A Truly Hybrid and Native Compiled Language

The Fundamental Question: Is OFS Interpreted or Compiled?

Answer: OFS is HYBRID — High-Performance Native AOT Compilation via LLVM and Instant AST Interpretation.

OFS unites the strengths of both execution models:

  1. Native Ahead-Of-Time (AOT) Compilation (`ofs build`): Directly generates LLVM IR from its self-hosted compiler frontend (ofscc), yielding machine code linked into standalone platform executables without virtual machines or embedded interpreters.
  2. Instant In-Memory AST Interpretation (`ofs run` / `ofs <file.ofs>`): Directly evaluates the typed Abstract Syntax Tree (AST) in memory using an integrated, pure-OFS interpreter backend (interpreter.ofs), supporting scripting and experimentation; hybrid native code may require compilation on a cache miss.

Execution model: interpreted and compiled with the same semantics

The golden rule compares ofs run program.ofs with ofs build program.ofs followed by execution of the binary: output, exit status and observable effects should match. A shared lexer, parser and type checker provide the foundation; tests provide the evidence. Run bash tests/parity/run.sh and inspect the parity matrix, which distinguishes matching programs, differences, expected errors and skipped cases. A difference is a bug or a documented limitation, rather than a second language semantics.

ofs run evaluates the typed AST. extern and rift vein call native symbols resolved by the Rift; pointers are real addresses and callbacks let C reenter an interpreted vein. ofs build emits LLVM IR and links an executable independent of the interpreter. ofs run --native compiles and executes the whole program in a temporary directory.

Programs using quartz run in hybrid mode: the interpreter identifies veins containing assembly, asks llvmgen for a module containing their dependency closure, and loads a native library into the same process. Other veins start interpreted and may later be promoted by crystallization. Functions called by the closure have native versions in the module; interpreted vein values passed to native code use callback trampolines. Scalar globals are synchronized on native entry, exit and callbacks; strings, arrays and objects share memory according to the representations supported by the Rift. The cache hashes the IR and compilation command (OFS_QUARTZ_CACHE, or $XDG_CACHE_HOME/ofs/quartz, or ~/.cache/ofs/quartz). OFS_VERBOSE=1 reports compilation or cache reuse. A cache miss requires clang; OFS_QUARTZ_CC selects the compiler.

The hybrid boundary inherits FFI dispatcher limits: up to 12 integer/pointer arguments or up to 4 arguments including crystal/f32; floating-point callbacks use the __ofs_cbx_K trampolines (outside Windows x64). The same native logic can approach build performance once compiled, but AST interpretation, library compilation and boundary crossings have costs. Performance equivalence requires measurements that distinguish warmup from cached execution.

Crystallization: hot veins become native

By default, ofs run counts calls to each eligible vein. At OFS_CRYSTALLIZE_THRESHOLD (default 1000, an integer from 1 to 1000000000), it generates IR for a single module containing veins with supported signatures and their dependencies. clang -O2 compiles the library in the background while interpretation continues; later calls poll for completion and switch to native dispatch. IR generation is synchronous. Batch promotion maintains one native copy of globals. With quartz, the required module is compiled at load time; other eligible veins gain native dispatch when the heat trigger fires.

OFS_CRYSTALLIZE=0 disables optional promotion while preserving hybrid quartz. OFS_VERBOSE=1 reports promotion and optional failures. Without clang, or if optional compilation fails, interpretation continues; a vein requiring quartz still requires native compilation. Signatures lacking supported trampolines, such as f32 at the boundary, are not promoted as roots. A long loop inside one call (the while in main, for instance) switches mode in the middle (OSR, wave 4): after OFS_CRYSTALLIZE_THRESHOLD iterations the loop is extracted into a native function, compiled in the background, and continues there with the live variables transferred; bench/ofs/loop.ofs drops from 18.6 s to 0.34 s (the native build takes 0.41 s). Only while loops without return/throw/?/&/geode in the body; OFS_OSR=0 turns it off. The cache avoids later compilations but does not remove IR-generation and library-loading costs. Compare cold, cached and AOT-binary times before claiming equivalent speed.

Safe low-level code

Safe code can call typed veins without a low-level block. Use fracture (or bedrock) for pointer operations such as &x and *p, and abyss for raw function addresses, raw fault_call and quartz. The type checker enforces the same rule in both modes: OFS_STRICT_FAULT=1 makes violations errors; the default migration mode warns until 2027-01-09. These blocks authorize operations but do not automatically validate an address or its lifetime. See the language reference for FFI and callback limits.

strbuf.ofs

Text buffer whose capacity doubles when full (amortized O(1) append). Use it when text is built in many steps or passes through several functions:

  • strbuf.create(capacity): creates an empty StrBuf.
  • strbuf.append(b, text), strbuf.append_char(b, byte_code), strbuf.append_int(b, n): append to the end.
  • strbuf.to_obsidian(b): returns a copy of the contents (the string does not change if the buffer keeps growing).
  • strbuf.length(b), strbuf.clear(b) (empties it, keeps the capacity), strbuf.release(b) (frees the memory).
attach {strbuf}

core main() {
    forge b: StrBuf = strbuf.create(64)
    strbuf.append(b, "total: ")
    strbuf.append_int(b, 42)
    echo(strbuf.to_obsidian(b))
    strbuf.release(b)
}

It works the same in ofs build and ofs run (it uses raw runtime memory, which the interpreter reaches through the Rift).

Strings and memory. Strings have no GC or reference counting: t = s makes both variables point to the same text. The native compiler only reuses or frees memory when it proves nobody else sees the value: s = s + x / s += x on a local variable that is never copied elsewhere grow in place; the intermediate parts of a + b + c and an f(a + b) whose parameter is not stored are freed; local arrays that do not escape are freed at the end of their scope. If the variable is copied, stored in a field/array or passed to a function that keeps it, everything works as before (a new copy on every +).

Points the grammar does not show:

  • The parentheses of if, while, match/assay and cycle/mine are required. if x == 1 { } fails with expected '('. The body must be a { } block.
  • The semicolon is optional at the end of statements and declarations. It is only required inside a C-style cycle.
  • assay is just another name for match (same token). match becomes a chain of if comparing with ==; _ is the default case and => separates pattern and body. There are no destructuring patterns.
  • shatter and erode are synonyms of break and continue. mine works like cycle ... in but only accepts the item in collection form.
  • Namespace calls (ns.fn(x)) become the symbol ns__fn. impl methods become Type__method.
  • attach {path} is only valid at file level. The text between the braces is glued token by token (F: marks a file path).
  • There is no struct literal (P { x: 1 }) and no monolith ... layout ...; the parser expects { right after the monolith name. Declare the variable (forge p: P) and assign the fields.
  • core is a reserved word: it marks the entry point (core main()) and cannot be used as a name.
  • Function type (F6): vein(T1, T2) -> R becomes an NK_TYPE_FN with the parameter types in extra, the return in c1 and, in val, the canonical text without spaces (vein(T1,T2)->R; without ->, void), which is the type_str of every expression of that type. The type's text helpers (vein_type_params, vein_type_ret, type_list_at, which splits on commas outside parentheses) live in ast.ofs and are shared by the three stages.
  • Calling something that is not a name (a[i](x), f(1)(2), s.a.b(x)): the parser keeps the called expression in the NK_CALL's c0; typeck decides whether it is a vein value or the old call by name.

Phase 2b: Contracts (ofs/ofscc/contracts.ofs, A5.1)

Runs between the parser and the type checker, in both modes (llvmgen and the interpreter get the same tree), and on every Fault Refract reload (refract_reload):

  1. Registration: NK_MINERAL nodes (mineral Name = T grain ...: c0 = base type, extra = NK_CONTRACT "grain") leave the tree; each vein's bearing/settle clauses live in an NK_BLOCK at c3 of the NK_FN_DECL (NK_CONTRACT, val = the word, c0 = the rule). A mineral of a mineral adds the rules; a repeated name, a cycle or an existing type name is [ERRO DE CONTRATO]. The grain shorthand (contains("@") → ofs_str_contains(value, "@")) is rewritten here.
  2. Static check: a constant evaluator (integers, booleans and text; + - * / % & | ^, comparisons, && || !, ofs_str_contains/ofs_str_eq/ofs_str_len, global const with a literal; a name declared in the local scope is unknown) checks calls to veins with bearing/mineral parameters, forge/assignment of a mineral, return from a -> Mineral vein and a settle that only depends on result. Definitely false = [ERRO DE CONTRATO file:line:col] + regra em ...; the driver stops (as on a syntax error). Definitely true skips the run-time check.
  3. Run-time check (off with OFS_CONTRACTS=0, which ofs build --release sets): plain OFS code inserted into the tree. At vein entry, if (!(grain)) + a call to the __ofs_contract_fail builtin with the message per mineral parameter and per bearing; after forge/=/+=/++ on a mineral (local, parameter or obj.field with an object of declared type); each return e becomes { forge __settle_result: R = e; checks; return __settle_result } (result → __settle_result; a parameter changed in the body and cited in a settle gets a __settle_in_p copy at entry). The message is built at run time from the rule text (expr_text), the location (ast_src_loc) and the values (ofs_stone_to_obsidian, ofs_crystal_to_obsidian, __ofs_bool_text, quoted text).
  4. Erasing minerals: every NK_TYPE/NK_TYPE_FN/NK_CAST in the program replaces the mineral name by its base (Array<UserId> → Array<stone>); the type checker, llvmgen and the interpreter never see minerals. Each erased node keeps a note (contracts.type_note) with the mineral and its rules, which Fault Refract adds to the signature (rf_sig/rf_mshape/global type): changing the grain of a used type is a type change.

The __ofs_contract_fail builtin (one argument: the message) is the only new one: void in the type checker; in llvmgen it becomes the runtime's ofs_array_fail(msg, ofs_str_len(msg)) (already present: "ofs: " + msg on stderr and exit(1); declared only when the module uses it); in the interpreter, BI_CONTRACT_FAIL writes the same text and exits with 1. A program without mineral/contracts goes through none of this (identical IR).

OFSCC_MODE=assay (ofs assay): before phase 2b, contracts.assay_source builds the text of a core main with the boundary cases (bounds of comparisons against constants in the rules, ±1; cases outside bearing/grain only listed), the driver parses it and assay_splice replaces the program's core main with it; then it runs interpreted with checks on.

Phase 3b: Sediment (ofs/ofscc/sediment.ofs, A5.3): bedrock arena and leaks

Runs after the typeck (it uses the types), in both modes, in ofs check and on every Fault Refract reload. A program without an allocating bedrock and without a dangling ofs_alloc does not change (identical IR).

  1. Levels. Each expression has a level: 0 = heap (or outside any arena), d = the arena of the bedrock at depth d. An allocation in the block itself (text +, [...], forge m: Monolith, the runtime's text/Array/ofs_alloc builtins) is d; reading a variable is its content; field, element, *p and ? take the base's level; a vein call takes the highest level of its arguments (it may return one of them). Variable: "home" level (depth of the declaration) and content (highest level assigned, capped at home), iterated to a fixed point, stored per declaration node.
  2. Kept parameters. Per vein, the mask of parameters that may be kept (assigned to a global, field, element, *p, push/set, captured by a geode, passed to a kept parameter of another vein or to an unknown vein/C); return does not keep. Fixed point across all veins, starting pessimistic (recursion stays kept). extern/rift (C) do not keep; runtime functions that keep (window title) do.
  3. Escape. A value whose level is higher than the place it goes to (return inside the bedrock, outer variable/global/parameter, field/element of an outer object, push/set, kept argument): obsidian is wrapped in the __bedrock_lift wrapper; text s += x going out becomes s = lift(s + x) (the __bedrock_lift wrapper); anything else is [ERRO DE ARENA] (outside abyss). Copying a pointer-free monolith into an outer variable is allowed.
  4. Mark. A bedrock NK_BLOCK with some allocation in its own code gets type_str = "arena". The llvmgen calls ofs_arena_open() (slot on the stack) and registers the close as a synthetic anchor (register_scope_free, kind 3: ofs_arena_close), run on every exit (emit_anchors_from_depth); inside it, every call that is not a runtime text/Array builtin (sediment.arena_builtin) runs with __ofs_arena_cur = null (the arena is lexical). __bedrock_lift becomes ofs_arena_lift. In the interpreter, exec_arena_block opens the runtime arena through dlsym, keeps it inactive for the interpreter's own allocations, and only the ofs_alloc written in the block (same vein) uses __ofs_arena_alloc.
  5. Runtime (stdlib/runtime/reservoir.ofs): ofs_alloc takes from the active arena (bump in 64 KB chunks that double, zeroed); ofs_free of a live arena block does nothing; ofs_realloc grows in place (last block) or copies inside the same arena; an Array grows in the region of the Array itself (__ofs_alloc_like), so an outer Array stays on the heap; ofs_arena_close also closes arenas opened above it, keeps the largest chunk and resets the ofs_str_char_at cache.
  6. Leaks. Per vein, outside "arena" blocks: a local variable that receives ofs_alloc/malloc/calloc/realloc/ofs_realloc and never appears in an owner use (call argument, return, right side of an assignment, Array, seal/anchor, geode, &p; *p, field, index and comparison do not count), or a bare allocation: [AVISO DE VAZAMENTO] on stderr. OFS_LEAK_WARN=0 turns it off.

Type Checking Rules

  1. Literals:
  • 42 → stone
  • 3.14 → crystal
  • "hello" → obsidian
  • true/false → bool
  1. Binary operations:
  • Arithmetic (+ - * /): both operands must be numeric
  • Comparison (== != < <= > >=): return bool
  • Logical (&& ||): operands and result are bool
  1. Variable declarations:
  • forge x: stone = 42 → explicit type
  • forge y = 42 → inferred as stone
  • const z = 100 → inferred, immutable
  1. Function calls:
  • Arguments count must match parameters
  • Argument types should be compatible with parameters
  1. Function types (F6): the name of a vein/extern (SYM_FN) used as a value gets the type vein(params)->ret of its declaration (fn_value_ident; an extern of a variadic C symbol is an error). f(x) with f a variable/parameter of vein type, s.field(x) with a vein field (vein_field_callee), a c0 coming from the parser and fault_call(f, ...) with a typed f become an NK_CALL __vein_call with the vein in c0 (check_vein_call): the arity is checked and each argument is converted to the parameter type with the F3 rules, but no defined conversion is an [ERRO DE TIPO] (not a warning). coerce_value requires the same signature when storing a vein value (fn_store_check, with a hint of what differs); ==/!= only between the same signature or with null; as between a vein and an address requires abyss. echo(f) and "x" + f get the __ofs_vein_name conversion (the vein's name in both modes).
  1. Low-level needs a block (F4; an allocating `bedrock` is also an arena: Phase 3b): the parser keeps fracture/bedrock/abyss/tectonic [X] as an NK_BLOCK with the name in val (the body of fracture vein/abyss vein too); llvmgen and the interpreter run it as a plain block. The typeck tracks the depth (_fracture_depth, _abyss_depth, modeled on _anchor_depth) and, in require_fault, requires the block for *p, &x, as with a pointer, fault_step/fault_memcpy/fault_memset (any block) and fault_call/fault_addr (abyss only). Outside the block: [AVISO DE FALHA file:line:col] on stderr until 2027-01-09; with OFS_STRICT_FAULT=1, [ERRO DE FALHA ...] and _semantic_errors++. Full rule: LANGUAGE_REFERENCE.md, section 12.
  2. Stratum and per-module permissions (A5.4 + Idea 4): the driver (ofscc.ofs, expand_attaches_body) reads each file's header as text, like attach (stratum, claim, caprock and the //! claim form), and does not pass those lines to the lexer; every file becomes a module in the ast.ofs table (ast_mod_*: stratum, declared claims, used claims, whether it is runtime, the main program's caprock), and the line map stores the module of each range (ast_mod_of_line). Phase 4A: AST Interpreter Backend (Interpretação Direta)

File: ofs/ofscc/interpreter.ofs (70KB, 2,086 lines)

The OFS interpreter backend evaluates the typed syntax tree (AST) directly in memory. Veins containing quartz use the hybrid path described below, which generates LLVM IR and caches a native library. It is the default backend used by ofs <file.ofs> and ofs run <file.ofs>.

Interpreter architecture

  1. `Value` system: a universal monolith that unifies scalar values (stone, crystal, obsidian, bool, null) and virtual heap handles for Array<T>, monolith objects and pointers.
  2. Environment and call frames: strict lexical scope based on frame markers (_current_frame_base and _globals_count), so callers' variables do not leak into callees or globals.
  3. Value semantics: forge y: T = x and y = x copy the monolith block (obj_clone()/memcpy into the block y already has, like the native store %T); vein parameters receive the monolith by reference, like the native pointer.
  4. Method dispatch: methods defined in impl Type blocks are resolved automatically, with self injected.
  5. Real pointers (F2): a pointer is an address (VAL_INT with type *T). *p/*p = v use mem_load/mem_store by the memory class of the pointee type (MC_*: width, sign, f32, obsidian, *T, monolith, variant), with the typeck static type precomputed per node in annotate_nodes (the same type llvmgen uses); the load/store is the interpreter's own native code (fracture { *p8 = v as u8 }). &x of a variable turns the entry into VAL_BOXED: the value moves to an 8-byte slot (box_var), read/written by env_load/env_store and freed in env_pop_one (_boxed_live keeps the fast path free when there is none). as mirrors llvmgen's NK_CAST (eval_cast). A monolith lives in raw memory with the llvmgen.struct_layout layout (the same function computes the native ofs_alloc size and the interpreter's offsets; compute_layouts), and VAL_OBJECT holds the block address; an Array field holds the interpreted handle as -(h+1).
  6. Built-ins: direct handling of I/O (echo), strings (ofs_str_*), arrays (ofs_array_*) and math (ofs_pow, ofs_sqrt). The list (is_builtin) is only a fast path, not a limit on what can be called.
  7. Rift (`extern vein`/`rift vein`): at load time (collect_declarations → resolve_calls → ffi_check_symbols), every called extern becomes an address via dlsym(RTLD_DEFAULT, sym) (honoring bind), after opening libm and OFS_FFI_LIBS; a missing symbol is the linker's error (undefined reference), exit code 1. Veins from stdlib/runtime/*.ofs (line ranges marked by expand_attaches through ast_mark_runtime_lines) use the native version linked into ofscc. The call (call_extern) converts arguments by the declared type (integers/pointers/obsidian as i64, crystal as double), stores them in a buffer and calls __ofs_ffi_dispatch, which llvmgen defines inside ofscc itself (emit_ffi_dispatch, when the module declares that extern): a switch with one call of exact LLVM type per signature class (ffi_sig/ffi_sig_supported: up to 4 i64|double args with an i64|double return, up to 12 integer-only, variadics with 1 to 3 fixed + up to 4 extra; 155 cases). That is why ofscc must be linked with -rdynamic (it exports the runtime and the dispatcher to dlsym). In F2, &x, monolith (the block) and Array go to the native function as addresses: the Array is the interpreter's value column, which already is a native ofs_array (arr_native_ptr), with its length synchronized on return (ffi_sync_arrays); an Array returned by the native function becomes an interpreted array that uses the same block (arr_adopt). native → OFS callbacks: the module that declares extern vein __ofs_cb_table gets from llvmgen (emit_cb_trampolines) 16 functions __ofs_cb_K(i64 x 6) that call __ofs_cb_enter(K, ...), defined at the end of interpreter.ofs; fault_addr of an interpreted vein binds the vein to a slot (cb_slot_for) and returns the address of __ofs_cb_K (found via dlsym, so an ofscc built by an older compiler still links); cb_enter pushes the arguments by each parameter's type, runs the vein and returns the result as i64, preserving the interpreter registers (re-entrant: it works inside a native call made by the interpreter). Exhausted slots, more than 6 parameters or crystal/f32 in the callback are a clear error (exit code 1).
  8. Vein values (F6): VAL_FN holds the type (_rt), the interpreted vein (_rr = id of the declaration node, or -1), the native address (_ri, of an extern or coming from C) and the name (_rs). resolve_calls marks each vein NK_IDENT in _naux (vein id+1, extern -(ei+1)); eval_ident only uses it when no variable has that name. __vein_call (CALL_VEIN) calls the interpreted vein directly (call_function_by_id) or the native address with the type's signature (call_native_sig → ffi_call_addr, the same path as call_extern). Going to C (ffi_arg_int, reg_as_int, as stone), an interpreted vein becomes the cb_slot_for trampoline; coming back from C (fn_from_raw: extern return, callback parameter), a trampoline address turns back into its original vein and an extern address gets its name. In raw memory (monolith field, *p) the MC_FN class stores the native address or -(id+1) for an interpreted vein, without spending a trampoline.

Alvos (OFSCC_TARGET)

Sem a variável, o IR sai com o triple do host (x86-64 Linux/Windows/macOS), idêntico ao de antes. OFSCC_TARGET=android emite aarch64-unknown-linux-android26 (ou passe um triple completo). O runtime magma usa só a libc, então para o Android basta gerar o IR do magma.ofs com o mesmo triple e compilar com o clang do NDK; a .so é linkada com -Wl,-init,__ofs_init_globals porque não há main(). Ver ANDROID.md.

Um extern vein que o próprio módulo define não é mais declarado de novo (antes: invalid redefinition).

Function address (fault_addr, fault_call)

fault_addr(name): typeck replaces the argument with the mangled symbol (ns.fn → ns__fn) and requires it to be a vein (SYM_FN); llvmgen resolves the bind of an extern/rift and emits ptrtoint ptr @symbol to i64. fault_call(address, args...) emits inttoptr + call i64 %p(...) with the LLVM types of the arguments. See LANGUAGE_REFERENCE.md.

Vein values (F6)

A vein(...) -> R type is ptr in LLVM (8 bytes in a monolith, like any pointer). The name of a vein used as a value (an NK_IDENT of vein type that is not a variable, is_vein_ref) becomes @symbol (with the extern's bind); a global initialized with a vein's name gets the constant @symbol. __vein_call (emit_vein_call) evaluates the vein, tests null (branching to __ofs_vein_null, which calls the runtime's ofs_array_fail: message and exit code 1) and emits call R %f(T1 a, T2 b) with the exact LLVM signature of the type; each argument goes through coerce_for_store to the parameter type. == between vein values is icmp ptr. __ofs_vein_name is a chain of icmp eq ptr %p, @symbol over the veins the module uses as values. Both helpers are only emitted when the module uses them: the IR of a program without vein values does not change.

geode (closures)

The parser reads geode (params) -> R { body } (a contextual word: geode followed by ( whose list closes before -> or {) as NK_LAMBDA (c0 params, c1 return, c2 body). The typeck checks the body in the creator's scope, with a stack of open geodes (_gd_base: the depth of each one's parameters); an identifier that is local to the vein (depth ≥ _fn_base) below the base of an open geode becomes a capture of that geode (and of the outer ones, transitively). Assigning to a capture, &capture and shatter/erode without a loop in the body are [ERRO DE GEODE]. Then the body is lifted into an NK_FN_DECL __geode_<vein>_<k> appended at the end of the program, with the captures as the first parameters (types rebuilt from the canonical text, make_type_node); the NK_LAMBDA keeps val = that name, extra = the captures (NK_IDENT) and c0..c3 = -1, type vein(params)->R. So the rest of the compiler (A6, contracts, crystallization, Refract) sees an ordinary vein.

Native: without captures, @__geode_... (goes to C like any vein). With captures, emit_geode allocates on the heap (arena off) [@name.env, MAGIC, capture 0..n] (8 bytes per capture, stored with its LLVM type) and the value is that address | 1. The adapter @name.env(ptr %env, params) (end of the module, emit_sediment_helpers) loads the captures and calls the body vein. If the module has a capturing geode (scan_geodes), emit_vein_call tests bit 0 and the mark and calls adapter(env, args) (or the vein directly, with a phi on the result), __ofs_vein_name returns <geode> for a tagged pointer, and vein values passed to functions outside the module or turned into addresses go through __ofs_geode_c_check (tagged = ofs_array_fail, exit code 1). Without a capturing geode none of this is emitted. In A6 each capture escapes (esc_walk(capture, 1)); the analysis is no longer switched off.

Interpreter: eval_geode builds a VAL_FN with _rr = id of the body vein (_naux resolved in resolve_calls_from) and, with captures, _ri = handle + 1 of an interpreted array with the copied captures. call_vein_value calls call_geode (captures, then the arguments on the stack). In raw memory the value is -(id + 1 + env·2^24). fn_native_addr of a capturing geode is the runtime error. Crystallization (cr_supported) keeps interpreted, when the program has geodes, a vein that handles vein values or reaches (rf_walk_calls) one that does; and a vein with an arena only crystallizes if the arena runtime is in the process. In Refract, a __geode_* vein with a new signature (captures changed) is neither refused nor redirected: geodes already created keep the old body.

Phase 4C: inline assembly and hybrid execution

TOK_QUARTZ → NK_QUARTZ represents a statement with instruction strings, inputs (NK_QUARTZ_IN), an optional destination and options (NK_QUARTZ_OPT: constraints, clobbers and dialect). parser.parse_quartz parses the syntax; typeck.check_quartz validates scalar destinations, operands and constraints, and require_fault requires abyss. llvmgen.emit_quartz emits call ... asm sideeffect, optional inteldialect and an output store. Memory inputs use ptr elementtype(T) with *m; +r outputs receive a tied input in the same register.

In the interpreter, hy_prepare finds veins containing quartz and requests their closure from llvmgen.hy_generate. The module contains used functions and globals and declares runtime symbols exported by the ofscc process (-rdynamic). The IR and compilation command determine the cache key. clang -shared -fPIC builds the library; dlopen/dlsym resolve roots and globals. Typed calls use ffi_call_addr/__ofs_ffi_dispatch; hy_sync_in/hy_sync_out synchronize globals, including around reentrant callbacks. Heap and runtime belong to the same process. Assembly lowering and native dependency closure can be reused by crystallization; live editing (Fault Refract, Phase 4D) uses both.

cr_tick counts calls and, at OFS_CRYSTALLIZE_THRESHOLD (default 1000), requests the same module for all eligible roots. IR generation is synchronous; clang -O2 compilation runs in the background, and later calls check a completion marker before installing native dispatch. OFS_CRYSTALLIZE=0 disables optional promotion; missing compilers or optional failures preserve interpretation. Long loops inside one call use OSR (below); replacement triggered by file edits is Fault Refract (Phase 4D).

Shared globals (wave 4). Hybrid modules do not define globals: each global in the closure becomes @__ofsg.<name> = global ptr null and every access goes through it (var_ptr emits load ptr, ptr @__ofsg.name). After dlopen, hy_load stores the address of the global's single cell (hy_global_cell, 8 bytes) there: the interpreter keeps the global itself in that cell (VAL_BOXED, the same mechanism as &x), so the interpreter and every .so (crystallization, OSR, Refract recrystallizations) read and write the same memory, with no copy at the boundary. Only Array globals (the interpreter has its own handle), vein(...) globals and not-yet-initialized globals keep a copy (_hy_gmode = 1, synchronized by hy_sync_in/out). Measured (gsync.ofs, 24 globals, 400k interpreted→native calls, OFS_OSR=0): 0.43 s → 0.18 s (pure interpretation takes 0.29 s: crystallization used to lose to it in this case).

OSR (wave 4). exec_while counts iterations of each loop execution; every 1024, osr_tick (unless OFS_OSR=0): an eligible loop (osr_prepare: while only; body without return/throw/anchor/?/&/geode/vein value/bedrock; reached veins without geodes and with the arena runtime when they use bedrock; the path to it through block/while/if/cycle) that adds up OFS_CRYSTALLIZE_THRESHOLD iterations is requested from llvmgen (hy_osr_add). Live variables are the declarations visible at the header (parameters and forge of the blocks on the path, osr_scope_decls) whose name appears in the loop (osr_live). hy_emit_osr generates __ofs_osr_<node>(ptr %st) -> i64 in its own module (the closure of the body; globals are the shared cells): it loads each variable from st[1..n] (8 bytes each; monolith is the pointer to the interpreter's block, Array the native ofs_array, text with owner 0), enters through the header (tests the condition), runs the loop like a normal while and writes the variables back to st, returning 0. osr_enter does the transfer (mem_store/mem_load by class; Array through arr_native_ptr/arr_sync, like globals) and the interpreter continues after the loop. Compilation runs in the background, one job at a time (_cr_josr, _hy_load_loops); cached by IR hash. A variable whose address was taken (&x) or outside the frame keeps the loop interpreted. bench/ofs/loop.ofs: 18.6 s → 0.34 s (native 0.41 s).

Floating-point callbacks and `f32` in the FFI (wave 4). Besides __ofs_cb_K(i64 x6), the module that declares __ofs_cb_table (the ofscc) gets __ofs_cbx_K(i64 x6, double x8) -> { i64, double } and __ofs_cbx_table: SysV x86-64 and AArch64 number integer and float argument registers separately, so the trampoline receives all of them; the { i64, double } return goes out in rax/x0 and xmm0/d0 and serves integer, crystal or f32 callbacks (bits in the low half). __ofs_cbx_enter (interpreter) receives the doubles as bits and assigns them to parameters in per-class order. On Windows x64 (positional registers) cbx is not generated and a float callback keeps the clear error. f32 in Rift/FFI and in hybrid roots travels as a double whose low 32 bits are the f32 (C reads only those); an f32 result comes from the low 32 bits of xmm0.

Assembly text remains target specific. LLVM does not translate instructions between x86-64 and AArch64. The hybrid interface keeps the FFI arity limits (up to 12 integers, up to 4 with crystal/f32; callbacks up to 6 integers and 8 floats). See LANGUAGE_REFERENCE.md and COMPILED_LANGUAGE.md for syntax and the parity rule.

Phase 4D: Fault Refract (live editing, L0/L1/L2/L3)

Files: ofs/ofscc/interpreter.ofs (Fault Refract section), ofs/ofscc/ofscc.ofs (refract_reload, refract_paths), typeck.reset, ast_srcmap_reset. Command: ofs refract (wrapper) = OFS_REFRACT=1 in run mode.

Dispatch cell. Every vein call goes through call_function_by_id(fid). With refract enabled, _rf_cell[fid] (one entry per AST node) maps the id to the live version: the old version of a swapped vein points to the new one, and identical copies in the new version point to the live one (so native state and crystallization heat stay on the version already running). rf_redirect keeps chains short (A→B then B→C becomes A→C). A per-vein counter (_rf_active) tells who is on the stack; a running call finishes on the old version, because the body being executed belongs to the old node (no OSR).

Watching. rf_tick runs at the start of every call; every OFS_REFRACT_PERIOD ms (clock via dlsym("clock_gettime"), time as a fallback) it flushes stdout (live output through pipes/files), checks pending native work and computes an FNV hash of the watched files' contents (refract_paths: the main file and attaches outside the stdlib and the runtime). Content that differs and stays stable for one period triggers rf_refract. A missing file (atomic save in progress) counts as no change.

In-process recompilation. refract_reload repeats the startup path (attach expansion, lexer, parser, typeck.reset + typeck.check) with stdout redirected to stderr (dup/dup2); new nodes go into the same pool. build_node_tables_from, annotate_nodes_from and resolve_calls_from process only the new nodes; the per-node crystallization tables (_cr_heat, _cr_eligible, _cr_quartz) grow with them. On an error the tables still grow (ids are global), but no cell changes.

Diff. rf_scan lists veins (key = name with namespace/monolith, as in collect_declarations), globals, monoliths and externs. Each vein gets a structural hash of its typed tree (rf_hash: kind, text and type_str of every node, no line numbers); equal hash = equal vein. Signature (rf_sig), monolith shape (fields and types), global type and extern shape feed the rules.

Safety (any rule refuses the whole swap and nothing changes): new signature of a vein called by an active vein (rf_active_user, from already resolved calls: CALL_FN, vein values and CALL_DYN methods by suffix), handed to C (_cb_fn) or used as a value; removed vein called by an active vein; monolith layout change with instances (obj_new counts per monolith); global with a new type; new extern without a symbol or changed extern; variant list that does not start with the old one (numeric tags must stay the same). Calls from unchanged veins were checked by the typeck against the new signature, because the whole program is checked.

Swap (L0). New veins are registered by name (as at startup); changed ones are not: the name still resolves to the old id and the cell leads to the new version. New globals take one of RF_GLOBAL_SLOTS (64) slots reserved at the end of the globals area ([0, _globals_count), where find_var looks), running the initializer without seeing the caller's locals; existing globals are not re-run. A new monolith (or one with a new layout and no instances) gets a new field range and compute_layouts. Registers and _cur_call_id are preserved around the swap.

L1 (native). Loaded .so files share the global cells (Phase 4C, wave 4). On a swap, the affected native roots are the changed ones and those that reach (rf_reaches, transitively) a changed vein, because calls inside a .so are direct. They get address 0 (they run interpreted, in the new version) and go to _rf_dirty; rf_launch generates the closure from the new root (llvmgen.hy_generate) and compiles it in the background. When the .so is ready, hy_set_root replaces the root entry (rf_live_fid). One job at a time; a job that finishes after another swap (generation _cr_jgen different from _rf_gen) is discarded and redone with the current program. Veins with quartz are compiled before the swap in soft mode (_hy_soft: a clang/dlopen failure refuses the swap instead of ending the program). The old .so stays loaded. Unloading it (dlclose) would require proving that nothing points into it anymore: having no frame inside it is not enough, because text literals and vein addresses of the .so may have gone into globals, arrays and objects; this is pending (copy literals to the heap or count references).

OSR in Refract (wave 4). At every while header, if _rf_gen changed since the loop started, rf_osr_target looks in the live version of the running vein (_cur_fn_id → rf_live_fid) for the loop at the same position among the while loops (pre-order) and compares the variables before it (osr_scope_decls, block/while/if only): same name and type keeps the live value, a new one gets its initial value (execute_stmt of the declaration at switch time), a removed one goes out of sight (_env_sym = -2), a different type or a new parameter refuses. rf_osr_switch runs the new loop and then the rest of the new version along the path (rf_exec_after in blocks, re-entry in the while loops above, nothing in if) and returns EXEC_RETURN so the old frame only unwinds; the active-frame count (rf_frame) moves to the new version. A loop without calls also sees the edit (rf_tick every 1024 iterations). A native (OSR) loop under Refract gets the __ofs_osr_poll hook in st[0] and asks every 65536 iterations; when the file changed (rf_osr_poll, at the OFS_REFRACT_PERIOD pace) it returns 1 through the header, the interpreter continues interpreted (_osr_hold until the edit is handled), switches version and requests OSR again with the new program (rf_apply clears _osr_addr: native loops call the old veins directly).

Compatible signature (wave 4). rf_sig_compat: old parameters equal (rf_tstr, with the grain) and first, new ones at the end with a default value; return equal, formerly void, a narrow integer where it was stone/i64, f32 where it was crystal. Compatible with an active user = accepted (callbacks and vein values still refuse). The parameter default (b: stone = 3, a literal) belongs to typeck: note_defaults validates it (literal, trailing only) and fill_defaults completes calls with copies of the literal; an old call of a vein that gained a parameter gets the default in bind_params (interpreted) or in rf_pad_defaults (pushed before a native root).

Monolith migration (wave 4). Under Refract every monolith block is registered (rf_obj_alloc: obj_new, obj_clone and, in the native code of hybrid modules, __ofs_obj_alloc instead of ofs_alloc, except inside a native bedrock, whose block dies at its end) and gets RF_OBJ_SLACK (64) spare bytes. A new layout with live instances: rf_migrate_check refuses a field that changes to a non-convertible type (numeric↔numeric converts) or a size beyond the slack; otherwise rf_migrate rewrites each instance in place (copy of the old block, zero, field by field by name: same type copies the bytes, numeric converts via mem_load/mem_store, a new field gets the type default as in obj_new), so pointers to it stay valid. Old fields leave the table (empty owner), which invalidates the field cache (_naux) of nodes that already ran. Instances created by C or with raw ofs_alloc are not known.

Limits: an interpreted vein that gets hot after being edited only crystallizes if it was already eligible at startup; up to 64 new globals per run; OSR only for while (not cycle) and not for loops with return/throw/? in the body; Refract OSR does not follow a loop inside cycle/match/bedrock; the old .so is not unloaded.

L3 (remote/Android), done. Files: ofs/ofscc/ofscc.ofs (Fault Refract L3 section: r3_scan, r3_hash, r3_build_manifest, r3_patch_plan), ofs/ofscc/llvmgen.ofs (rf3_set, rf3_emit_cells, rf3_patch_generate, the call through the cell in emit_expr and the external globals in emit_header), ofs/stdlib/geophone.ofs (agent), wrapper (android_build with --refract, refract_remote_run). The app runs AOT native, not interpreted. Build with cells (OFSCC_REFRACT=cells): the driver appends attach {geophone} to the source, lists the user veins (those in the refract_paths files; main and __*, such as geodes, get no cell) and llvmgen emits @__ofs_cell.<vein> = global ptr @<vein> and, for every NK_CALL whose target has a cell, a load ptr plus an indirect call (variadic calls and vein values stay direct). The manifest (@__ofs_refract_manifest, text with one record per line: V symbol/hash/signature/cell, G global/type, M monolith/fields, X extern/shape, S variants) uses a structural hash of the typed tree like rf_hash (kind, text and type_str, no lines), computed after typeck and sediment. The agent starts through @llvm.global_ctors (after __ofs_init_globals, which the build links with -Wl,-init), on the thread that loads the lib (the main one), and adds the abstract socket ofs-refract.<package> to that thread's looper (ALooper_addFd): no new thread, because the runtime is not thread-safe, and a patch is applied between two events. SO_PEERCRED only accepts uids 2000 (adb/shell), 0 and the app's own. Patch (OFSCC_REFRACT=patch, OFSCC_REFRACT_BASE = the manifest the app sent on connect, already merged with earlier patches' records): r3_patch_plan diffs vein by vein and applies the rules (new signature for a vein with a cell, new global or new global type, layout of an existing monolith, changed extern, reordered variants: rc 4 with the message; nothing changed: rc 3). It includes the changed veins, the ones without a cell in the app (new veins from earlier patches, geodes: redefined in every patch, since calls to them are direct) and the cell veins that use one without a cell. rf3_patch_generate emits only those veins; globals become external (the app's unique address: state carries on, like wave 4's global cells), variants stay internal to the patch (appending works), the other veins they use become declare (the hy_walk closure, non-transitive) and @__ofs_refract_install stores the new address of each vein with a cell. On the PC the NDK clang links the patch with -shared -fPIC -Wl,-Bsymbolic -Wl,--no-undefined against the build's lib<name>.so (which got a -soname): dlopen in the app resolves the declares and globals there through DT_NEEDED, and a symbol the app lacks becomes a link error on the PC. The app writes the .so to code_cache/ofs-refract/, dlopens it, calls the installer, merges the patch's manifest and replies OK/ERR; then it calls oal__refresh (if present) or requests a frame. Measured on a moto g(8) power (Android 11): a 6 KB patch applied in 1 to 3 ms, same PID, counter preserved (ofs/tests/refract/android.sh). Limits: no native OSR (a running vein finishes in the old version); a stored vein value points at the build's version (the PC warns); new signatures, new globals and new layouts need a reinstall; every patch's .so stays loaded; aarch64 only.

Phase 4E: magma.cast (Idea 5): compiling and loading OFS at runtime

Files: ofs/stdlib/magma.ofs (the API, pure OFS, the same in both modes), ofs/ofscc/ofscc.ofs (OFSCC_MODE=cast, magma_manifest, OFS_MAGMA_CAPROCK), llvmgen.set_magma_manifest, typeck (claim magma, magma_vent_seat), ast.ofs (CLAIM_MAGMA, mod ceiling), wrapper (--export-dynamic).

Decision: the compiler runs in a separate process, in both modes. Under ofs run the compiler is in the process, but recompiling another program into the same node pool and typeck (the refract_reload path) would replace state the host program's interpreter and crystallization still use, and compiler errors call exit in several places: a broken mod would take the program down. A separate process isolates both and is the same path natively, where the binary has no compiler inside (the alternative, linking ofscc as a library, would put the compiler in every binary). Under ofs run the process is the running ofscc itself (/proc/<pid>/exe, detected through the interpreter__run symbol exported with -rdynamic); natively, OFS_MAGMA_OFSCC or the installed ofscc, searched like the wrapper does.

Pipeline. magma.cast writes an sh script into a mkdtemp directory (ulimit -v 3000000, timeout 120): ofscc with OFSCC_MODE=cast, OFS_STRICT_FAULT=1 and the ceiling (OFS_MAGMA_CAPROCK) → IR; key = sha256 of IR + clang + flags + uname; with no cached .so, clang -shared -fPIC -O2 -Wno-override-module -Wl,-Bsymbolic -lm (plus -mllvm -opaque-pointers on clang 14) and atomic publication (cp + mv). The .so is opened with dlopen(RTLD_NOW) (local); __magma_manifest (text name\tsymbol\tsignature per vein of the mod file) is read with dlsym, and __ofs_init_globals runs once per .so (the same source reuses the module). Any failure becomes magma.crack(m) (compiler log without progress lines).

`cast` mode in the driver. It is ir plus: the OFS_MAGMA_CAPROCK ceiling applied as a caprock (intersected with the mod's own) that also covers module 0 (ast_mod_set_cast_ceiling, check_modules starts at 0); [ERRO DE MAGMA] if the mod has core main; the manifest (magma_manifest: top-level and namespace veins on module 0 lines, no __*, signature from typeck.param_types_of + vein_type_make, the canonical F6 text) emitted by llvmgen at the end of generate as @__magma_manifest.

Typed `magma.vent`. coerce_value (typed forge, =, argument, return) recognizes magma__vent (with m, the name and "") (the 3rd parameter defaults to "", filled by fill_defaults) stored into a vein(...) place: it replaces the literal with the canonical type text and wraps the call in an NK_CAST to that type, created by typeck itself (it does not go through the abyss rule, like implicit conversions). At runtime the stdlib only returns the address when the manifest signature matches; otherwise 0, which becomes null. Native: inttoptr and a call with the exact signature; interpreter: fn_from_raw → a Rift call (call_native_sig), and an interpreted vein handed to the mod becomes a __ofs_cb_K trampoline.

Shared runtime. The .so carries no runtime: ofs_*/echo_* come from the process (same heap, stdout, strings, arena). ofscc is already -rdynamic; the wrapper links with --export-dynamic/-rdynamic when the IR defines @magma__cast; without the symbols (dlsym(RTLD_DEFAULT, "ofs_str_concat") == 0) magma.cast returns the error with a hint. -Wl,-Bsymbolic keeps the mod's veins and globals bound inside it even when the program exports same-named symbols.

Security. CLAIM_MAGMA (bit 8; CLAIM_ALL = 15): require_claim on calls to magma__cast and on its definition (the magma module declares claim rift, abyss, magma), always an error (no migration window); crust = [ERRO DE ESTRATO]; a caprock without magma forbids attaching the module.

Limits: no dlclose (the .so stays loaded after magma.release: literals and addresses may be stored, as in wave 4); Linux/macOS only; monolith crosses the boundary by name (layout not checked); the mod does not see the program's globals.

Phase 4F: ofs fossil (Idea 2): record, replay and travel back in time

Files: ofs/ofscc/fossil.ofs (the .fossil format, reading/writing, per-symbol policy table fz_spec, source hash), interpreter.ofs (section "ofs fossil": fs_*; hooks in execute_stmt, call_extern, ffi_call_addr, call_builtin (echo/exit), fault_runtime_error, hy_prepare, run), ast.ofs (ast_src_file, ast_src_line, ast_exp_line), ofscc.ofs (OFS_FOSSIL, source from the header, fs_enable/fs_finish), wrapper (ofs fossil, --to, --back, --dig, --layer), VS Code extension (ofs.fossilReplay/Next/Back).

Where to record. What already existed decided the design: every native call of the interpreter goes through call_extern → ffi_call_addr → ffi_invoke (F1), including the runtime's native veins (ofs_read_line, pulse__now_ms, registered as extern by ffi_runtime_native). call_extern looks up the symbol's policy (fs_spec_of, cached per extern; 0 = normal call, costing only a test of _fs_mode) and leaves it in _fs_pol; ffi_call_addr consumes it and, with the arguments already in the FFI slots, calls fs_invoke instead of ffi_invoke. There the integer/pointer arguments are copied before the call (a callback may reuse the buffer). Recording: calls C and writes the event (raw return, float bits from the return slot, returned text, the localtime block, bytes C wrote into the effect argument and the FNV-1a hash of output data). Replaying: reads the next event, checks the symbol (otherwise diverges with rc 3), builds the return (text becomes a fresh copy, "the argument itself" becomes the current argument), copies the bytes into the argument's current pointer, checks the output hash and only really calls C for console output when not silenced. The rest (ffi_set_result, ffi_sync_arrays) is the same path as before, so the registers end up as during recording.

Policy (fz_spec, one integer per symbol: policy, return kind, effect argument and size, console rule, hash argument and data): world (input, clock, randomness, environment, files, network), output (console really runs, file/network is a checked no-op), process exit (exit: closes the fossil first) and live (everything else, deterministic). OFS_FOSSIL_WORLD adds symbols.

Determinism of the rest. The interpreter is deterministic given what comes from outside: addresses change (C pointers, buffers), but the program only hands them back to C. That is why crystallization and OSR are off (hy_prepare: _cr_enabled = false when _fs_mode != 0): native code would bypass the hook and not count steps. quartz stays native, with a warning.

Steps. execute_stmt calls fs_step(id) when _fs_on (recording and replaying): counts the statement and, on replay, compares with the target (step, expanded line via _fs_nline, precomputed only when there is a line target, or the first statement of the vein body). Without fossil the cost is one global test per statement (measured: interpreted fib(35) 6.21 s after × 6.42 s before, within noise).

Going back: layers via `fork`. Restoring the interpreter state by copying (_env_*, _arr_* tables, raw memory of monoliths, ofs_alloc, C memory) would be large and fragile; fork copies everything on demand and is the same idea as rr's checkpoints. Every _fs_every steps (--layer, default 2000; at most 32 layers, then every other one is dropped and the interval doubles), fs_layer_make does fflush and fork: the child becomes a layer and sleeps reading its own pipe; the parent goes on. Going back to step t: kills the layers after the chosen one, sends go t to the closest layer ≤ t and exits; the layer forks again (it keeps holding the point) and the child runs silenced up to t. Since replay is deterministic, all layers are on the same timeline and stay valid. Commands are read byte by byte with read (the stdio buffer would be duplicated by fork).

Supervisor. With navigation, the process the shell waits for forks right at the start and stays out of the run: it receives through a pipe A <pid> (new active timeline), H <pid> (the active one handed over), L/K <pid> (layer created/ended) and X <code> (end). On Linux it is a *subreaper* (prctl(PR_SET_CHILD_SUBREAPER)): it reaps orphans and, if the active process dies without X/H, kills the layers and exits with 128 + signal. POSIX functions via dlsym + fault_call (the Windows ofscc links without them; there only forward --to).

State shown. fs_where (step, file:line through the line map, vein, line text) and fs_show_vars (locals of the current frame _current_frame_base.., globals whose NK_VAR_DECL is in a program file, collected by fs_collect_user_globals; arrays and monoliths through interp_array_get/obj_load_field; opaque FILE* as <ponteiro do C>).

Limits: scanf and structures outside the table; UI (X11/Android events); calls through a vein value coming from C (call_native_sig) really run; the language has no argv yet. Next step: a DAP adapter with step-back on top of --dig.

Deterministic:

Active Architecture: Direct LLVM Backend

The OFS compiler emits LLVM IR directly without intermediate C code: 

llvmgen.ofs → output.ll (LLVM IR) → llc -filetype=obj → output.o → ld (with magma.o) → executable

Benefits:

  • Direct LLVM IR emission without intermediate C code; the driver can use llc and the native linker. The hybrid path compiles its library with clang.
  • Byte-for-byte reproducibility and deterministic IR emission
  • Compilation time depends on the program, optimization level and selected native toolchain

OFS Self-Hosting Bootstrap Guide

The OFS compiler is fully self-hosted and deterministic. The bootstrap process compiles the compiler using itself, without depending on external C++ compilers or legacy runtimes.

Quick Start

To bootstrap the native compiler in the repository: 

bash ofs/bootstrap/scripts/bootstrap-minimal.sh

Once built, the compiler binary will reside in ofs/dist/ofs (or ofs/dist/ofscc).

Compile a program: 

ofs/dist/ofs build ofs/examples/hello.ofs -o hello
./hello

What is Self-Hosting / Bootstrap?

Bootstrapping occurs when a programming language's compiler compiles its own source code. This milestone formally proves that the language's grammar, type system, and standard library are expressive and robust enough for systems-level development.

  • Lisp (1962): First self-hosting programming language.
  • C (1972): Bootstrapped and established as the systems standard.
  • Rust (2011): Compiler written in Rust.
  • Go (2015): Compiler migrated completely to Go.
  • OFS (2024–2026): Compiler and native runtime self-hosted.

Process Overview

Phase 1: Seed Compiler

The repository provides a pre-compiled native compiler binary in ofs/dist/ (ofs / ofscc) to initiate the build cycle.

Phase 2: Recompilation

The script compiles all compiler source modules (ofs/ofscc/*.ofs) using the existing binary, emitting a fresh compiler executable.

Phase 3: Determinism Verification

The newly generated compiler compiles the compiler source once more. The binary output from pass 2 is compared byte-for-byte with pass 3 (v2 === v3). Identical checksums confirm deterministic build reproducibility.

OFS Performance Analysis

OFS performance work is split between compiler throughput and generated-program runtime.

The main hotspots currently identified are:

  1. substring allocation while materializing tokens;
  2. repeated string concatenation in import expansion and escaping;
  3. linear lookup tables for symbols, fields, variables, and interned strings;
  4. length calls repeated inside loops whose collections do not change.

The public ofs_str_char_at function still validates bounds. The lexer now uses an internal known-length byte read only after checking _pos against _len. In seven-process measurements on June 14, 2026, median IR generation for the small workload moved from 8.11 ms to 7.54 ms. Compiling ofscc.ofs moved from 4,610.40 ms to 3,694.08 ms. Bootstrap stages two and three emitted identical IR.

The planned order is:

  1. repair and expand lexer self-host tests;
  2. add detailed lexer, parser, type-checker, and LLVM IR timing;
  3. benchmark 10 KB, 100 KB, and 1 MB sources;
  4. introduce token slices or a compilation arena;
  5. add a native string builder (strbuf already exists in the stdlib);
  6. measure indexed symbol tables;
  7. evaluate LTO and LLVM flags.

Link and runtime optimization

The distributed runtime is built with -ffunction-sections and -fdata-sections. The launcher enables --gc-sections on ELF, dead_strip on Mach-O, and OPT:REF on PE/COFF so unused runtime functions do not remain in every application.

On the workload published on June 14, 2026, this reduced the OFS executable from 28,224 to 16,056 bytes without changing its checksum. The launcher caches CRT paths and native toolchain binaries (llc and ld) instead of slow filesystem probing on every compilation. Median build time for the same workload moved from 320.81 ms to 208.78 ms on the recorded machine.

These are distribution-pipeline improvements. They do not change syntax, type checking, or program semantics.

Goal

The goal is to reduce concrete compile-time and run-time costs of the compiler and runtime without changing language semantics, compromising memory integrity, or introducing silent regressions. Total build time should stay competitive with equivalent native toolchains by removing redundant work, not by removing language features.

Compilation Flow

OFS source
  -> module resolution and expansion (attach)
  -> lexer
  -> parser
  -> type checker
  -> LLVM IR generation (llvmgen.ofs)
  -> static LLVM compiler (llc -filetype=obj)
  -> native link with the native runtime (ld / ld.lld)
  -> native executable (ELF / Mach-O / PE)

Each stage is measured in isolation: optimizing the generated binary does not necessarily reduce lexer time, and lexer improvements do not change the CPU use of the resulting program.

Hotspots and Optimization Opportunities

1. Character reads in the lexer

ofs_str_char_at checks bounds against the string length. The lexer already tracks _pos against _len, so the ofs_str_char_at_known variant avoids a redundant strlen per character and keeps processing of large sources linear, O(N).

2. Substring allocation

The lexer slices text for identifiers, numbers and literals. The optimized strategy is:

  • keep (start, length) tuples that point into the original file buffer during parsing;
  • materialize heap strings only when a syntax node or the symbol table needs them to persist;
  • use a per-compilation-unit arena allocator, released in one step at the end.

3. String concatenation

Sequential concatenation in loops copies prefixes repeatedly. In the LLVM generator, cg_emit writes straight to the output file and avoids temporary buffers.

4. Symbol tables and scope lookup

Linear symbol lists have good cache locality for small and medium programs. For large code bases, hash tables or scope-indexed structures reduce the lookup cost for variables and types.

Measurement Methodology

  1. A controlled set of lexical and syntactic tests with sources from 10 KB to 1 MB.
  2. Per-phase timing: front end (lexer, parser, types), LLVM IR emission, native link.
  3. Real system metrics via wait4: user CPU time, system time and peak resident memory (RSS).
  4. Strict output checksum verification so no optimization changes semantics.

Limits

  • Text: system text field via oal.edit_open (keyboard + field as an alternative); no CJK fonts (the system Roboto has no Japanese).

OFS Web Stack Architecture

The OFS web stack is structured across three distinct layers:

LayerExtensionPurpose
ODL.odlSemantic document structure and textual content
OES.oesDesign tokens, responsive layout rules, and keyframe animations
OFS.ofsNative processing logic, static page generation, and HTTP serving

ODL and OES are standalone languages compiled by the OFS toolchain, rather than mere aliases for handwritten HTML and CSS. However, standard HTML5 and CSS remain the browser distribution targets.

1. Static Site Generation

The toolchain compiles ODL and OES source files directly into production-ready browser assets: 

ODLC_INPUT=page.odl ODLC_OUTPUT=public/index.html ofs run ofs/tools/odlc.ofs
OESC_INPUT=theme.oes OESC_OUTPUT=public/theme.css ofs run ofs/tools/oesc.ofs

The output can be deployed to standard static hosting providers, such as GitHub Pages, Cloudflare Pages, or traditional web servers (Nginx/Apache).

2. Integrated Native Web Server (webserver)

The standard library provides an HTTP server written in OFS and executed as a standalone binary: 

attach {webserver}

core main() {
    forge body = "<h1>OFS Native Server</h1><p>Running without external runtime dependencies.</p>"
    webserver.serve_html_forever(8080, body)
}

The compiled binary manages network sockets and serves the pre-rendered artifacts on demand.

3. Web Ecosystem Interoperability

The ODL compiler provides explicit directives to interoperate with existing web technologies:

  • mark / markdown: Compiles embedded Markdown into semantic HTML.
  • raw / html: Injects raw HTML fragments without automatic escaping.
  • wire / script: Injects classic JavaScript scripts (<script src="...">).
  • spark / module / node: Injects modern ES modules (<script type="module" src="...">).
  • pulse / js: Embeds inline JavaScript code (<script>...</script>).
  • server / php: Emits server-side processing blocks (<?php ... ?>).
  • raw / css in OES: Injects direct CSS rules for gradual migrations.

4. VS Code Extension and Live Reload (*Go Live*)

The official VS Code extension enables *Go Live* development mode when opening .odl documents or .ofs programs that import webui or webserver.

When *Go Live* is started:

  1. The .odl document is compiled to HTML.
  2. Sibling .oes style files in the directory are compiled to CSS.
  3. A local development HTTP server is initiated.
  4. The server watches .odl, .oes, scripts, and graphical assets, automatically triggering compilation and browser reload via Server-Sent Events (SSE).

5. Browser Compatibility

Web browsers do not execute .odl and .oes files natively. OFS adopts the industry-standard workflow established by TypeScript, JSX, and Sass:

  1. Project source code is authored in .odl and .oes.
  2. Build tools compile the source files into standard HTML5, CSS, and JS.
  3. Hosting providers and browsers receive the compiled artifacts.
  4. For debugging and inspection, the native server exposes text/odl and text/oes MIME types.

6. Current Technical Scope

  • ODL and OES compile whitespace-delimited source code into static markup and stylesheets.
  • Reverse HTML/CSS import tools encapsulate complex legacy blocks into raw directives (raw).
  • Native HTTP routing logic remains separate from document layout definitions.
  • Components are designed for compile-time or bootstrap-time static evaluation.

Live editing on the device (Fault Refract L3)

With the phone on USB (USB debugging on), the app runs on the device and every edit saved on the PC goes into it without reinstalling or restarting the process: edited veins are swapped on their next call and globals keep the values they already had. 

ofs refract --remote app.oal                   # build --refract, install, open, connect and watch
ofs refract --remote app.oal --serial 0064380838
ofs build --target android app.oal --refract --install   # just the APK with cells and agent

Example: ofs/examples/refract_android/ (a per-second counter; edit painel.texto() in painel.ofs and save). PC output: 

refract: conectado a org.ofs.refract.demo (pid 16109, geracao 0, porta 7341 -> localabstract:ofs-refract.org.ofs.refract.demo)
refract: alteradas: painel.texto
refract: geracao 1 aplicada no app em 1 ms: painel__texto (6272 bytes, pid 16109)

How it works.

  1. `--refract` build. User veins (the main file and local attaches; the stdlib is left out) get an exported dispatch cell (@__ofs_cell.<vein>, a pointer) and every direct call to them loads the cell. The .so carries the manifest (@__ofs_refract_manifest: typed-tree hash and signature of each vein, global types, monolith layouts, externs, variants) and the geophone agent (stdlib geophone.ofs, attached by ofscc). The lib gets -soname lib<name>.so so the patch can link against it. Without `--refract` none of this exists: the IR is identical to before.
  2. Agent (`geophone`). Starts as a library constructor on the main thread and listens on the abstract Unix socket ofs-refract.<package>. The socket is added to the main thread's looper (ALooper_addFd), so a patch is applied between two events and the runtime (not thread-safe) never sees another thread. Log: adb logcat -s ofs-refract.
  3. PC (`ofs refract --remote`). Builds with --refract, installs and opens, adb forward tcp:7341 localabstract:ofs-refract.<package>, connects, asks for the manifest and watches the .oal and the user's .ofs files. On save: oalc (for .oal), ofscc in patch mode (OFSCC_REFRACT=patch: vein-by-vein diff against the app's manifest plus the rules below), NDK clang (--target=aarch64-linux-android26 -shared -fPIC -Wl,-Bsymbolic -Wl,--no-undefined, linked against the app's lib<name>.so), sends the .so and prints the app's reply.
  4. In the app. The .so goes to code_cache/ofs-refract/, is opened with dlopen, and __ofs_refract_install stores the new veins' addresses in the cells. The patch's globals are the app's (external, same address): state carries on. Then the agent calls oal.refresh() (OAL apps) or requests a frame.

What goes in and what is refused. Changed vein with the same signature: swapped. New vein: goes into the patch (no cell in the app); it and its callers are re-sent in every following patch. Removed vein: stays in the app, unused. New monolith, new extern and variants appended at the end: accepted. Refused (the app keeps the previous version; the message gives the reason and asks for a reinstall): new signature for a vein with a cell, new global or global with a new type, changed layout of an existing monolith (the native app does not migrate instances), extern with a new signature, removed or reordered variants. Compile error: nothing is sent. A patch using a symbol the app lacks (a new stdlib attach) fails to link on the PC, naming the symbol. Changes to the .oal header (app/version/permission) ask for a reinstall.

Limits. A running vein finishes in the old version (no native OSR). A stored vein value (callback handed to C, fault_addr) points at the build's version: the PC warns. Each patch's .so stays loaded until the process ends. aarch64/API 26+ only.

Security. The agent only exists in --refract builds (never in a normal or release build). The socket is abstract and local: from outside the device only adb reaches it, and the agent only accepts the adb uid (shell, 2000), root or the app itself (SO_PEERCRED); others are refused and logged. Anyone with adb access can inject code into the app: it is the same trust boundary as adb/run-as; do not ship a --refract APK.

Protocol v1 (text lines ending in \n): on connect the app sends OFS-REFRACT 1 <package> <pid> <generation>; MANIFEST → the manifest lines and END; PATCH <generation> <n> followed by n bytes of the .so → OK <generation> <ms> <veins> or ERR <generation> <reason>; PING → PONG; BYE closes. Manifest: one record per line, tab-separated fields (V <symbol> <hash> <signature> <1|0 cell>, G <global> <type>, M <monolith> <fields>, X <extern> <shape>, S - <variants>); the app merges each patch's records (key = first two fields), so the PC always diffs against what is running.

Variables: OFS_REFRACT_PORT (PC port, 7341), OFS_REFRACT_PERIOD (ms between checks, 300), OFS_REFRACT_ONCE=1 (exit after the first applied or refused patch). Device test: ofs/tests/refract/android.sh (skips without a device).

Runtime model (stdlib android.ofs)

  • Entry: android.ofs exports vein ANativeActivity_onCreate(...), which NativeActivity finds through dlsym. It fills activity->callbacks with the addresses of OFS veins using fault_addr (see LANGUAGE_REFERENCE.md).
  • Single thread: everything runs on the Android main thread, with no pthread. The magma runtime is not thread-safe, so this is intentional.
  • lifecycle: onStart/Resume/Pause/Stop/Destroy, onWindowFocusChanged, onNativeWindow*, onInputQueue*, onContentRectChanged, onConfigurationChanged, onLowMemory callbacks;
  • input: AInputQueue_attachLooper on the main thread's looper, with an OFS callback;
  • frames: AChoreographer_postFrameCallback (API 24+), rescheduled only on request (android.request_frame() or android.continuous = true).
  • Long work must be split into chunks, one per EV_FRAME.
  • Contract: the program defines vein android_event(ev: stone) -> void and reads state from android.*:

            android.unlock_post()

    if (ev == android.EV_TOUCH_DOWN) { android.request_frame() }
    if (ev == android.EV_BACK) { android.finish() }

Audio (`audio_android.ofs` + `wav.ofs`): audio.open() opens a 44.1 kHz stereo i16 AAudio stream with a callback; audio.play(channel, wav.load(...) or wav.decode(ptr, n), loop), stop, stop_all, set_volume(channel, %), set_master(%), playing(channel), pause/resume/close, pump() once per frame. The mixer runs on the audio thread and only touches raw memory (no Arrays/strings); replaced PCM is freed after a safe delay. wav.ofs decodes 8/16-bit PCM and Microsoft ADPCM (output identical to ffmpeg's). The CLI links -laaudio.

The back button is delivered as EV_BACK and does not close the app by itself: call android.finish() (OAL does it by default).

Text input via the system keyboard (android_input.ofs)

ainput.open(title, text, multiline) opens an android.app.Dialog with a JNI-created EditText (no Java of our own): default keyboard (Gboard), cursor, paste and autocomplete. No listeners: the buttons are ToggleButtons (they toggle on tap; ainput.poll() reads isChecked()), and back/tap outside closes the Dialog (isShowing()). poll() returns 0 open, 1 OK, 2 cancelled; ainput.text() reads the text. OAL exposes it as oal.edit_open.

Current limits

  • arm64-v8a (aarch64) only and API 26+. No x86/armv7.
  • Software rendering (ANativeWindow_lock), no OpenGL/Vulkan.
  • Audio: WAV only (PCM/MS-ADPCM); no Ogg/MP3; no quality resampling (integer 16.16 step).
  • No onSaveInstanceState (the app saves its own state in on pause).
  • The offsets of C structs (ANativeActivity, ANativeWindow_Buffer, ARect, struct stat/statfs, JNIEnv table) are fixed for aarch64.
  • 32-bit C integers arrive as stone with undefined upper bits: use android.s32().
  • fault_call only passes integers and pointers (no float/double).
  • The installed ofs/dist/magma.o and ofscc still predate the Android target: until the next release, the CLI builds ofscc from source.

Generic JNI, WebView, HTTP (stdlib)

  • Generic JNI (android.ofs): jni_call(obj, name, signature, a..f) (the return kind comes from the signature: V, Z, I, J, object), jni_new(class, signature, a..d), jni_scall(class, name, signature, a..d) (static), jni_static_int_field, jni_global/jni_delete_global, jni_new_byte_array/jni_get_bytes/jni_set_bytes, jni_new_object_array/jni_set_object_elem; android.jni_failed tells whether a Java exception happened. Main thread only.
  • `android_webview.ofs`: webview.open(base_url, html) opens a WebView (JS, DOM storage, file access, media without gesture) in a full-screen immersive android.app.Dialog; poll() (Back closes the Dialog), eval(js), title(), pause(on), close(). Why a Dialog: NativeActivity takes the main window surface (takeSurface), so a View added to its window is not drawn; the Dialog has its own window and gets touch directly (not through AInputQueue). No Java subclass: the shim goes in as a <script> in the HTML (loadDataWithBaseURL("file:///folder/", html)), and the JS-to-OFS return channel is document.title (Chromium cuts titles at 4096 characters and collapses whitespace/control chars: send in chunks and with encodeURIComponent). EV_FRAME keeps arriving while the main window is covered. ofs_str_char_at is O(n): read bytes by pointer on large texts.
  • `android_http.ofs`: ahttp.open(url)/read(buf)/close() and get_text(url) over HttpURLConnection (HTTPS with certificate checking and redirects; the OpenSSL of tls.ofs cannot be linked in an APK). Blocks up to ~4 s per call on the main thread (use short per-frame steps; StrictMode is relaxed). Needs permission INTERNET in the .oal. Accepts file:///... and absolute paths.

Engine mode: hosting other code/Views in the NativeActivity (stdlib android.ofs)

To run a game engine (SDL, Godot) inside the app, without installing an APK and without Java in the APK (hasCode=false):

  • release_window(): calls getWindow().takeSurface(null) and takeInputQueue(null). Call it in `EV_CREATE` (the window is attached only after onResume). From then on the NativeActivity no longer claims the surface or the input queue: set_content_view(view) (or a Java adapter's setContentView) draws normally and gets touch/keys through Java. OFS stops receiving EV_WINDOW_* and touches; lifecycle events still arrive. Tested on Android 11 (Moto G8 Power). In AOSP's NativeActivity.java, onCreate calls takeSurface(this)/takeInputQueue(this) before ANativeActivity_onCreate; ViewRootImpl reads those callbacks when the window is attached, so null wins.
  • dex_load_class(dex, libs_dir, "pkg.Class"): DexClassLoader (parent: the activity's class loader) + loadClass; returns a global class reference or 0 (reason in jni_error). dex accepts several files separated by :. The .dex must live in the app's internal storage and, on Android 14+, be read-only (set_read_only(path)). libs_dir is that loader's System.loadLibrary search path.
  • jni_scall_cls(cls, name, signature, a..d): static method on an already obtained jclass (e.g. from dex_load_class).
  • jni_take_error(): if a Java exception is pending, stores its toString() in jni_error, prints the stack to logcat (System.err) and clears it.
  • intent_extra(key): getIntent().getStringExtra(key) ("" if missing).
  • self_intent(keys, values) / restart_process(keys, values): Intent for this same activity with String extras and FLAG_ACTIVITY_NEW_TASK|CLEAR_TASK; restart_process calls startActivity and kills the process (Process.killProcess(myPid)): the system opens the activity in a fresh process (~60 ms on a Moto G8). M.O.O.N uses it to enter and leave "engine mode" (one engine per process).

[1.1.0] - 2026-04-12 — Self-Hosted Compiler

Major Milestone: OFS Compiler is Self-Hosting

The OFS compiler is now written entirely in OFS!

After implementing a complete compiler pipeline in pure OFS (lexer, parser, type checker, code generator), the language has reached a critical milestone: it can compile itself. This is the same achievement as Go (2015), Rust (2011), and C (1972).

Technical Details

Compiler Architecture:

  • Phase 1: Lexer — Tokenizes source (80 token kinds)
  • Phase 2: Parser — Recursive descent + Pratt precedence
  • Phase 3: Type Checker — Scope stack + type inference
  • Phase 4: Codegen — Emits valid C code
  • Phase 5: C Compilation — Calls gcc -O2
  • Phase 6: Output — Native executable

Features Supported:

  • All primitive types (stone, crystal, obsidian, bool, u8-u64, i32)
  • Functions, variables, constants
  • Arrays, monoliths (structs)
  • Control flow (if/else, while, cycle, match, break, continue, return)
  • Operators (arithmetic, logical, bitwise, comparison)
  • String literals with escape sequences
  • Comments (//, /* */)
  • Type inference (basic)
  • Error messages (simple)

Limitations (Addressed in v1.2):

  • Command-line argument parsing
  • impl/namespace/strata (parsing only)
  • Full error recovery
  • Diagnostics beyond stderr

[1.0.148] - 2026-09-30 — Hybrid Interpreter Backend & Differential Testing

Added

  • AST Interpreter Backend (`interpreter.ofs`): OFS is now a true hybrid language. Running ofs <file.ofs> or ofs run <file.ofs> directly evaluates the typed AST without invoking LLVM, Clang, or linker phases, providing sub-millisecond execution for scripting and prototyping.
  • Value Monolith & Dynamic Heap: Full runtime support for primitives (stone, crystal, obsidian, bool), handles for Array<T>, heap-allocated monolith structs with value-copy semantics, and pointers with the Location table.
  • Lexical Call Frame Scoping: Frame base tracking (_current_frame_base and _globals_count) ensuring that local variables in caller functions never leak or shadow global declarations in callees.
  • Method Dispatch via `impl`: Support for methods declared in impl Type { vein method(self: Type) ... } called directly on instances (instance.method()).
  • Differential Test Suite: Automated differential runner ofs/tests/interpreter/test_differential.sh with 9 end-to-end test suites asserting 1-to-1 output equivalence between interpreted mode and native LLVM builds.
  • CI Integration: Added differential test validation to GitHub Actions workflows on Linux and macOS.

Changed

  • ofs run <file.ofs> defaults to instant interpreted execution; ofs run --native <file.ofs> is available for temporary compilation + execution.
  • Windows PowerShell runner src/packaging/windows/ofs.ps1 updated with interpreted mode and --native flag for complete parity across Linux, macOS, and Windows.
