Empezando

Guía de inicio de OFS

OFS (Obsidian Fault Script) es un lenguaje de programación híbrido y self-hosted, que incluye un intérprete AST integrado para ejecución instantánea (ofs run) y un backend LLVM para generar ejecutables binarios nativos de alto rendimiento (ofs build).

El ecosistema incluye el compilador, la biblioteca estándar, herramientas de línea de comandos y los lenguajes de dominio web ODL y OES.

1. Instalación

Paquetes precompilados

Hay instaladores oficiales disponibles para varias distribuciones y sistemas operativos:

  • Debian / Ubuntu:
  sudo dpkg -i ofs-debian-ubuntu-x64-installer-v*.deb
  • Fedora / RHEL / openSUSE:
  sudo rpm -Uvh ofs-fedora-x64-installer-v*.rpm
  • Arch / Manjaro:
  sudo pacman -U ofs-arch-x64-installer-v*.pkg.tar.zst
  • macOS (Apple Silicon / ARM64):
  • Ejecute el script instalador incluido en el release de GitHub.
  • Windows (x64):
  • Ejecute el instalador ofs-windows-x64-installer-v*.exe.
  • VS Code:
  • Instale la extensión oficial ofs-vscode-extension.vsix para soporte de sintaxis, resaltado y recarga dinámica (*Go Live*).

Compilación desde el código fuente (Bootstrap)

Para compilar el compilador directamente desde el repositorio: 

git clone https://github.com/Samwns/Obsidian-Fault-Script.git
cd Obsidian-Fault-Script
bash ofs/bootstrap/scripts/bootstrap-minimal.sh

El binario del compilador se generará en ofs/dist/ofs (o ofs/dist/ofscc).

Termux (Android)

OFS corre en el propio teléfono, dentro de Termux (aarch64).

Instalar (en Termux): 

curl -fsSL https://raw.githubusercontent.com/Samwns/Obsidian-Fault-Script/main/src/packaging/termux/install_termux.sh | bash
# o, con el paquete local:  bash install_termux.sh ofs-termux-aarch64.tar.gz

El instalador ejecuta pkg install -y clang, descarga la última release ofs-termux-aarch64.tar.gz, la extrae en $PREFIX (bin/ofs y lib/ofs/) y prueba ofs --version.

Usar: ofs run hello.ofs (interpretado), ofs build hello.ofs -o hello && ./hello (nativo aarch64, enlaza con el clang de Termux). Las herramientas están en $PREFIX/lib/ofs/tools/ (ofs run $PREFIX/lib/ofs/tools/odlc.ofs).

Limitaciones: sin ventanas X11 por ahora (ventanas .oll/.oal); generar un APK en el teléfono (ofs build --target android) queda para después.

3. Primer programa

Cree un archivo llamado hello.ofs: 

core main() {
    echo("Olá, Mundo via OFS!")
}

Ejecución directa en el intérprete AST: 

ofs hello.ofs
# o: ofs run hello.ofs

O compilación a un ejecutable binario nativo: 

ofs build hello.ofs -o hello
./hello

Salida: 

Olá, Mundo via OFS!

4. Tipos de datos

OFS es de tipado estático. El compilador ofrece inferencia de tipos en las declaraciones de variables locales (forge).

Tipos fundamentales

  • stone: Entero de 64 bits con signo.
  • crystal: Punto flotante de 64 bits (IEEE 754).
  • obsidian: Secuencia de caracteres UTF-8 (*string*).
  • bool: Booleano (true o false).
  • void: Ausencia de valor de retorno.

Enteros de ancho fijo

  • Sin signo: u8, u16, u32, u64
  • Con signo: i8, i32

Ejemplo de declaración y conversión explícita: 

core main() {
    forge contador: stone = 10
    forge taxa: crystal = 3.14159
    forge ativo: bool = true
    forge nome: obsidian = "Obsidian"

    forge canal_r: u8 = 255
    forge canal_g: u8 = 128
    forge pixel: u32 = (canal_r as u32 << 16) | (canal_g as u32 << 8)

    echo(nome)
    echo(pixel)
}

5. Funciones

Las funciones se definen con la palabra clave vein. El punto de entrada nativo del programa es la función core main(). 

vein somar(a: stone, b: stone) -> stone {
    return a + b
}

vein fatorial(n: stone) -> stone {
    if (n <= 1) {
        return 1
    }
    return n * fatorial(n - 1)
}

core main() {
    forge s = somar(15, 27)
    forge f = fatorial(5)
    echo(s)
    echo(f)
}

Las funciones pueden componer llamadas entre sí e invocar otras rutinas: 

vein quadrado(n: stone) -> stone {
    return n * n
}

vein soma_quadrados(a: stone, b: stone) -> stone {
    return quadrado(a) + quadrado(b)
}

core main() {
    echo(soma_quadrados(3, 4))
}

Nota: Las expresiones anónimas (*lambdas*) están especificadas en el árbol sintáctico (NK_LAMBDA) y en planificación en el roadmap del lenguaje. Actualmente todas las funciones deben tener nombre con vein.

6. Estructuras de datos (monolith)

OFS usa la palabra clave monolith para definir tipos compuestos y bloques impl para asociar métodos: 

monolith Retangulo {
    largura: stone
    altura: stone
}

impl Retangulo {
    vein area(self: Retangulo) -> stone {
        return self.largura * self.altura
    }

    vein perimetro(self: Retangulo) -> stone {
        return (self.largura + self.altura) * 2
    }
}

core main() {
    forge r: Retangulo
    r.largura = 10
    r.altura = 5

    echo(r.area())
    echo(r.perimetro())
}

7. Módulos e importaciones (attach)

La declaración attach importa módulos de la biblioteca estándar instalada o archivos locales: 

attach {math}
attach {string}
attach {io}

Para importar archivos locales relativos o absolutos, use el prefijo F:: 

attach {F:./modulos/auxiliar.ofs}

8. Control de flujo

Condicionales (if / else)

core main() {
    forge x: stone = 10
    if (x > 0) {
        echo("positivo")
    } else if (x < 0) {
        echo("negativo")
    } else {
        echo("zero")
    }
}

Bucles de repetición (while)

core main() {
    forge i: stone = 0
    while (i < 5) {
        echo(i)
        i = i + 1
    }
}

Selección de múltiples caminos

Las ramificaciones con múltiples condiciones usan if / else if / else: 

core main() {
    forge status_code = 200
    if (status_code == 200) {
        echo("Sucesso")
    } else if (status_code == 404) {
        echo("Não encontrado")
    } else {
        echo("Outro código")
    }
}

Nota: La construcción match está reservada en la especificación del AST (NK_MATCH) y en el lexer, con parser y desvío dedicados planificados en el roadmap.

Manejo y validación de errores (throw)

La instrucción throw muestra un mensaje de fallo y termina el proceso con código de error 1: 

vein dividir(dividendo: stone, divisor: stone) -> stone {
    if (divisor == 0) {
        throw "Divisão por zero inválida"
    }
    return dividendo / divisor
}

core main() {
    echo(dividir(10, 2))
}

Nota: La estructura tremor { ... } catch (...) { ... } está modelada en la gramática (NK_TREMOR), con desenrollado estructurado de pila previsto para las próximas etapas del runtime y del intérprete.

9. Interoperabilidad nativa con C (rift / extern vein)

Es posible declarar y llamar símbolos C externos directamente: 

extern vein puts(s: obsidian) -> stone
rift vein strlen(s: obsidian) -> stone bind "strlen" abi c

core main() {
    puts("Mensagem enviada via puts do C")
}

10. Stack web: ODL y OES

El ecosistema OFS cuenta con dos lenguajes de dominio específico (DSL) dedicados a construir interfaces web estáticas y dinámicas:

ODL (Obsidian Document Language)

Estructura semántica para documentos web compilada a HTML5: 

page "Aplicação OFS" "pt"
skin "estilo.css"

flow
  deck.navegacao
    title1 "Título Principal"
    link.botao "Documentação" "#docs"
  stage#conteudo
    band.artigo
      mark "## Conteúdo nativo\nTexto formatado em **Markdown**."
      raw "<div class=\"custom\">HTML bruto quando necessário</div>"
  spark "app.js"

Compilación de ODL (la herramienta odlc forma parte de la biblioteca estándar de herramientas y se ejecuta con el propio ofs): 

# en el repositorio OFS (o con las tools instaladas en /usr/share/ofs/tools)
ODLC_INPUT=documento.odl ODLC_OUTPUT=public/index.html ofs run ofs/tools/odlc.ofs

OES (Obsidian Effect Scripts)

Definición de estilos, variables, reglas responsivas y animaciones compilada a CSS: 

gem primario "#5b34ea"
gem fundo "#120e24"

paint .botao
  fill "$primario"
  curve "6px"
  space "8px 16px"
  edge "none"

veil "(max-width: 768px)"
  paint .grade
    grid-cols "1fr"

pulse "surgir"
  rise
    opacity "0"
  rest
    opacity "1"

Compilación de OES (mismo patrón, usando la herramienta oesc): 

OESC_INPUT=estilo.oes OESC_OUTPUT=public/estilo.css ofs run ofs/tools/oesc.ofs

Servidor HTTP nativo (webserver)

La biblioteca estándar incluye un servidor HTTP nativo integrado al runtime: 

attach {webserver}

core main() {
    forge html = "<h1>Servidor Nativo OFS</h1><p>Executando sem dependências externas.</p>"
    webserver.serve_html_forever(8080, html)
}

Empezando

OFS — Beginner's Journey

A step-by-step practical guide to learning Obsidian Fault Script (OFS) from the ground up, starting with primitives and advancing to structures, modules, and collections.

How to Follow This Guide

  1. Read and work through one module at a time.
  2. Run each example via the terminal with ofs run file.ofs (or compile with ofs build file.ofs -o app).
  3. Experiment by changing values and verifying compiler feedback.
  4. Advance to the next module only after fully understanding the program output.

Module 1: Variables and Primitive Types

Goal: Understand core main(), variable declarations with forge, console output with echo(), and fundamental types. 

core main() {
    forge name: obsidian = "Alice"
    forge age: stone = 24
    forge rating: crystal = 9.8
    forge active: bool = true

    echo(name)
    echo(age)
    echo(rating)
    echo(active)
}

Challenge: Declare additional variables to hold a city name (obsidian) and an exchange rate (crystal).

Module 2: Conditionals and Loops

Goal: Use conditional branching (if / else) and loops (while). 

core main() {
    forge energy: stone = 3

    while (energy > 0) {
        echo(energy)
        energy = energy - 1
    }

    if (energy == 0) {
        echo("Recharge required")
    }
}

Challenge: Write a loop that counts down from 5 to 1 and then prints "Liftoff".

Module 3: Functions (vein)

Goal: Structure and reuse computational logic using the vein keyword. 

vein double(n: stone) -> stone {
    return n * 2
}

vein add(a: stone, b: stone) -> stone {
    return a + b
}

core main() {
    echo(double(21))
    echo(add(10, 32))
}

Challenge: Write a function average(a: stone, b: stone) -> stone that returns the integer arithmetic mean of two numbers.

Module 4: Fixed-Width Integers

Goal: Work with machine-sized integer types (u8, u16, u32, i8, i32). 

core main() {
    forge channel_r: u8 = 255
    forge channel_g: u8 = 128
    forge channel_b: u8 = 0

    forge pixel: u32 = (channel_r as u32 << 16) | (channel_g as u32 << 8) | (channel_b as u32)
    echo(pixel)
}

Challenge: Extract the green channel (channel_g) back out from pixel using right bit-shifts and masking (& 0xFF).

Module 5: Records (monolith) and Methods (impl)

Goal: Model composite structures and attach methods using monolith and impl. 

monolith Rectangle {
    width: stone
    height: stone
}

impl Rectangle {
    vein area(self: Rectangle) -> stone {
        return self.width * self.height
    }

    vein perimeter(self: Rectangle) -> stone {
        return (self.width + self.height) * 2
    }
}

core main() {
    forge r: Rectangle
    r.width = 10
    r.height = 20

    echo(r.area())
    echo(r.perimeter())
}

Challenge: Add an is_square(self: Rectangle) -> bool method that returns true when width equals height.

Module 6: Namespaces (namespace)

Goal: Group functions and constants under scoped identifiers to prevent collisions. 

namespace math_utils {
    vein square(x: stone) -> stone {
        return x * x
    }

    vein cube(x: stone) -> stone {
        return x * x * x
    }
}

core main() {
    echo(math_utils.square(5))
    echo(math_utils.cube(3))
}

Module 7: Modular Code with attach

Goal: Split code across separate files and import functions.

Helper file helper.ofs: 

vein greet(name: obsidian) -> obsidian {
    return "Hello, " + name + "!"
}

Main file main.ofs: 

attach {F:./helper.ofs}

core main() {
    echo(greet("OFS"))
}

Module 8: Arrays and Collections (Array<T>)

Goal: Store sequential collections of items, access values by index, and inspect array length. 

core main() {
    forge scores: Array<stone> = [85, 92, 78]
    echo(scores[0])

    scores[1] = 95
    echo(scores[1])
    echo(ofs_array_len(scores))
}

Challenge: Create an array with 4 numbers and compute their total sum using a loop.

Module 9: Structured Loops (cycle)

Goal: Iterate cleanly using C-style indexed loops and collection traversal. 

core main() {
    cycle (forge i = 0; i < 5; i++) {
        echo(i)
    }

    forge items: Array<stone> = [10, 20, 30]
    cycle (val in items) {
        echo(val)
    }
}

Challenge: Use cycle (item in list) to count how many numbers in an array are greater than 15.

1. Estructura de programa

Todo programa ejecutable necesita un core main(): 

core main() {
    echo("inicio")
}

core es palabra reservada: solo marca el punto de entrada. Usarla como nombre (vein core(), core(1), también dentro de un namespace) es error de compilación ("core e palavra reservada…"); renombre la función (p. ej. core_fn). Cualquier error sintáctico detiene la compilación con código 1.

Un archivo .ofs puede contener:

  • attach { ... }
  • extern vein y rift vein
  • vein y core
  • monolith
  • impl
  • namespace
  • strata
  • forge global

4. Funciones e intents

Funciones normales

vein soma(a: stone, b: stone) -> stone {
    return a + b
}

Entrada del programa

core main() {
    echo("ok")
}

Intent

vein square(x: stone) -> stone intent pure {
    return x * x
}

Intents aceptados:

  • pure
  • impure
  • fractal

Composición de funciones

Las funciones pueden invocar a otras funciones y admiten recursión directa: 

vein quadrado(n: stone) -> stone {
    return n * n
}

vein soma_quadrados(a: stone, b: stone) -> stone {
    return quadrado(a) + quadrado(b)
}

core main() {
    echo(soma_quadrados(3, 4))
}

Nota: Las expresiones anónimas de función (vein(...) -> ... en línea) están especificadas en el árbol sintáctico (NK_LAMBDA) y planificadas para la hoja de ruta de evolución del lenguaje. Actualmente, todas las funciones deben declararse con nombre mediante vein.

5. monolith, impl y layouts

Estructura

monolith Rect {
    w: stone
    h: stone
}

Métodos con impl

impl Rect {
    vein area(self: Rect) -> stone {
        return self.w * self.h
    }
}

Uso: 

forge r: Rect
r.w = 10
r.h = 5
echo(r.area())

Layout explícito

Planificado: layout es palabra reservada, pero el parser todavía no acepta layout en un monolith (da expected '{' after monolith name). Hoy todo monolith usa el layout nativo. La sintaxis de abajo es la prevista. 

monolith Header layout packed {
    tag: stone
    flags: stone
}

Layouts soportados:

  • native
  • packed
  • c

8. Control de flujo

if / else

if (x > 10) {
    echo("alto")
} else {
    echo("baixo")

while

while (energia > 0) {
    energia -= 1

cycle

Forma tipo C: 

cycle (forge i = 0; i < 10; i++) {
    echo(i)
}

Forma iterativa: 

cycle (n in nums) {
    echo(n)
}

Selección de múltiples caminos

La selección de múltiples ramas se realiza mediante cadenas de if / else if: 

if (code == 200) {
    echo("ok")
} else if (code == 404) {
    echo("nao encontrado")
} else {
    echo("erro")
}

O con match (sinónimo: assay), que compara el valor con cada caso usando ==; _ es el caso por defecto: 

match (code) {
    200 => { echo("ok") }
    404 => { echo("no encontrado") }
    _ => { echo("error") }
}

Manejo de errores e interrupción (throw)

La instrucción throw muestra un mensaje de diagnóstico y termina la ejecución con código de salida 1: 

vein dividir(dividendo: stone, divisor: stone) -> stone {
    if (divisor == 0) {
        throw "divisao por zero indefinida"
    }
    return dividendo / divisor
}

core main() {
    echo(dividir(10, 2))
}

Nota: La sintaxis tremor { ... } catch (e: obsidian) { ... } es reconocida por la gramática (NK_TREMOR), con desenrollado estructurado de pila y captura en tiempo de ejecución previstos para las capas del intérprete y la evolución del runtime.

strata (enumeraciones de variantes)

strata Status { Idle, Running, Failed }

Nota: strata se analiza sintáctica y semánticamente, con generación directa para el backend LLVM prevista en la hoja de ruta de tipos algebraicos.

expr? desenvuelve una variante de resultado:

  • Solid(v)? y Ore(v)? valen v.
  • Crack(e)? y Barren? salen de la vein actual de inmediato (los anchor pendientes se ejecutan), propagando el fallo. Las variantes de fallo son las llamadas Crack y Barren; cualquier otra cuenta como éxito.

El valor propagado es igual en los dos modos:

  • En la compilación nativa las variantes son etiquetas i64 sin payload: la etiqueta es la posición de la variante en el orden de declaración de todas las strata del programa (con strata Outcome { Solid, Crack } declarada primero, Crack = 1). Una vein ... -> stone que propaga Crack devuelve esa etiqueta, y echo imprime 1 en los dos modos. Con retorno obsidian se obtiene el texto de la etiqueta; con crystal, el número; en core main se convierte en el código de salida.
  • En el intérprete, si el tipo de retorno declarado es el propio tipo strata (-> Outcome), se devuelve la variante entera (con payload).
  • Como el código nativo no guarda payload, x? sobre una expresión que no es un constructor directo (p. ej. f()?) vale la etiqueta de la variante de éxito, no su payload.
strata Outcome { Solid, Crack }

vein ok() -> stone {
    forge v = Solid(7)?      // 7
    return v
}

vein bad() -> stone {
    forge v = Crack("boom")? // sale aquí devolviendo 1
    return v
}

core main() {
    echo(ok())   // 7
    echo(bad())  // 1
}

Prueba: ofs/tests/regress/question_propagation.ofs.

Dirección de función y llamada indirecta (fault_addr, fault_call)

OFS no tiene un tipo "puntero a función", pero puede obtener la dirección de una vein como stone y llamar a una dirección con la ABI de C. Sirve para callbacks de bibliotecas C (qsort, ANativeActivity, ALooper, AChoreographer) y para tablas de funciones de C (JNI). 

rift vein c_qsort(base: *stone, n: stone, size: stone, cmp: stone) -> void bind "qsort" abi c

vein crescente(a: *stone, b: *stone) -> stone {
    forge x = 0
    forge y = 0
    fracture { x = *a; y = *b; }
    if (x < y) { return -1 }
    if (x > y) { return 1 }
    return 0
}

core main() {
    forge buf = ofs_alloc(64)
    // ...llena 8 valores...
    c_qsort(buf, 8, 8, fault_addr(crescente))
    forge r = fault_call(fault_addr(crescente), buf, fault_step(buf, 1))
}
  • fault_addr(nome) → stone: dirección de la vein. Acepta vein del módulo, ns.vein y extern/rift vein (con bind, devuelve el símbolo de C). En IR: ptrtoint ptr @simbolo to i64. Fuera de una vein, es un error semántico.
  • fault_call(endereco, args...) → stone: llamada indirecta con la ABI de C (inttoptr + call i64). Argumentos enteros, punteros y obsidian; el retorno se lee como i64 (las funciones void devuelven basura, ignórela). Sin float/double.
  • La vein usada como callback debe tener parámetros compatibles con la ABI de C: stone para enteros (los enteros de 32 bits llegan con la parte superior indefinida; enmascárelos con & 4294967295) y *stone para punteros.
  • En el intérprete (ofs run), fault_addr de un extern/rift vein devuelve la dirección C y fault_addr de una vein interpretada devuelve un trampolín nativo que reentra en el intérprete (el qsort de arriba funciona igual). Ver "En el intérprete (ofs run): FFI".
  • Prueba: ofs/tests/runtime/test_fault_addr_qsort.ofs.

Campos importantes:

  • bind "..." define el símbolo nativo real
  • abi c define la ABI de C
  • ... se acepta en una función variádica nativa

En el intérprete (ofs run): FFI

ofs run llama a las mismas funciones C que enlazaría la compilación nativa, sin C propio y sin libffi:

  • Resolución al cargar. Cada extern vein/rift vein llamada por el programa (o pasada a fault_addr) se convierte en una dirección con dlsym(RTLD_DEFAULT, "símbolo"), usando el bind cuando existe. Antes, el intérprete abre libm (la compilación enlaza -lm) y las bibliotecas de OFS_FFI_LIBS (libfoo.so:/ruta/libbar.so); si falta algún símbolo, prueba también libX11/libXft (ofs build enlaza ambas cuando existen). Un símbolo ausente da el mismo error del enlazador (undefined reference to 'x') antes de ejecutar, con código de salida 1. Una extern declarada y nunca llamada no necesita existir (como en el enlace).
  • Runtime OFS. ofscc se enlaza con -rdynamic, así que ofs_alloc, ofs_echo_color etc. también se encuentran. Las veins definidas en stdlib/runtime/*.ofs (incluidas con attach) ejecutan la versión nativa enlazada en ofscc, como los builtins, cuando la firma cabe en el FFI; OFS_RUN_RUNTIME=interp lo desactiva.
  • Conversión. stone, bool, enteros (i8..u64, ajustados al ancho y al signo), punteros y obsidian (el char* del propio valor) van como i64; crystal va en registro FP. El retorno sigue el tipo declarado: char* pasa a obsidian sin copia (como en nativo, donde obsidian es el puntero; NULL pasa a null), *T pasa a la dirección (puede volver a C, compararse con null, convertirse con as y desreferenciarse), monolith al bloque y Array al propio ofs_array.
  • Trampolines. La llamada pasa por __ofs_ffi_dispatch, generada por llvmgen dentro de ofscc: un caso con el tipo LLVM exacto por clase de firma (hasta 4 argumentos con cualquier mezcla stone/crystal y retorno entero o crystal; hasta 12 solo enteros; variádicas con 1 a 3 fijos y hasta 4 extras). Otra clase es un error claro.
  • Variádicas (printf, snprintf, open...): las que llvmgen conoce por nombre; los extras van en el tipo declarado (o en el del valor), con la convención correcta (%al en x86-64).
  • fault_addr(extern) devuelve la dirección C y fault_call(direccion, ...) llama con los argumentos en el tipo del valor (como en nativo). fault_step suma sobre un puntero de C.
  • Memoria cruda (F2). El intérprete corre nativo, así que un puntero es una dirección real. *p y *p = v leen y escriben con el ancho del tipo apuntado (u8/i8/u16/i16/u32/i32/u64/i64/stone/f32/f64/crystal/bool (4 bytes)/obsidian/*T), con el tipo estático del typeck (el mismo que usa el llvmgen); los enteros estrechos quedan con signo extendido (iN) o ceros (uN), como en el nativo. Un p nulo falla como en el nativo (dirección 0). fault_memcpy/fault_memset usan memcpy/memset reales, de cualquier tamaño; fault_step(p, i) suma i * sizeof(*p) con el tipo estático de p.
  • `as` sigue la regla del llvmgen: mismo tipo LLVM solo cambia el tipo; ptrtoint/inttoptr (incluido obsidian, que es el propio char*); fptosi/sitofp (desde el ancho de origen); fpext/fptrunc (f32 redondea); trunc si el origen es más ancho, si no zext (también desde iN: (0 - 1) as i8 as stone da 255). forge x: u8 = 300 y x = v en un u8/i32/f32 truncan como el store del nativo.
  • `&x`. La dirección de una variable del intérprete es real: en el primer &x la variable pasa a vivir en un slot de memoria cruda de 8 bytes (C puede leerlo y escribirlo: sscanf(s, "%d", &n), strtol(s, &fin, 10), modf(x, &entera)), liberado cuando la variable sale de alcance, como la alloca del nativo. &x de un monolith es el propio bloque. Solo existe dirección de variable (el nativo tampoco tiene &s.campo/&a[i]: use (&s) as stone + offset); &x de una variable Array es un error claro.
  • `monolith` con layout C. Las instancias viven en memoria cruda con el layout de llvmgen.struct_layout (el mismo del código nativo: campos en orden, cada uno alineado a su propio tamaño, hasta 8; bool ocupa 4 bytes; Array y monolith anidado ocupan 8). s o &s pasado a C (memcpy, qsort de structs...) ve los mismos bytes que el build nativo. Como en el nativo, un monolith pasado a una vein es por referencia y forge y: T = x/y = x copian. Un campo Array guarda el array del intérprete (C no debe leerlo).
  • `Array` y strings. Un Array pasado a C es el propio ofs_array nativo (cabecera [data, len, cap, elem_size] + datos) de la columna de valores del intérprete; C escribe los elementos en el lugar y la longitud se sincroniza a la vuelta. Elementos de un solo tipo (enteros/punteros, crystal, bool, obsidian o monolith); tipos mezclados son un error claro. Un Array devuelto por C usa el mismo bloque, sin copia. obsidian ya es el char*. Use ofs_array_data(a) para pasar solo los datos (ej.: qsort).
  • Callbacks C → OFS. fault_addr(vein) de una vein interpretada liga la vein a uno de 16 trampolines nativos (__ofs_cb_0..__ofs_cb_15, generados por el llvmgen dentro del ofscc); C llama al trampolín, que reentra en el intérprete, incluso dentro de una llamada C hecha por el propio programa (qsort dentro de qsort, fault_call de otro callback). La misma vein reutiliza su slot. Hasta 6 parámetros enteros, punteros, obsidian, bool o monolith (por puntero) y retorno entero/puntero. Más de 16 veins distintas, más de 6 parámetros o crystal/f32 en el callback dan un error claro con código 1 (use ofs run --native). f32 como argumento del FFI tampoco está soportado aún.
  • bedrock, fracture y abyss son bloques comunes en los dos modos (el nativo no cambia nada dentro de ellos); las celdas y regiones del bedrock (stdlib) usan la memoria cruda de arriba.
  • Pruebas: ofs/tests/regress/ffi_*.ofs, tests/parity/cases/libc_*.

seal / anchor (ejecutar al salir del ámbito)

seal { … } y anchor { … } son lo mismo (el mismo token): registran una acción que se ejecuta cuando termina el ámbito actual, en cualquier salida (fin del bloque, return, break/shatter, continue/erode, propagación ?). Varias acciones se ejecutan en orden inverso (la última registrada va primero). seal es el nombre temático ("sella el recurso al salir"); anchor sigue valiendo. Aceptan un bloque o una sola instrucción. 

vein copiar(origen: obsidian) -> stone {
    forge f = fopen(origen, "r")
    seal { fclose(f) }           // se ejecuta en cualquier return de abajo
    anchor echo("fin de copiar") // igual que seal; va antes del fclose (LIFO)
    if (f == null) { return 1 }
    // ...
    return 0
}
  • La acción se evalúa al salir, con los valores de ese momento.
  • return, break, continue y throw dentro de seal/anchor están prohibidos (error E0042).
  • Funciona igual en nativo y en ofs run. Prueba: ofs/tests/regress/seal_defer.ofs.

while (bucle solo con condición)

forge count: stone = 10
while (count > 0) {
    echo(count)
    count -= 1
}

Sintaxis: 

while (<condition>) {
    <body>
}

while es azúcar sintáctico para un cycle con solo una condición. break y continue funcionan dentro de los bloques while.

En attach {modulo}, el guion se vuelve guion bajo (terminal-colors → terminal_colors.ofs). Un módulo que no existe en ninguno de esos lugares es error de compilación, con la lista de rutas probadas ([ERRO DE ATTACH archivo:linea]: modulo 'x' nao encontrado). Antes, attach {x} de un módulo inexistente se ignoraba en silencio.

Nombres indefinidos

Usar un nombre no declarado (variable, global, constante) es error de compilación en los dos modos, con el archivo y la línea reales y una sugerencia cuando hay un nombre parecido ([ERRO SEMANTICO calc.ofs:5:12]: identificador indefinido 'contadr' / voce quis dizer 'contador'?). Los globales de nivel superior se pueden usar en una vein antes de la línea que los declara. Un módulo verificado solo (ofs check modulo.ofs) no ve los nombres del archivo que lo anexa: verifique el archivo principal. Los tipos incompatibles en una operación ([AVISO DE TIPO]) siguen siendo solo aviso.

Funciones externas

Declare funciones externas de C para FFI (Foreign Function Interface): 

extern vein ofs_pow(base: crystal, exp: crystal) -> crystal
extern vein ofs_sqrt(val: crystal) -> crystal
extern vein ofs_str_len(s: obsidian) -> stone

core main() {
    forge result = ofs_pow(2.0, 10.0)
    echo(result)  // prints 1024
}

Todas las funciones del runtime de OFS pueden accederse mediante declaraciones extern. Esto permite programar a bajo y alto nivel en el mismo lenguaje.

rift vein

OFS ahora también admite rift vein como forma de declaración orientada a la interoperabilidad nativa: 

rift vein strlen(text: obsidian) -> stone

core main() {
    echo(strlen("fault"))
}

rift vein se reduce al mismo pipeline de llamadas externas que extern vein, pero presenta la interoperabilidad como un límite nativo de OFS en lugar de enmarcar la característica solo como "extern C".

También puede añadir metadatos explícitos de interoperabilidad: 

rift vein text_size(text: obsidian) -> stone bind "strlen" abi c
  • bind "symbol" define el nombre del símbolo de enlace externo.
  • abi c declara la ABI prevista.
  • abi system está reservado para llamadas en el límite de plataforma/sistema.

Dirección de interoperabilidad

extern vein es la superficie FFI actual. Hoy en día es más adecuada para símbolos de runtime y compatibles con C.

La hoja de ruta amplía esto hacia capas de interoperabilidad nativa más ricas para:

  • límites de objetos y bibliotecas de C,
  • capas de puente de C++,
  • puentes de host/runtime de C#,
  • incrustación de Python o bindings de host,
  • escapes de ensamblador específicos del destino.

Estos son elementos de la hoja de ruta, no todos son funciones implementadas hoy.

Estructuras (monolith)

Las estructuras se definen con la palabra clave monolith: 

monolith Player {
    name: obsidian
    hp:   stone
    speed: crystal
}

También puede declarar un modo de layout explícito: 

monolith Header layout packed {
    tag: stone
    flags: stone
}

Modos de layout soportados actualmente:

  • layout native
  • layout packed
  • layout c

layout packed se reduce a un layout de struct empaquetado de LLVM. layout c se acepta como intención explícita orientada a la ABI y actualmente se reduce igual que native hasta que se amplíe el subsistema completo de ABI/layout.

Creación de instancias

forge hero: Player
hero.name = "Obsidian Knight"
hero.hp = 100
hero.speed = 1.5

Acceso a campos

Use la notación de punto para acceder a los campos: 

echo(hero.name)     // "Obsidian Knight"
echo(hero.hp)       // 100
hero.hp -= 10       // recibe daño

Un campo puede ser otro monolith. El campo guarda una referencia al subobjeto (8 bytes en el layout C); forge c: Cuerpo ya crea el subobjeto en cero, así que c.pos.x = 1 funciona directamente. c.pos = v hace que el campo apunte a v; forge w: Vec3 = c.pos copia. Igual en nativo y en ofs run (prueba: ofs/tests/regress/monolith_nested.ofs).

Paso a funciones

vein greet(p: Player) -> void {
    echo(p.name)
    echo(p.hp)
}

core main() {
    forge hero: Player
    hero.name = "Knight"
    hero.hp = 100
    hero.speed = 1.5
    greet(hero)
}

Punteros (shard / fracture)

Las operaciones con punteros solo están permitidas dentro de bloques fracture (seguro), bedrock (de bajo nivel tipado) o abyss (inseguro).

fracture (bloque de punteros seguro)

core main() {
    forge x: stone = 10

    fracture {
        shard p: *stone = &x   // p apunta a x
        *p = 42                // desreferenciar y asignar
    }

    echo(x)  // prints 42
}

Reglas clave:

  • Los punteros solo pueden crearse y usarse dentro de bloques fracture
  • El compilador verifica los tipos de todas las operaciones con punteros
  • &x toma la dirección de x
  • *p desreferencia el puntero p

Tipos de puntero

shard p: *stone       // puntero a stone (i64*)
shard q: *crystal     // puntero a crystal (f64*)
shard s: *obsidian    // puntero a obsidian (i8**)

bedrock (bloque de bajo nivel tipado)

bedrock es el bloque de bajo nivel nativo de OFS para trabajo tipado cercano a la máquina. 

core main() {
    forge x: stone = 10

    bedrock {
        shard p: *stone = &x
        *p = *p + fault_spin_left(1, 3)
    }

    echo(x)
}

Use bedrock cuando quiera control de bajo nivel e intrínsecos parecidos a los de la máquina, manteniendo las reglas tipadas de OFS.

Colecciones (Arrays)

Literales de array

forge nums = [10, 20, 30, 40, 50]
forge names = ["Alice", "Bob", "Charlie"]

Todos los elementos deben ser del mismo tipo. El tipo del array se infiere a partir de los elementos.

Indexación

forge first = nums[0]    // 10
forge last = nums[4]     // 50
nums[2] = 99             // modificar elemento

La indexación de arrays es basada en cero y con verificación de límites en tiempo de ejecución. Fuera del límite (a[7], ofs_array_get/ofs_array_set), el programa termina con código 1 y ofs: indice 7 fora do limite do array (tamanho 5) en stderr, en los dos modos.

Iteración

// Por rango
cycle (n in nums) {
    echo(n)
}

// Por índice
cycle (forge i = 0; i < 5; i++) {
    echo(nums[i])
}

Memoria insegura (abyss)

El bloque abyss permite operaciones de memoria crudas e inseguras: 

abyss {
    // Raw memory access — no type checking
    // Use with extreme caution
}

Reglas:

  • La verificación de tipos se relaja dentro de los bloques abyss
  • Se permite el direccionamiento directo de memoria
  • Úselo solo cuando sea absolutamente necesario
  • Prefiera fracture para las operaciones con punteros

Alias de directiva: tectonic

Puede usar tectonic como directiva de prefijo para los modos de memoria/efectos. Es una sintaxis alias que se asigna al mismo comportamiento de runtime/semántico:

  • tectonic fracture { ... } -> igual que fracture { ... }
  • tectonic safe { ... } -> igual que fracture { ... }
  • tectonic abyss { ... } -> igual que abyss { ... }
  • tectonic unsafe { ... } -> igual que abyss { ... }
  • tectonic fractal { ... } -> igual que fractal { ... }
  • tectonic bedrock { ... } -> igual que bedrock { ... }

Ejemplo: 

core main() {
    forge x: stone = 10

    tectonic fracture {
        shard p: *stone = &x
        *p = 20
    }

    tectonic safe {
        shard q: *stone = &x
        *q = *q + 1
    }

    tectonic abyss {
        shard raw: *stone = &x
        *raw = *raw + 1
    }

    tectonic unsafe {
        shard raw2: *stone = &x
        *raw2 = *raw2 + 1
    }

    tectonic fractal {
        echo("effect-lifted mode")
    }

    tectonic bedrock {
        shard native: *stone = &x
        *native = *native + 1
    }
}

Intrínsecos fault_*

Dentro de bedrock, fracture o abyss, OFS expone intrínsecos parecidos a los de la máquina con nombres nativos de OFS: 

bedrock {
    forge x: stone = 0xF0F0
    echo(fault_count(x))
    echo(fault_lead(x))
    echo(fault_trail(x))
    echo(fault_swap(x))
    echo(fault_spin_left(x, 4))
    echo(fault_spin_right(x, 4))
    echo(fault_weave(0xFF00, 0xAAAA, 0x5555))
}

Intrínsecos disponibles:

  • fault_count(stone) -> conteo de población (bits a 1)
  • fault_fence() -> emite una barrera de memoria a nivel de máquina
  • fault_prefetch(*stone) -> solicita una captación previa a nivel de máquina para el destino de un puntero
  • fault_trap() -> emite una trampa a nivel de máquina
  • fault_lead(stone) -> cuenta los ceros a la izquierda
  • fault_trail(stone) -> cuenta los ceros a la derecha
  • fault_swap(stone) -> intercambio de bytes
  • fault_spin_left(stone, stone) -> rotación a la izquierda
  • fault_spin_right(stone, stone) -> rotación a la derecha
  • fault_step(*stone, stone) -> avance tipado de punteros en elementos
  • fault_addr(vein) -> dirección de la vein como stone (ver FFI)
  • fault_call(endereco, args...) -> llamada indirecta con ABI de C (ver FFI)
  • fault_cut(value, shift, width) -> extrae un campo de bits
  • fault_patch(base, shift, width, insert) -> reemplaza un campo de bits
  • fault_weave(mask, left, right) -> mezcla bits de left y right usando mask
  • fault_unreachable() -> marca el camino actual como inalcanzable, se reduce a IR llvm.trap + unreachable
  • fault_memcpy(dst, src, len) -> copia de memoria en bloque (se reduce a llvm.memcpy); dst y src deben ser punteros
  • fault_memset(dst, val, len) -> relleno de memoria en bloque con el byte val (se reduce a llvm.memset); dst debe ser un puntero

Semántica exacta (igual en la compilación nativa y en el intérprete ofs run):

  • Todo en 64 bits, complemento a 2: fault_count(-1) = 64; fault_lead(0) = fault_trail(0) = 64; fault_lead(-1) = 0.
  • fault_spin_left/fault_spin_right: rotación de 64 bits (llvm.fshl/llvm.fshr); la distancia se toma módulo 64 (fault_spin_right(6, 65) = 3).
  • fault_weave(mask, left, right) = (left & mask) | (right & ~mask): el bit viene de left donde mask tiene 1 y de right donde tiene 0.
  • fault_trap() y fault_unreachable() terminan el proceso con SIGILL (el intérprete hace lo mismo con raise(SIGILL)).
  • fault_fence()/fault_prefetch() no hacen nada en el intérprete.
  • En el intérprete los punteros son direcciones reales: fault_memcpy/fault_memset copian/rellenan cualquier tamaño, y fault_step, fault_addr y fault_call funcionan como en el nativo (ver "En el intérprete (ofs run): FFI").
  • Prueba: ofs/tests/regress/fault_intrinsics.ofs.

Estas funciones están diseñadas para cubrir operaciones que el ensamblador ya tiene, y al mismo tiempo dar a OFS espacio para su propio vocabulario orientado a la máquina.

asm (escape de ensamblador en línea) — planeado

Estado: planeado. El asm en línea todavía no está disponible: el lexer no reconoce la palabra asm y el backend LLVM no genera InlineAsm. El ejemplo muestra el diseño previsto y no compila hoy. Por ahora use los intrínsecos fault_*.

Cuando ningún intrínseco fault_* cubre su necesidad, asm emitirá una cadena de ensamblador sin procesar directamente en ese punto del código. Solo se permitirá dentro de un bloque bedrock, fracture o abyss. 

bedrock {
    asm "nop"     // planeado
    asm "int3"    // planeado
}

Restricciones:

  • Planeado: el argumento debe ser un literal de cadena.
  • La sintaxis de operandos de entrada/salida (restricciones completas estilo AT&T) todavía no es analizable; use los intrínsecos fault_* cuando necesite enlazar operandos.
  • Planeado: genera una llamada de ensamblador en línea sin valor de retorno en LLVM IR, reenviando la cadena de ensamblador textualmente.
  • Planeado: la expresión asm se reducirá a InlineAsm de LLVM, despachada en el análisis semántico y en la generación de código. Todavía no está implementado.

Lenguaje

OFS: Lenguaje híbrido y compilado nativo

Pregunta esencial: ¿OFS es interpretado o compilado?

Respuesta: OFS es HÍBRIDO — compilación nativa AOT vía LLVM e interpretación directa del AST.

OFS combina lo mejor de los dos paradigmas:

  1. Compilación nativa AOT (`ofs build`): genera representación intermedia LLVM IR directamente con su propio compilador self-hosted (ofscc), emite código de máquina y enlaza ejecutables mediante los linkers nativos del sistema operativo, sin VM y sin intérprete en el binario final.
  2. Ejecución interpretada instantánea (`ofs run` / `ofs <arquivo.ofs>`): ejecuta el árbol sintáctico abstracto (AST) tipado directamente en memoria mediante un intérprete AST integrado escrito en OFS puro (interpreter.ofs), ideal para scripts rápidos, prototipado y validación inmediata.

¿Qué significa el modelo híbrido?

  1. Desarrollo instantáneo: En modo ofs run o ofs arquivo.ofs, el código se ejecuta directamente en memoria sin el retraso de invocar llc y el linker.
  2. Producción nativa sin VM: En modo ofs build, el ejecutable final no incluye ningún intérprete ni máquina virtual; se ejecuta directamente como código de máquina de la CPU (x86_64, ARM64).
  3. Frontend unificado: Tanto el intérprete como el generador LLVM comparten el mismo lexer, el mismo parser y el mismo verificador estático de tipos, lo que garantiza la coherencia semántica.
  4. Self-hosted: Todo el compilador (ofscc), incluyendo el parser, el type checker, el generador LLVM y el intérprete, está escrito en OFS.

strbuf.ofs

Búfer de texto cuya capacidad se duplica al llenarse (anexar es O(1) amortizado). Úselo cuando el texto se arma en muchos pasos o pasa por varias funciones:

  • strbuf.create(capacidad): crea un StrBuf vacío.
  • strbuf.append(b, texto), strbuf.append_char(b, codigo_byte), strbuf.append_int(b, n): anexan al final.
  • strbuf.to_obsidian(b): devuelve una copia del contenido (la cadena no cambia si el búfer sigue creciendo).
  • strbuf.length(b), strbuf.clear(b) (lo vacía y conserva la capacidad), strbuf.release(b) (libera la memoria).
attach {strbuf}

core main() {
    forge b: StrBuf = strbuf.create(64)
    strbuf.append(b, "total: ")
    strbuf.append_int(b, 42)
    echo(strbuf.to_obsidian(b))
    strbuf.release(b)
}

Por ahora solo en código nativo (usa memoria cruda del runtime; ofs run aún no tiene FFI).

Cadenas y memoria. Las cadenas no tienen GC ni conteo de referencias: t = s hace que ambas variables apunten al mismo texto. El compilador nativo solo reutiliza o libera memoria cuando demuestra que nadie más ve el valor: s = s + x / s += x en una variable local que nunca se copia a otro lugar crecen en el lugar; las partes intermedias de a + b + c y un f(a + b) cuyo parámetro no se guarda se liberan; los arrays locales que no escapan se liberan al final de su ámbito. Si la variable se copia, se guarda en un campo/array o se pasa a una función que la guarda, todo funciona como antes (una copia nueva en cada +).

Phase 1: Lexer (Tokenization)

File: ofs/ofscc/lexer.ofs (433 lines)

Input

forge x: stone = 42

Processing

  1. Character classification (chars.ofs):
   is_digit(c), is_alpha(c), is_alnum(c), is_space(c)
  1. Token recognition:
  • Keywords (38): forge, vein, monolith, if, cycle, match/assay, strata, attach, etc.
  • Operators (25+): +, -, *, /, ==, !=, &&, ||, &, |, ^, ~, %, ?, etc.
  • Literals: 42, 3.14, "hello\n", true, false, null
  • Identifiers: x, _var, CamelCase
  • Comments: // and /* */
  1. Multi-character operators:
  • ++ / -- / += / -= / *= /= / == / != / <= / >= / && / || / << / >> / -> / =>

Output

Token { kind: TOK_FORGE, val: "forge", line: 1, col: 1 }
Token { kind: TOK_IDENT, val: "x", line: 1, col: 7 }
Token { kind: TOK_COLON, val: ":", line: 1, col: 8 }

Key Design Decisions

  • No lexer actions — Just tokenize, don't parse yet
  • Line/column tracking — For error messages
  • Escape sequences — \n, \t, \\, \", \r, \0 handled
  • Hex/float literals — 0xFF, 1.0e-5 supported

Phase 2: Parser (AST Construction)

file: ofs/ofscc/parser.ofs (1,246 lines)

Strategy

  1. Recursive Descent for statements + declarations
  2. Pratt Parser for expressions (operator precedence)
  3. Pool-based AST — nodes stored in global Array<Node>

Grammar (Simplified)

program     ::= (fn_decl | monolith_decl | impl_decl | namespace_decl
                | strata_decl | extern_decl | attach_decl | var_decl)*

fn_decl     ::= ("vein" | "core") IDENT "(" params? ")" ("->" type)? block
params      ::= IDENT ":" type ("," IDENT ":" type)*
extern_decl ::= ("extern" | "rift") "vein" IDENT "(" params? ")" ("->" type)?
                ("bind" STRING)? ("abi" IDENT)?
monolith_decl ::= "monolith" IDENT "{" (IDENT ":" type (","|";")?)* "}"
impl_decl   ::= "impl" IDENT "{" fn_decl* "}"
namespace_decl ::= "namespace" IDENT "{" (fn_decl | var_decl | monolith_decl
                | extern_decl | impl_decl | strata_decl)* "}"
strata_decl ::= "strata" IDENT "{" (IDENT ("(" type ")")? (","|";")?)* "}"
attach_decl ::= "attach" "{" path "}"          // e.g. attach {core}, attach {F:lib.ofs}
var_decl    ::= ("forge" | "const" | "shard") IDENT (":" type)? ("=" expr)? ";"?

type        ::= IDENT | "Array" "<" type ">" | "*" type

stmt        ::= var_decl | if_stmt | while_stmt | cycle_stmt | mine_stmt
              | match_stmt | return_stmt | throw_stmt | tremor_stmt
              | anchor_stmt | unsafe_block | block | "break" | "continue"
              | "shatter" | "erode" | expr ";"?
if_stmt     ::= "if" "(" expr ")" block ("else" (if_stmt | block))?
while_stmt  ::= "while" "(" expr ")" block
cycle_stmt  ::= "cycle" "(" IDENT "in" expr ")" block          // over a collection
              | "cycle" "(" "forge" IDENT "in" expr ")" block
              | "cycle" "(" init? ";" expr? ";" expr? ")" block // C style
mine_stmt   ::= "mine" "(" IDENT "in" expr ")" block
match_stmt  ::= ("match" | "assay") "(" expr ")" "{" (pattern "=>" (block | stmt))* "}"
pattern     ::= expr | "_"                                      // "_" is the default case
return_stmt ::= "return" expr? ";"?
throw_stmt  ::= "throw" expr ";"?
tremor_stmt ::= "tremor" block ("catch" "(" IDENT (":" type)? ")" block)?
anchor_stmt ::= "anchor" stmt
unsafe_block::= ("fracture" | "bedrock" | "abyss" | "tectonic") ("fracture"|"bedrock"|"abyss")? block
block       ::= "{" stmt* "}"

expr        ::= unary (binop expr)*         // precedence: see table below
unary       ::= ("-" | "!" | "~" | "&" | "*") postfix(primary)
postfix     ::= primary ( "(" args? ")" | "[" expr "]" | "." IDENT
                        | "++" | "--" | "?" | "as" type )*
primary     ::= IDENT | INT | FLOAT | STRING | "true" | "false" | "null"
              | "(" expr ")" | "[" (expr ("," expr)*)? "]" | "echo" "(" args? ")"

Points the grammar does not show:

  • The parentheses of if, while, match/assay and cycle/mine are required. if x == 1 { } fails with expected '('. The body must be a { } block.
  • The semicolon is optional at the end of statements and declarations. It is only required inside a C-style cycle.
  • assay is just another name for match (same token). match becomes a chain of if comparing with ==; _ is the default case and => separates pattern and body. There are no destructuring patterns.
  • shatter and erode are synonyms of break and continue. mine works like cycle ... in but only accepts the item in collection form.
  • Namespace calls (ns.fn(x)) become the symbol ns__fn. impl methods become Type__method.
  • attach {path} is only valid at file level. The text between the braces is glued token by token (F: marks a file path).
  • There is no struct literal (P { x: 1 }) and no monolith ... layout ...; the parser expects { right after the monolith name. Declare the variable (forge p: P) and assign the fields.
  • core is a reserved word: it marks the entry point (core main()) and cannot be used as a name.

Phase 4A: AST Interpreter Backend (Interpretação Direta)

File: ofs/ofscc/interpreter.ofs (70KB, 2,086 lines)

The OFS interpreter backend runs the typed syntax tree (AST) directly in memory, without generating intermediate files, C code or LLVM IR. It is the default backend used by ofs <file.ofs> and ofs run <file.ofs>.

Interpreter architecture

  1. `Value` system: a universal monolith that unifies scalar values (stone, crystal, obsidian, bool, null) and virtual heap handles for Array<T>, monolith objects and pointers.
  2. Environment and call frames: strict lexical scope based on frame markers (_current_frame_base and _globals_count), so callers' variables do not leak into callees or globals.
  3. Value semantics: forge y: T = x and y = x copy the monolith block (obj_clone()/memcpy into the block y already has, like the native store %T); vein parameters receive the monolith by reference, like the native pointer.
  4. Method dispatch: methods defined in impl Type blocks are resolved automatically, with self injected.
  5. Real pointers (F2): a pointer is an address (VAL_INT with type *T). *p/*p = v use mem_load/mem_store by the memory class of the pointee type (MC_*: width, sign, f32, obsidian, *T, monolith, variant), with the typeck static type precomputed per node in annotate_nodes (the same type llvmgen uses); the load/store is the interpreter's own native code (fracture { *p8 = v as u8 }). &x of a variable turns the entry into VAL_BOXED: the value moves to an 8-byte slot (box_var), read/written by env_load/env_store and freed in env_pop_one (_boxed_live keeps the fast path free when there is none). as mirrors llvmgen's NK_CAST (eval_cast). A monolith lives in raw memory with the llvmgen.struct_layout layout (the same function computes the native ofs_alloc size and the interpreter's offsets; compute_layouts), and VAL_OBJECT holds the block address; an Array field holds the interpreted handle as -(h+1).
  6. Built-ins: direct handling of I/O (echo), strings (ofs_str_*), arrays (ofs_array_*) and math (ofs_pow, ofs_sqrt). The list (is_builtin) is only a fast path, not a limit on what can be called.
  7. FFI (`extern vein`/`rift vein`): at load time (collect_declarations → resolve_calls → ffi_check_symbols), every called extern becomes an address via dlsym(RTLD_DEFAULT, sym) (honoring bind), after opening libm and OFS_FFI_LIBS; a missing symbol is the linker's error (undefined reference), exit code 1. Veins from stdlib/runtime/*.ofs (line ranges marked by expand_attaches through ast_mark_runtime_lines) use the native version linked into ofscc. The call (call_extern) converts arguments by the declared type (integers/pointers/obsidian as i64, crystal as double), stores them in a buffer and calls __ofs_ffi_dispatch, which llvmgen defines inside ofscc itself (emit_ffi_dispatch, when the module declares that extern): a switch with one call of exact LLVM type per signature class (ffi_sig/ffi_sig_supported: up to 4 i64|double args with an i64|double return, up to 12 integer-only, variadics with 1 to 3 fixed + up to 4 extra; 155 cases). That is why ofscc must be linked with -rdynamic (it exports the runtime and the dispatcher to dlsym). In F2, &x, monolith (the block) and Array go to C as addresses: the Array is the interpreter's value column, which already is a native ofs_array (arr_native_ptr), with its length synchronized on return (ffi_sync_arrays); an Array returned by C becomes an interpreted array that uses the same block (arr_adopt). C → OFS callbacks: the module that declares extern vein __ofs_cb_table gets from llvmgen (emit_cb_trampolines) 16 functions __ofs_cb_K(i64 x 6) that call __ofs_cb_enter(K, ...), defined at the end of interpreter.ofs; fault_addr of an interpreted vein binds the vein to a slot (cb_slot_for) and returns the address of __ofs_cb_K (found via dlsym, so an ofscc built by an older compiler still links); cb_enter pushes the arguments by each parameter's type, runs the vein and returns the result as i64, preserving the interpreter registers (re-entrant: it works inside a C call made by the interpreter). Exhausted slots, more than 6 parameters or crystal/f32 in the callback are a clear error (exit code 1).

What is Self-Hosting / Bootstrap?

Bootstrapping occurs when a programming language's compiler compiles its own source code. This milestone formally proves that the language's grammar, type system, and standard library are expressive and robust enough for systems-level development.

  • Lisp (1962): First self-hosting programming language.
  • C (1972): Bootstrapped and established as the systems standard.
  • Rust (2011): Compiler written in Rust.
  • Go (2015): Compiler migrated completely to Go.
  • OFS (2024–2026): Compiler and native runtime self-hosted.

Process Overview

Phase 1: Seed Compiler

The repository provides a pre-compiled native compiler binary in ofs/dist/ (ofs / ofscc) to initiate the build cycle.

Phase 2: Recompilation

The script compiles all compiler source modules (ofs/ofscc/*.ofs) using the existing binary, emitting a fresh compiler executable.

Phase 3: Determinism Verification

The newly generated compiler compiles the compiler source once more. The binary output from pass 2 is compared byte-for-byte with pass 3 (v2 === v3). Identical checksums confirm deterministic build reproducibility.

OFS Performance Analysis

OFS performance work is split between compiler throughput and generated-program runtime.

The main hotspots currently identified are:

  1. substring allocation while materializing tokens;
  2. repeated string concatenation in import expansion and escaping;
  3. linear lookup tables for symbols, fields, variables, and interned strings;
  4. length calls repeated inside loops whose collections do not change.

The public ofs_str_char_at function still validates bounds. The lexer now uses an internal known-length byte read only after checking _pos against _len. In seven-process measurements on June 14, 2026, median IR generation for the small workload moved from 8.11 ms to 7.54 ms. Compiling ofscc.ofs moved from 4,610.40 ms to 3,694.08 ms. Bootstrap stages two and three emitted identical IR.

The planned order is:

  1. repair and expand lexer self-host tests;
  2. add detailed lexer, parser, type-checker, and LLVM IR timing;
  3. benchmark 10 KB, 100 KB, and 1 MB sources;
  4. introduce token slices or a compilation arena;
  5. add a native string builder (strbuf already exists in the stdlib);
  6. measure indexed symbol tables;
  7. evaluate LTO and LLVM flags.

Link and runtime optimization

The distributed runtime is built with -ffunction-sections and -fdata-sections. The launcher enables --gc-sections on ELF, dead_strip on Mach-O, and OPT:REF on PE/COFF so unused runtime functions do not remain in every application.

On the workload published on June 14, 2026, this reduced the OFS executable from 28,224 to 16,056 bytes without changing its checksum. The launcher caches CRT paths and native toolchain binaries (llc and ld) instead of slow filesystem probing on every compilation. Median build time for the same workload moved from 320.81 ms to 208.78 ms on the recorded machine.

These are distribution-pipeline improvements. They do not change syntax, type checking, or program semantics.

Goal

The goal is to reduce concrete compile-time and run-time costs of the compiler and runtime without changing language semantics, compromising memory integrity, or introducing silent regressions. Total build time should stay competitive with equivalent native toolchains by removing redundant work, not by removing language features.

Compilation Flow

OFS source
  -> module resolution and expansion (attach)
  -> lexer
  -> parser
  -> type checker
  -> LLVM IR generation (llvmgen.ofs)
  -> static LLVM compiler (llc -filetype=obj)
  -> native link with the native runtime (ld / ld.lld)
  -> native executable (ELF / Mach-O / PE)

Each stage is measured in isolation: optimizing the generated binary does not necessarily reduce lexer time, and lexer improvements do not change the CPU use of the resulting program.

Hotspots and Optimization Opportunities

1. Character reads in the lexer

ofs_str_char_at checks bounds against the string length. The lexer already tracks _pos against _len, so the ofs_str_char_at_known variant avoids a redundant strlen per character and keeps processing of large sources linear, O(N).

2. Substring allocation

The lexer slices text for identifiers, numbers and literals. The optimized strategy is:

  • keep (start, length) tuples that point into the original file buffer during parsing;
  • materialize heap strings only when a syntax node or the symbol table needs them to persist;
  • use a per-compilation-unit arena allocator, released in one step at the end.

3. String concatenation

Sequential concatenation in loops copies prefixes repeatedly. In the LLVM generator, cg_emit writes straight to the output file and avoids temporary buffers.

4. Symbol tables and scope lookup

Linear symbol lists have good cache locality for small and medium programs. For large code bases, hash tables or scope-indexed structures reduce the lookup cost for variables and types.

Measurement Methodology

  1. A controlled set of lexical and syntactic tests with sources from 10 KB to 1 MB.
  2. Per-phase timing: front end (lexer, parser, types), LLVM IR emission, native link.
  3. Real system metrics via wait4: user CPU time, system time and peak resident memory (RSS).
  4. Strict output checksum verification so no optimization changes semantics.

OES Reference

OES (Obsidian Effect Scripts) is the styling, effects, and animation language of the OFS ecosystem.

You write .oes source files. The oesc tool from the standard library compiles them into standard CSS (ofs run ofs/tools/oesc.ofs, with OESC_INPUT/OESC_OUTPUT), and the browser consumes the resulting stylesheet. OES serves as the design system's source of truth.

gem surface "#120d1f"

  ink "#13071f"
  curve "8px"
  transition "transform .2s ease"

    opacity "0"

Typed Syntax and Explicit Scope

Along with the whitespace-sensitive syntax, typed tokens and scoped blocks can be declared with braces:

Syntax Rules

  • The gem keyword declares reusable design tokens mapped to CSS custom properties (--name: value;).
  • gem name: Type = "value" defines typed design tokens.
  • The paint keyword opens a visual styling block for a selector.
  • Style properties are indented within the paint block.
  • Braces {} and end delimiters provide explicit block scoping.
  • $token references are emitted as var(--token).
  • veil specifies responsive media queries (@media).
  • guard specifies browser feature queries (@supports).
  • strata defines cascade layers (@layer).
  • pulse defines animation timeline keyframes (@keyframes).

OFS Web Stack Architecture

The OFS web stack is structured across three distinct layers:

LayerExtensionPurpose
ODL.odlSemantic document structure and textual content
OES.oesDesign tokens, responsive layout rules, and keyframe animations
OFS.ofsNative processing logic, static page generation, and HTTP serving

ODL and OES are standalone languages compiled by the OFS toolchain, rather than mere aliases for handwritten HTML and CSS. However, standard HTML5 and CSS remain the browser distribution targets.

1. Static Site Generation

The toolchain compiles ODL and OES source files directly into production-ready browser assets: 

ODLC_INPUT=page.odl ODLC_OUTPUT=public/index.html ofs run ofs/tools/odlc.ofs
OESC_INPUT=theme.oes OESC_OUTPUT=public/theme.css ofs run ofs/tools/oesc.ofs

The output can be deployed to standard static hosting providers, such as GitHub Pages, Cloudflare Pages, or traditional web servers (Nginx/Apache).

2. Integrated Native Web Server (webserver)

The standard library provides an HTTP server written in OFS and executed as a standalone binary: 

attach {webserver}

core main() {
    forge body = "<h1>OFS Native Server</h1><p>Running without external runtime dependencies.</p>"
    webserver.serve_html_forever(8080, body)
}

The compiled binary manages network sockets and serves the pre-rendered artifacts on demand.

3. Web Ecosystem Interoperability

The ODL compiler provides explicit directives to interoperate with existing web technologies:

  • mark / markdown: Compiles embedded Markdown into semantic HTML.
  • raw / html: Injects raw HTML fragments without automatic escaping.
  • wire / script: Injects classic JavaScript scripts (<script src="...">).
  • spark / module / node: Injects modern ES modules (<script type="module" src="...">).
  • pulse / js: Embeds inline JavaScript code (<script>...</script>).
  • server / php: Emits server-side processing blocks (<?php ... ?>).
  • raw / css in OES: Injects direct CSS rules for gradual migrations.

4. VS Code Extension and Live Reload (*Go Live*)

The official VS Code extension enables *Go Live* development mode when opening .odl documents or .ofs programs that import webui or webserver.

When *Go Live* is started:

  1. The .odl document is compiled to HTML.
  2. Sibling .oes style files in the directory are compiled to CSS.
  3. A local development HTTP server is initiated.
  4. The server watches .odl, .oes, scripts, and graphical assets, automatically triggering compilation and browser reload via Server-Sent Events (SSE).

5. Browser Compatibility

Web browsers do not execute .odl and .oes files natively. OFS adopts the industry-standard workflow established by TypeScript, JSX, and Sass:

  1. Project source code is authored in .odl and .oes.
  2. Build tools compile the source files into standard HTML5, CSS, and JS.
  3. Hosting providers and browsers receive the compiled artifacts.
  4. For debugging and inspection, the native server exposes text/odl and text/oes MIME types.

6. Current Technical Scope

  • ODL and OES compile whitespace-delimited source code into static markup and stylesheets.
  • Reverse HTML/CSS import tools encapsulate complex legacy blocks into raw directives (raw).
  • Native HTTP routing logic remains separate from document layout definitions.
  • Components are designed for compile-time or bootstrap-time static evaluation.

Architectural Specification — OFS IDLE (Obsidian Integrated Development & Learning Environment)

This document establishes the technical specification for the OFS IDLE: a high-performance integrated development environment matching the ergonomics and layout of Visual Studio Code, authored 100% in Obsidian Fault Script (OFS) and rendered natively via the Obsidian Layout Language (OLL), free of Electron, Chromium, Node.js, or Microsoft proprietary code.

1. Clean-Room Principles

  1. Zero External JS/Electron Dependencies: OFS IDLE is developed completely in OFS syntax (vein, forge, monolith, attach), running atop the native Magma runtime stack (Canvas, Window, OLL, FS).
  2. Industry-Standard Architecture: Ergonomic paradigms (Activity Bar, collapsible tree Sidebar, multi-tab editor groups with numbered gutters, collapsible terminal panel, and status bar) are universal development environment designs.
  3. Native Identity: All visual assets employ official OFS branding and vector iconography.

Herramientas

ODL and OES

ODL (Obsidian Document Language) and OES (Obsidian Effect Scripts) are standalone OFS web languages. They keep the browser output compatible with HTML and CSS, but the authored source uses OFS vocabulary: page, skin, flow, deck, stage, band, gem, paint, veil, and pulse.

The OFS toolchain compiles them natively. Browsers receive generated HTML, CSS, and JavaScript artifacts.

Hosting

Generated artifacts can be hosted by GitHub Pages, any static host, Node, PHP, or the OFS native web server. The VS Code extension recognizes .odl as a site document and its Go Live command compiles neighboring .oes files before starting a local preview with automatic reload.

When publishing to GitHub Pages, keep the generated index.html and site.css at the public root. If you want the authored language available too, copy the sources into a non-executed folder such as source/page.odl and source/site.oes. They are served as source files and do not interfere with the browser artifact.

  • Fase 4: Codegen — Emite código C válido
  • Fase 5: Compilación C — Invoca gcc -O2
  • Fase 6: Salida — Ejecutable nativo

Características soportadas:

  • Todos los tipos primitivos (stone, crystal, obsidian, bool, u8-u64, i32)
  • Funciones, variables, constantes
  • Arrays, monoliths (structs)
  • Control de flujo (if/else, while, cycle, match, break, continue, return)
  • Operadores (aritméticos, lógicos, a nivel de bits, comparación)
  • Literales de cadena con secuencias de escape
  • Comentarios (//, /* */)
  • Inferencia de tipos (básica)
  • Mensajes de error (simples)

Limitaciones (abordadas en v1.2):

  • Análisis de argumentos de línea de comandos
  • impl/namespace/strata (solo parseo)
  • Recuperación completa de errores
  • Diagnósticos más allá de stderr

[1.0.148] - 2026-09-30 — Backend de intérprete híbrido y pruebas diferenciales

Added

  • Backend de intérprete AST (`interpreter.ofs`): OFS es ahora un lenguaje híbrido real. Ejecutar ofs <file.ofs> o ofs run <file.ofs> evalúa directamente el AST tipado sin invocar las fases de LLVM, Clang o el linker, ofreciendo ejecución en sub-milisegundos para scripting y prototipado.
  • Value Monolith y heap dinámico: soporte completo en runtime para primitivos (stone, crystal, obsidian, bool), manejadores para Array<T>, structs monolith en heap con semántica de copia por valor, y punteros con la tabla Location.
  • Ámbito lexico de marcos de llamada: seguimiento de la base del marco (_current_frame_base y _globals_count) que garantiza que las variables locales de las funciones llamadoras nunca se filtren ni oculten las declaraciones globales de las funciones llamadas.
  • Despacho de métodos mediante `impl`: soporte para métodos declarados en impl Type { vein method(self: Type) ... } llamados directamente sobre instancias (instance.method()).
  • Suite de pruebas diferenciales: ejecutor automático ofs/tests/interpreter/test_differential.sh con 9 suites de prueba de extremo a extremo que verifican la equivalencia 1 a 1 de la salida entre el modo interpretado y los builds nativos de LLVM.
  • Integración CI: validación de pruebas diferenciales añadida a los flujos de GitHub Actions en Linux y macOS.

Changed

  • ofs run <file.ofs> ejecuta por defecto de forma interpretada e instantánea; ofs run --native <file.ofs> está disponible para compilación temporal + ejecución.
  • El ejecutor de PowerShell para Windows src/packaging/windows/ofs.ps1 se actualizó con el modo interpretado y el flag --native para la paridad completa entre Linux, macOS y Windows.
