Guia de Introdução ao OFS

O OFS (Obsidian Fault Script) é uma linguagem de programação híbrida, self-hosted, que conta com um interpretador AST integrado para execução instantânea (ofs run) e um backend LLVM para geração de executáveis binários nativos de alta performance (ofs build).

O ecossistema inclui compilador, biblioteca padrão, ferramentas de linha de comando e as linguagens de domínio web ODL e OES.

1. Instalação

Pacotes pré-compilados

Instaladores oficiais estão disponíveis para diversas distribuições e sistemas operacionais:

  • Debian / Ubuntu:
  sudo dpkg -i ofs-debian-ubuntu-x64-installer-v*.deb
  • Fedora / RHEL / openSUSE:
  sudo rpm -Uvh ofs-fedora-x64-installer-v*.rpm
  • Arch / Manjaro:
  sudo pacman -U ofs-arch-x64-installer-v*.pkg.tar.zst
  • macOS (Apple Silicon / ARM64):
  • Execute o script instalador fornecido no release do GitHub.
  • Windows (x64):
  • Execute o instalador ofs-windows-x64-installer-v*.exe.
  • VS Code:
  • Instale a extensão oficial ofs-vscode-extension.vsix para suporte a sintaxe, realce e recarregamento dinâmico (*Go Live*).

Compilação a partir do código-fonte (Bootstrap)

Para compilar o compilador diretamente a partir do repositório: 

git clone https://github.com/Samwns/Obsidian-Fault-Script.git
cd Obsidian-Fault-Script
bash ofs/bootstrap/scripts/bootstrap-minimal.sh

O binário do compilador será gerado em ofs/dist/ofs (ou ofs/dist/ofscc).

Termux (Android)

O OFS roda no próprio celular, dentro do Termux (aarch64).

Instalar (no Termux): 

curl -fsSL https://raw.githubusercontent.com/Samwns/Obsidian-Fault-Script/main/src/packaging/termux/install_termux.sh | bash
# ou, com o pacote local:  bash install_termux.sh ofs-termux-aarch64.tar.gz

O instalador roda pkg install -y clang, baixa a última release ofs-termux-aarch64.tar.gz, extrai em $PREFIX (bin/ofs e lib/ofs/) e testa ofs --version.

Usar: ofs run hello.ofs (interpretado), ofs build hello.ofs -o hello && ./hello (nativo aarch64, liga com o clang do Termux). As ferramentas ficam em $PREFIX/lib/ofs/tools/ (ofs run $PREFIX/lib/ofs/tools/odlc.ofs).

Limitações: sem janelas X11 por enquanto (.oll/.oal em janela); gerar APK no celular (ofs build --target android) fica para depois.

3. Primeiro Programa

Crie um arquivo chamado hello.ofs: 

core main() {
    echo("Olá, Mundo via OFS!")
}

Execução direta no interpretador AST: 

ofs hello.ofs
# ou: ofs run hello.ofs

Ou compilação para executável binário nativo: 

ofs build hello.ofs -o hello
./hello

Saída: 

Olá, Mundo via OFS!

4. Tipos de Dados

OFS é estaticamente tipado. O compilador oferece inferência de tipos em declarações de variáveis locais (forge).

Tipos fundamentais

  • stone: Inteiro de 64 bits com sinal.
  • crystal: Ponto flutuante de 64 bits (IEEE 754).
  • obsidian: Sequência de caracteres UTF-8 (*string*).
  • bool: Booleano (true ou false).
  • void: Ausência de valor de retorno.

Inteiros de largura fixa

  • Sem sinal: u8, u16, u32, u64
  • Com sinal: i8, i32

Exemplo de declaração e conversão explícita: 

core main() {
    forge contador: stone = 10
    forge taxa: crystal = 3.14159
    forge ativo: bool = true
    forge nome: obsidian = "Obsidian"

    forge canal_r: u8 = 255
    forge canal_g: u8 = 128
    forge pixel: u32 = (canal_r as u32 << 16) | (canal_g as u32 << 8)

    echo(nome)
    echo(pixel)
}

5. Funções

Funções são definidas com a palavra-chave vein. O ponto de entrada nativo do programa é a função core main(). 

vein somar(a: stone, b: stone) -> stone {
    return a + b
}

vein fatorial(n: stone) -> stone {
    if (n <= 1) {
        return 1
    }
    return n * fatorial(n - 1)
}

core main() {
    forge s = somar(15, 27)
    forge f = fatorial(5)
    echo(s)
    echo(f)
}

Funções podem compor chamadas entre si e invocar outras rotinas: 

vein quadrado(n: stone) -> stone {
    return n * n
}

vein soma_quadrados(a: stone, b: stone) -> stone {
    return quadrado(a) + quadrado(b)
}

core main() {
    echo(soma_quadrados(3, 4))
}

Nota: Expressões anônimas (*lambdas*) estão especificadas na árvore sintática (NK_LAMBDA) e em planejamento no roadmap da linguagem. Atualmente todas as funções devem ser nomeadas com vein.

6. Estruturas de Dados (monolith)

OFS utiliza a palavra-chave monolith para definir tipos compostos e blocos impl para associar métodos: 

monolith Retangulo {
    largura: stone
    altura: stone
}

impl Retangulo {
    vein area(self: Retangulo) -> stone {
        return self.largura * self.altura
    }

    vein perimetro(self: Retangulo) -> stone {
        return (self.largura + self.altura) * 2
    }
}

core main() {
    forge r: Retangulo
    r.largura = 10
    r.altura = 5

    echo(r.area())
    echo(r.perimetro())
}

7. Módulos e Importações (attach)

A declaração attach importa módulos da biblioteca padrão instalada ou arquivos locais: 

attach {math}
attach {string}
attach {io}

Para importar arquivos locais relativos ou absolutos, utilize o prefixo F:: 

attach {F:./modulos/auxiliar.ofs}

8. Controle de Fluxo

Condicionais (if / else)

core main() {
    forge x: stone = 10
    if (x > 0) {
        echo("positivo")
    } else if (x < 0) {
        echo("negativo")
    } else {
        echo("zero")
    }
}

Laços de repetição (while)

core main() {
    forge i: stone = 0
    while (i < 5) {
        echo(i)
        i = i + 1
    }
}

Seleção de múltiplos caminhos

Ramificações com múltiplas condições utilizam if / else if / else: 

core main() {
    forge status_code = 200
    if (status_code == 200) {
        echo("Sucesso")
    } else if (status_code == 404) {
        echo("Não encontrado")
    } else {
        echo("Outro código")
    }
}

Nota: O construto match está reservado na especificação da AST (NK_MATCH) e no lexer, com parser e desvio dedicados planejados no roadmap.

Tratamento e validação de erros (throw)

A instrução throw exibe uma mensagem de falha e encerra o processo com código de erro 1: 

vein dividir(dividendo: stone, divisor: stone) -> stone {
    if (divisor == 0) {
        throw "Divisão por zero inválida"
    }
    return dividendo / divisor
}

core main() {
    echo(dividir(10, 2))
}

Nota: A estrutura tremor { ... } catch (...) { ... } está modelada na gramática (NK_TREMOR), com desbobinamento estruturado previsto para as próximas etapas de runtime e interpretador.

9. O Rift: bibliotecas nativas do sistema (rift / extern vein)

O Rift (a fenda) é a fronteira por onde o OFS alcança as bibliotecas nativas do sistema (libc, libm, X11, JNI do Android, kernel32). rift vein e extern vein declaram uma função que mora numa biblioteca nativa, e ela é chamada pela convenção de chamada do sistema. Não há código C no OFS: o compilador e o runtime são escritos em OFS.

A convenção de chamada do sistema é conhecida tecnicamente como ABI C (abi c); não envolve código C. 

extern vein puts(s: obsidian) -> stone
rift vein strlen(s: obsidian) -> stone bind "strlen" abi c

core main() {
    puts("Mensagem enviada via puts da libc")
}

10. Stack Web: ODL e OES

O ecossistema OFS possui duas linguagens de domínio específico (DSLs) dedicadas à construção de interfaces web estáticas e dinâmicas:

ODL (Obsidian Document Language)

Estrutura semântica para documentos web compilada para HTML5: 

page "Aplicação OFS" "pt"
skin "estilo.css"

flow
  deck.navegacao
    title1 "Título Principal"
    link.botao "Documentação" "#docs"
  stage#conteudo
    band.artigo
      mark "## Conteúdo nativo\nTexto formatado em **Markdown**."
      raw "<div class=\"custom\">HTML bruto quando necessário</div>"
  spark "app.js"

Compilação do ODL (a ferramenta odlc faz parte da biblioteca padrão de ferramentas e roda com o próprio ofs): 

# no repositório OFS (ou com as tools instaladas em /usr/share/ofs/tools)
ODLC_INPUT=documento.odl ODLC_OUTPUT=public/index.html ofs run ofs/tools/odlc.ofs

OES (Obsidian Effect Scripts)

Definição de estilos, variáveis, regras responsivas e animações compilada para CSS: 

gem primario "#5b34ea"
gem fundo "#120e24"

paint .botao
  fill "$primario"
  curve "6px"
  space "8px 16px"
  edge "none"

veil "(max-width: 768px)"
  paint .grade
    grid-cols "1fr"

pulse "surgir"
  rise
    opacity "0"
  rest
    opacity "1"

Compilação do OES (mesmo padrão, usando a ferramenta oesc): 

OESC_INPUT=estilo.oes OESC_OUTPUT=public/estilo.css ofs run ofs/tools/oesc.ofs

Servidor HTTP nativo (webserver)

A biblioteca padrão fornece um servidor HTTP nativo integrado ao runtime: 

attach {webserver}

core main() {
    forge html = "<h1>Servidor Nativo OFS</h1><p>Executando sem dependências externas.</p>"
    webserver.serve_html_forever(8080, html)
}

11. Recursos de Baixo Nível

OFS suporta manipulação direta de memória e contextos específicos quando necessário:

  • fracture { ... }: Bloco com contexto de ponteiros tipados.
  • abyss { ... }: Fronteira explícita para operações de baixo nível de máquina.
  • bedrock: Biblioteca padrão para alocações explícitas de células e regiões de memória.
attach {bedrock}

core main() {
    forge celula = bedrock_cell_new(42)
    echo(bedrock_cell_read(celula))
    bedrock_cell_drop(celula)
}

OFS — Jornada do Iniciante

Guia prático para aprender Obsidian Fault Script (OFS) por etapas graduais, do básico até a manipulação de estruturas, coleções e módulos.

Como Utilizar este Guia

  1. Estude um módulo de cada vez.
  2. Execute o código no terminal com ofs run arquivo.ofs (ou compile com ofs build arquivo.ofs -o programa).
  3. Modifique os valores para testar o comportamento.
  4. Avance apenas após compreender os resultados impressos no terminal.

Módulo 1: Primeiros Valores e Variáveis

Objetivo: Compreender a função core main(), a declaração de variáveis com forge, a saída no terminal com echo() e os tipos primitivos fundamentais. 

core main() {
    forge nome: obsidian = "Ana"
    forge idade: stone = 19
    forge peso: crystal = 55.7
    forge ativo: bool = true

    echo(nome)
    echo(idade)
    echo(peso)
    echo(ativo)
}

Desafio: Adicione variáveis para armazenar uma cidade (obsidian) e uma taxa (crystal).

Módulo 2: Decisão e Laços de Repetição

Objetivo: Utilizar condicionais (if / else) e laços de repetição (while). 

core main() {
    forge energia: stone = 3

    while (energia > 0) {
        echo(energia)
        energia = energia - 1
    }

    if (energia == 0) {
        echo("Recarga necessária")
    }
}

Desafio: Crie um laço que realize uma contagem regressiva de 5 a 1 e exiba "Decolagem".

Módulo 3: Funções (vein)

Objetivo: Estruturar e reutilizar código com funções declaradas pela palavra-chave vein. 

vein dobro(n: stone) -> stone {
    return n * 2
}

vein somar(a: stone, b: stone) -> stone {
    return a + b
}

core main() {
    echo(dobro(21))
    echo(somar(10, 32))
}

Desafio: Escreva uma função media(a: stone, b: stone) -> stone que retorne a média aritmética inteira de dois números.

Módulo 4: Tipos Inteiros de Largura Fixa

Objetivo: Manipulação de bytes e inteiros com sinal e sem sinal (u8, u16, u32, i8, i32). 

core main() {
    forge canal_r: u8 = 255
    forge canal_g: u8 = 128
    forge canal_b: u8 = 0

    forge pixel: u32 = (canal_r as u32 << 16) | (canal_g as u32 << 8) | (canal_b as u32)
    echo(pixel)
}

Desafio: Isole o canal verde (canal_g) de volta a partir de pixel utilizando deslocamento de bits e máscara (& 0xFF).

Módulo 5: Estruturas de Dados (monolith) e Métodos (impl)

Objetivo: Modelar tipos compostos e encapsular operações com monolith e impl. 

monolith Retangulo {
    largura: stone
    altura: stone
}

impl Retangulo {
    vein area(self: Retangulo) -> stone {
        return self.largura * self.altura
    }

    vein perimetro(self: Retangulo) -> stone {
        return (self.largura + self.altura) * 2
    }
}

core main() {
    forge r: Retangulo
    r.largura = 10
    r.altura = 20

    echo(r.area())
    echo(r.perimetro())
}

Desafio: Crie um método eh_quadrado(self: Retangulo) -> bool que retorne verdadeiro caso largura e altura sejam idênticas.

Módulo 6: Espaços de Nomes (namespace)

Objetivo: Agrupar funções e constantes relacionadas para manter o escopo global organizado. 

namespace calculo {
    vein quadrado(x: stone) -> stone {
        return x * x
    }

    vein cubo(x: stone) -> stone {
        return x * x * x
    }
}

core main() {
    echo(calculo.quadrado(5))
    echo(calculo.cubo(3))
}

Módulo 7: Módulos Externos com attach

Objetivo: Dividir código em múltiplos arquivos e importar funções.

Arquivo auxiliar auxiliar.ofs: 

vein saudacao(nome: obsidian) -> obsidian {
    return "Olá, " + nome + "!"
}

Arquivo principal main.ofs: 

attach {F:./auxiliar.ofs}

core main() {
    echo(saudacao("OFS"))
}

Módulo 8: Vetores e Coleções (Array<T>)

Objetivo: Armazenar coleções sequenciais homogêneas, acessar e alterar elementos por índice e consultar o tamanho do vetor. 

core main() {
    forge notas: Array<stone> = [85, 92, 78]
    echo(notas[0])

    notas[1] = 95
    echo(notas[1])
    echo(ofs_array_len(notas))
}

Desafio: Crie um array com 4 números e calcule a soma total de seus elementos usando um laço.

Módulo 9: Laços Estruturados (cycle)

Objetivo: Iterar de forma limpa utilizando laços indexados estilo C e iteração sobre coleções. 

core main() {
    cycle (forge i = 0; i < 5; i++) {
        echo(i)
    }

    forge itens: Array<stone> = [10, 20, 30]
    cycle (valor in itens) {
        echo(valor)
    }
}

Desafio: Utilize cycle (item in lista) para contar quantos números em um array são maiores que 15.

1. Estrutura de programa

Todo programa executável precisa de um core main(): 

core main() {
    echo("inicio")
}

core é palavra reservada: só marca o ponto de entrada. Usá-la como nome (vein core(), core(1), inclusive dentro de namespace) é erro de compilação ("core e palavra reservada…"); renomeie a função (ex.: core_fn). Qualquer erro sintático encerra a compilação com código 1.

Um arquivo .ofs pode conter:

  • attach { ... }
  • extern vein e rift vein
  • vein e core
  • monolith
  • impl
  • namespace
  • strata
  • forge global

Comentários

// Comentário de uma linha

/* Comentário
   de várias linhas */

forge x = 42  // comentário no fim da linha

Terminação de instruções

Instruções terminam com quebra de linha ou ponto e vírgula. Quebras de linha dentro de (), [] e {} são ignoradas (continuação implícita). 

forge x = 10; forge y = 20

forge resultado = soma(
    10,
    20
)

Avisos (não barram o programa)

[AVISO DE TIPO] aparece quando um valor é guardado num tipo sem conversão definida, por exemplo forge x: stone = "abc" ou forge c: crystal = true. Nesses casos o nativo reinterpreta os bits (ou o endereço) e o interpretador guarda o valor como está. Isso continua aviso porque código de baixo nível às vezes quer exatamente essa reinterpretação: use as T para deixar a intenção explícita.

Quando o typeck não sabe o tipo de um lado (chamada sem assinatura conhecida, por exemplo), ele não converte nem acusa erro.

Variantes no `echo`: echo(v) de uma variante (tipo strata ou literal Verde) imprime o nome nos dois modos. A etiqueta numérica sai com v as stone.

Propagação ?

expr? desembrulha uma variante de resultado:

  • Solid(v)? e Ore(v)? valem v.
  • Crack(e)? e Barren? saem da vein atual na hora (os anchor pendentes rodam), propagando a falha. As variantes de falha são as de nome Crack e Barren; qualquer outra conta como sucesso.

O valor devolvido pela propagação é igual nos dois modos:

  • No build nativo variantes são etiquetas i64 sem payload: a etiqueta é a posição da variante na ordem de declaração de todas as strata do programa (com strata Outcome { Solid, Crack } declarada primeiro, Crack = 1). Uma vein ... -> stone que propaga Crack devolve essa etiqueta, e echo imprime 1 nos dois modos. Com retorno obsidian vem o texto da etiqueta; com crystal, o número; em core main vira o código de saída.
  • No interpretador, se o retorno declarado for o próprio tipo strata (-> Outcome), a variante é devolvida inteira (com payload).
  • Como o nativo não guarda payload, x? sobre uma expressão que não é um construtor direto (ex.: f()?) vale a etiqueta da variante de sucesso, não o payload.
strata Outcome { Solid, Crack }

vein ok() -> stone {
    forge v = Solid(7)?      // 7
    return v
}

vein bad() -> stone {
    forge v = Crack("boom")? // sai aqui devolvendo 1
    return v
}

core main() {
    echo(ok())   // 7
    echo(bad())  // 1
}

Teste: ofs/tests/regress/question_propagation.ofs.

break e continue

cycle (forge i = 0; i < 100; i++) {
    if (i == 50) {
        break       // sai do laço
    }
    if (i % 2 == 0) {
        continue    // pula números pares
    }
    echo(i)
}

break e continue funcionam em cycle e em while. while é açúcar sintático para um cycle só com condição.

seal e anchor (rodar ao sair do escopo)

seal { … } e anchor { … } são a mesma coisa (o mesmo token): registram uma ação que roda quando o escopo atual termina, em qualquer saída (fim do bloco, return, break/shatter, continue/erode, propagação ?). Várias ações rodam em ordem inversa (a última registrada roda primeiro). seal é o nome temático ("sela o recurso ao sair"); anchor continua valendo. Aceitam um bloco ou um comando só. 

vein copiar(origem: obsidian) -> stone {
    forge f = fopen(origem, "r")
    seal { fclose(f) }          // roda em qualquer return abaixo
    anchor echo("fim de copiar") // igual a seal; roda antes do fclose (LIFO)
    if (f == null) { return 1 }
    // ...
    return 0
}
  • A ação é avaliada na saída, com os valores daquele momento.
  • return, break, continue e throw dentro de seal/anchor são proibidos (erro E0042).
  • Funciona igual no nativo e no ofs run. Teste: ofs/tests/regress/seal_defer.ofs.

11. extern vein e rift vein

O Rift (a fenda) é a fronteira por onde o OFS alcança as bibliotecas nativas do sistema (libc, libm, X11, JNI do Android, kernel32). extern vein/rift vein declaram uma função que mora numa biblioteca nativa. Não há código C no OFS. (A convenção de chamada do sistema é conhecida tecnicamente como ABI C; não envolve código C.)

extern vein

extern vein puts(s: obsidian) -> stone

rift vein

rift vein ofs_window_create(title: obsidian, w: stone, h: stone) -> void abi c

Metadados de link

rift vein text_size(s: obsidian) -> stone bind "strlen" abi c

Endereço de função e chamada indireta (fault_addr, fault_call)

O OFS não tem tipo "ponteiro de função", mas pode obter o endereço de uma vein como stone e chamar um endereço pela convenção de chamada do sistema. Serve para callbacks de bibliotecas nativas (qsort, ANativeActivity, ALooper, AChoreographer) e para tabelas de funções nativas (JNI). 

rift vein c_qsort(base: *stone, n: stone, size: stone, cmp: stone) -> void bind "qsort" abi c

vein crescente(a: *stone, b: *stone) -> stone {
    forge x = 0
    forge y = 0
    fracture { x = *a; y = *b; }
    if (x < y) { return -1 }
    if (x > y) { return 1 }
    return 0
}

core main() {
    forge buf = ofs_alloc(64)
    // ...preenche 8 valores...
    abyss {
        c_qsort(buf, 8, 8, fault_addr(crescente))
        forge r = fault_call(fault_addr(crescente), buf, fault_step(buf, 1))
    }
}
  • fault_addr(nome) → stone: endereço da vein. Aceita vein do módulo, ns.vein e extern/rift vein (com bind, devolve o símbolo nativo). Em IR: ptrtoint ptr @simbolo to i64. Fora de uma vein, é erro semântico.
  • fault_call(endereco, args...) → stone: chamada indireta pela convenção de chamada do sistema (inttoptr + call i64). Argumentos inteiros, ponteiros e obsidian; o retorno é lido como i64 (funções void devolvem lixo, ignore). Sem float/double.
  • A vein usada como callback deve ter parâmetros compatíveis com a convenção de chamada do sistema: stone para inteiros (inteiros de 32 bits chegam com o topo indefinido; mascare com & 4294967295) e *stone para ponteiros.
  • No interpretador (ofs run), fault_addr de extern/rift vein devolve o endereço nativo e fault_addr de uma vein interpretada devolve um trampolim nativo que reentra no interpretador (o qsort acima funciona igual). Ver "No interpretador (ofs run): o Rift".
  • Teste: ofs/tests/runtime/test_fault_addr_qsort.ofs.

Campos importantes:

  • bind "..." define o símbolo nativo real
  • abi c seleciona a convenção de chamada do sistema
  • ... é aceito em função variádica nativa

No interpretador (ofs run): o Rift

O ofs run chama as mesmas funções nativas das bibliotecas do sistema que o build nativo ligaria, sem código C e sem libffi:

  • Resolução no carregamento. Cada extern vein/rift vein chamada no programa (ou passada a fault_addr) vira um endereço com dlsym(RTLD_DEFAULT, "símbolo"), usando o bind quando houver. Antes, o interpretador abre a libm (o build liga -lm) e as bibliotecas de OFS_FFI_LIBS (libfoo.so:/caminho/libbar.so); se algum símbolo faltar, tenta também libX11/libXft (o ofs build liga as duas quando existem). Símbolo ausente dá o mesmo erro do linker (undefined reference to 'x') antes de rodar, com código de saída 1. Uma extern declarada e nunca chamada não precisa existir (como no link).
  • Runtime OFS. O ofscc é linkado com -rdynamic, então ofs_alloc, ofs_echo_color etc. também são achados. As veins definidas em stdlib/runtime/*.ofs (anexadas com attach) rodam na versão nativa linkada no ofscc, como os builtins, quando a assinatura cabe no Rift; OFS_RUN_RUNTIME=interp desliga isso.
  • Conversão. stone, bool, inteiros (i8..u64, ajustados à largura e ao sinal), ponteiros e obsidian (o char* do próprio valor) vão como i64; crystal vai em registrador FP. O retorno segue o tipo declarado: char* vira obsidian sem cópia (como no nativo, onde obsidian é o ponteiro; NULL vira null), *T vira o endereço (pode voltar à função nativa, ser comparado com null, convertido com as e desreferenciado), monolith o bloco e Array o próprio ofs_array.
  • Trampolins. A chamada passa por __ofs_ffi_dispatch, gerada pelo llvmgen no próprio ofscc: um caso de tipo LLVM exato por classe de assinatura (até 4 argumentos com qualquer mistura stone/crystal e retorno inteiro ou crystal; até 12 só inteiros; variádicas com 1 a 3 fixos e até 4 extras). Classe fora disso é erro claro.
  • Variádicas (printf, snprintf, open...): as mesmas que o llvmgen conhece por nome; os extras vão no tipo declarado (ou no tipo do valor), com a convenção correta (%al no x86-64).
  • fault_addr(extern) devolve o endereço nativo e fault_call(endereco, ...) chama com os argumentos no tipo do valor (como no nativo). fault_step(p, i) soma i * sizeof(*p) com o tipo estático de p, como o getelementptr do nativo.
  • Memória crua (F2). O interpretador roda nativo, então ponteiro é endereço real. *p e *p = v leem e escrevem pela largura do tipo apontado (u8/i8/u16/i16/u32/i32/u64/i64/stone/f32/f64/crystal/bool (4 bytes)/obsidian/*T), com o tipo estático do typeck (o mesmo que o llvmgen usa); inteiros estreitos ficam com sinal estendido (iN) ou zeros (uN), como no nativo. p nulo falha como no nativo (endereço 0). fault_memcpy/fault_memset usam memcpy/memset de verdade, de qualquer tamanho.
  • `as` segue a regra do llvmgen: mesmo tipo LLVM só troca o tipo; ptrtoint/inttoptr (incluindo obsidian, que é o próprio char*); fptosi; sitofp de iN/stone e uitofp de uN ((255 as u8) as crystal dá 255.0); fpext/fptrunc (f32 arredonda); trunc se a origem é mais larga, senão sext de iN e zext de uN/bool ((0 - 1) as i8 as stone dá -1). forge x: u8 = 300 e x = v num u8/i32/f32 truncam como o store do nativo.
  • `&x`. O endereço de uma variável do interpretador é real: no primeiro &x a variável passa a morar num slot de memória crua de 8 bytes (a função nativa pode ler e escrever nele: sscanf(s, "%d", &n), strtol(s, &fim, 10), modf(x, &inteira)), liberado quando a variável sai de escopo, como a alloca do nativo. &x de um monolith é o próprio bloco. Só existe endereço de variável (o nativo também não tem &s.campo/&a[i]: use (&s) as stone + offset); &x de uma variável Array é erro claro.
  • `monolith` com layout do sistema. As instâncias vivem em memória crua com o layout de llvmgen.struct_layout (o mesmo do código nativo: campos na ordem, cada um alinhado ao próprio tamanho, até 8; bool ocupa 4 bytes; Array e monolith aninhado ocupam 8). s ou &s passado à função nativa (memcpy, qsort de structs...) vê os mesmos bytes do build nativo. Como no nativo, monolith passado a uma vein é por referência e forge y: T = x/y = x copiam. Um campo Array guarda o array do interpretador (a função nativa não deve lê-lo).
  • `Array` e strings. Um Array passado à função nativa é o próprio ofs_array nativo (cabeçalho [data, len, cap, elem_size] + dados) da coluna de valores do interpretador; a função nativa escreve nos elementos no lugar e o comprimento é sincronizado na volta. Elementos de um só tipo (inteiros/ponteiros, crystal, bool, obsidian ou monolith); tipos misturados são erro claro. Um Array devolvido pela função nativa usa o mesmo bloco, sem cópia. obsidian já é o char*. Use ofs_array_data(a) para passar só os dados (ex.: qsort).
  • Callbacks nativos → OFS. fault_addr(vein) de uma vein interpretada liga a vein a um de 16 trampolins nativos (__ofs_cb_0..__ofs_cb_15, gerados pelo llvmgen no ofscc); a biblioteca chama o trampolim, que reentra no interpretador, inclusive dentro de uma chamada nativa feita pelo próprio programa (qsort dentro de qsort, fault_call de outro callback). A mesma vein reusa o slot. Até 6 parâmetros inteiros, ponteiros, obsidian, bool ou monolith (por ponteiro) e retorno inteiro/ponteiro. Mais de 16 veins diferentes, mais de 6 parâmetros ou crystal/f32 no callback dão erro claro com código 1 (use ofs run --native). f32 como argumento do Rift também ainda não é suportado.
  • bedrock, fracture e abyss não mudam a execução nos dois modos (o nativo gera o mesmo código dentro deles); o typeck os exige para as operações de memória crua (ver seção 12, "Regras"). As células e regiões do bedrock (stdlib) usam a memória crua acima.
  • Testes: ofs/tests/regress/ffi_*.ofs, ptr_widths.ofs, tests/parity/cases/ (ptr_*, libc_*, monolith_memcpy, qsort_fault_addr, fault_call_basic, bedrock_block).

Direção da interoperabilidade

extern vein é a superfície atual do Rift, mais adequada a símbolos de runtime e bibliotecas nativas do sistema. O roadmap amplia isso para: fronteiras com objetos e bibliotecas nativas, pontes para outros ecossistemas, embedding de Python e escapes de assembly específicos do destino. Esses itens são roadmap, não recursos implementados hoje.

Padrão híbrido

É válido e recomendado misturar alto e baixo nível no mesmo arquivo:

  • lógica de negócio em vein comuns;
  • chamada de bibliotecas nativas pelo Rift (rift vein);
  • trabalho próximo à máquina em bedrock;
  • armazenamento explícito com bedrock.ofs.

Regras de fracture, bedrock, tectonic e abyss (F4)

O typeck exige um bloco de baixo nível para as operações que mexem em memória crua. A regra vale igual no ofs build e no ofs run (vem do typeck):

  • Continuam livres fora de bloco: chamar extern/rift vein (mesmo com ponteiro como argumento ou retorno, ex. forge buf = ofs_alloc(64)), comparar ponteiro com null, guardar e passar ponteiro adiante, e os intrínsecos de bits (fault_count, fault_cut, fault_weave...).
  • tectonic X vale como X (tectonic abyss { } = abyss); tectonic { } sozinho vale como fracture. Blocos aninhados somam: dentro de abyss, tudo é liberado.

Intrínsecos fault_*

Os de bits valem em qualquer lugar; fault_step, fault_memcpy e fault_memset pedem fracture/bedrock/abyss, e fault_addr/fault_call pedem abyss (tabela acima):

  • fault_count(stone) → contagem de bits 1 (popcount)
  • fault_fence() → barreira de memória
  • fault_prefetch(*stone) → pré-busca de memória para o alvo do ponteiro
  • fault_trap() → armadilha (trap) da máquina
  • fault_lead(stone) → zeros à esquerda
  • fault_trail(stone) → zeros à direita
  • fault_swap(stone) → troca de bytes
  • fault_spin_left(stone, stone) / fault_spin_right(stone, stone) → rotação de bits
  • fault_step(*stone, stone) → avanço de ponteiro tipado, em elementos
  • fault_addr(vein) → endereço da vein como stone (ver seção 11)
  • fault_call(endereco, args...) → chamada indireta pela convenção de chamada do sistema (ver seção 11)
  • fault_cut(value, shift, width) → extrai um campo de bits
  • fault_patch(base, shift, width, insert) → substitui um campo de bits
  • fault_weave(mask, left, right) → mistura bits de left e right conforme mask
  • fault_unreachable() → marca o caminho como inalcançável (gera llvm.trap + unreachable)
  • fault_memcpy(dst, src, len) → cópia de memória em bloco (llvm.memcpy); dst e src são ponteiros
  • fault_memset(dst, val, len) → preenchimento de memória com o byte val (llvm.memset); dst é ponteiro

Semântica exata (igual no build nativo e no interpretador ofs run):

  • Tudo em 64 bits, complemento de 2: fault_count(-1) = 64; fault_lead(0) = fault_trail(0) = 64; fault_lead(-1) = 0.
  • fault_spin_left/fault_spin_right: rotação de 64 bits (llvm.fshl/llvm.fshr); a distância é tomada módulo 64 (fault_spin_right(6, 65) = 3).
  • fault_weave(mask, left, right) = (left & mask) | (right & ~mask): o bit vem de left onde mask tem 1 e de right onde tem 0.
  • fault_trap() e fault_unreachable() encerram o processo com SIGILL (o interpretador faz o mesmo com raise(SIGILL)).
  • fault_fence()/fault_prefetch() não fazem nada no interpretador.
  • No interpretador ponteiros são endereços reais: fault_memcpy/fault_memset copiam/preenchem qualquer tamanho, e fault_step, fault_addr e fault_call funcionam como no nativo (ver "No interpretador (ofs run): o Rift").
  • Teste: ofs/tests/regress/fault_intrinsics.ofs.

Esses intrínsecos cobrem operações que o assembly já tem e dão ao OFS vocabulário próprio, orientado à máquina.

asm inline (planejado)

Estado: planejado. O asm inline ainda não está disponível no compilador: o lexer não reconhece a palavra asm e o backend LLVM não gera InlineAsm. Os exemplos abaixo mostram o desenho previsto e não compilam hoje. Enquanto isso, use os intrínsecos fault_*.

  • O argumento deve ser um literal de string.
  • Operandos de entrada/saída (restrições estilo AT&T) ainda não serão analisáveis na primeira versão; use fault_* quando precisar vincular operandos.

Linguagem

OFS: Linguagem Híbrida e Compilada Nativa

Pergunta Essencial: OFS é Interpretada ou Compilada?

Resposta: OFS é HÍBRIDA — Compilação Nativa AOT via LLVM e Interpretação Direta de AST.

O OFS combina o melhor dos dois paradigmas:

  1. Compilação Nativa AOT (`ofs build`): gera representação intermediária LLVM IR diretamente pelo seu próprio compilador auto-hospedado (ofscc), emitindo código de máquina e ligando executáveis através de linkers nativos do sistema operacional, sem VM e sem interpretador no binário final.
  2. Execução Instantânea Interpretada (`ofs run` / `ofs <arquivo.ofs>`): executa a árvore sintática abstrata (AST) tipada diretamente na memória através de um interpretador AST integrado em OFS puro (interpreter.ofs), ideal para scripts rápidos, prototipação e validação imediata.

O que Significa o Modelo Híbrido?

  1. Desenvolvimento Instantâneo: Em modo ofs run ou ofs arquivo.ofs, o código é executado diretamente na memória sem o atraso da invocação do llc e do linker.
  2. Produção Nativa sem VM: Em modo ofs build, o executável final não embute nenhum interpretador nem máquina virtual; roda diretamente como código de máquina da CPU (x86_64, ARM64).
  3. Frontend Compartilhado: o interpretador e o gerador LLVM compartilham lexer, parser e verificador de tipos. Isso não garante paridade de execução: hoje o ofs run ainda é um subconjunto do build nativo (sem extern fora da lista de builtins e sem ponteiros). O plano é chegar à paridade; até lá, programas com extern próprio ou ponteiros só rodam com ofs build.
  4. Auto-hospedado (Self-hosted): Todo o compilador (ofscc), incluindo o parser, type checker, gerador LLVM e interpretador, é escrito em OFS.

Conclusão

OFS é uma linguagem moderna, híbrida e auto-suficiente:

  • Execução de scripts imediata com o interpretador AST (ofs run).
  • Compilação direta para código de máquina nativo de alta performance (ofs build).
  • Frontend 100% escrito na própria linguagem OFS.
  • Runtime nativo integrado de alto desempenho (Stack Magma).

    forge b: StrBuf = strbuf.create(64)
    strbuf.append(b, "total: ")
    strbuf.append_int(b, 42)
    echo(strbuf.to_obsidian(b))

Só no código nativo por enquanto (usa memória crua do runtime; o ofs run ainda não alcança o Rift).

Strings e memória. Strings não têm GC nem contagem de referência: t = s faz as duas variáveis apontarem para o mesmo texto. O compilador nativo só reaproveita ou libera memória quando prova que ninguém mais vê o valor: s = s + x / s += x numa variável local que nunca é copiada para outro lugar crescem no lugar; as partes intermediárias de a + b + c e um f(a + b) cujo parâmetro não é guardado são liberados; arrays locais que não escapam são liberados no fim do escopo. Se a variável for copiada, guardada num campo/array ou passada para uma função que a guarda, tudo continua como antes (cópia nova a cada +).

Fase 1: Lexer (tokenização)

Arquivo: ofs/ofscc/lexer.ofs (433 linhas)

Entrada

Processamento

  1. Classificação de caracteres (chars.ofs):
   is_digit(c), is_alpha(c), is_alnum(c), is_space(c)
  1. Reconhecimento de tokens:

Fase 2: Parser (construção da AST)

Arquivo: ofs/ofscc/parser.ofs (1.246 linhas)

Estratégia

  1. Descida recursiva para comandos e declarações
  2. Parser de Pratt para expressões (precedência de operadores)
  3. AST em pool — nós guardados em um Array<Node> global

Gramática (simplificada)

program     ::= (fn_decl | monolith_decl | impl_decl | namespace_decl
                | strata_decl | extern_decl | attach_decl | var_decl)*

fn_decl     ::= ("vein" | "core") IDENT "(" params? ")" ("->" type)? block
params      ::= IDENT ":" type ("," IDENT ":" type)*
extern_decl ::= ("extern" | "rift") "vein" IDENT "(" params? ")" ("->" type)?
                ("bind" STRING)? ("abi" IDENT)?
monolith_decl ::= "monolith" IDENT "{" (IDENT ":" type (","|";")?)* "}"
impl_decl   ::= "impl" IDENT "{" fn_decl* "}"
namespace_decl ::= "namespace" IDENT "{" (fn_decl | var_decl | monolith_decl
                | extern_decl | impl_decl | strata_decl)* "}"
strata_decl ::= "strata" IDENT "{" (IDENT ("(" type ")")? (","|";")?)* "}"
attach_decl ::= "attach" "{" caminho "}"          // ex.: attach {core}, attach {F:lib.ofs}
var_decl    ::= ("forge" | "const" | "shard") IDENT (":" type)? ("=" expr)? ";"?

type        ::= IDENT | "Array" "<" type ">" | "*" type

stmt        ::= var_decl | if_stmt | while_stmt | cycle_stmt | mine_stmt
              | match_stmt | return_stmt | throw_stmt | tremor_stmt
              | anchor_stmt | unsafe_block | block | "break" | "continue"
              | "shatter" | "erode" | expr ";"?
if_stmt     ::= "if" "(" expr ")" block ("else" (if_stmt | block))?
while_stmt  ::= "while" "(" expr ")" block
cycle_stmt  ::= "cycle" "(" IDENT "in" expr ")" block          // sobre uma coleção
              | "cycle" "(" "forge" IDENT "in" expr ")" block
              | "cycle" "(" init? ";" expr? ";" expr? ")" block // estilo C
mine_stmt   ::= "mine" "(" IDENT "in" expr ")" block
match_stmt  ::= ("match" | "assay") "(" expr ")" "{" (pattern "=>" (block | stmt))* "}"
pattern     ::= expr | "_"                                      // "_" é o caso padrão
return_stmt ::= "return" expr? ";"?
throw_stmt  ::= "throw" expr ";"?
tremor_stmt ::= "tremor" block ("catch" "(" IDENT (":" type)? ")" block)?
anchor_stmt ::= "anchor" stmt

expr        ::= unary (binop expr)*         // precedência na tabela abaixo
unary       ::= ("-" | "!" | "~" | "&" | "*") postfix(primary)

                        | "++" | "--" | "?" | "as" type )*

              | "(" expr ")" | "[" (expr ("," expr)*)? "]" | "echo" "(" args? ")"

Pontos que a gramática não mostra:

  • Os parênteses de if, while, match/assay e cycle/mine são obrigatórios. if x == 1 { } dá o erro expected '('. O corpo precisa ser um bloco { }.
  • O ponto e vírgula é opcional no fim de comandos e declarações. Só é exigido dentro do cycle estilo C.
  • assay é só outro nome de match (mesmo token). O match vira uma cadeia de if comparando com ==; _ é o caso padrão e => separa padrão e corpo. Não há padrões de desestruturação.
  • shatter e erode são sinônimos de break e continue. mine é como o cycle ... in, mas só aceita o formato item in coleção.
  • Chamadas com namespace (ns.fn(x)) viram o símbolo ns__fn. Métodos de impl viram Tipo__metodo.
  • attach {caminho} só vale no nível do arquivo. O texto entre as chaves é colado token a token (F: indica caminho de arquivo).
  • Não existe literal de struct (P { x: 1 }) nem monolith ... layout ...; o parser espera { logo depois do nome do monolith. Declare a variável (forge p: P) e atribua os campos.
  • core é palavra reservada: marca o ponto de entrada (core main()) e não serve como nome.

Fase 4A: Backend interpretador de AST (interpretação direta)

Arquivo: ofs/ofscc/interpreter.ofs (70 KB, 2.086 linhas)

O backend interpretador da OFS executa a árvore sintática (AST) tipada diretamente em memória, sem gerar arquivos intermediários, código C ou LLVM IR. É o backend padrão utilizado pelo comando ofs <arquivo.ofs> e ofs run <arquivo.ofs>.

Arquitetura do Interpretador

  1. Sistema `Value`: Monolith universal que unifica valores escalares (stone, crystal, obsidian, bool, null) e handles virtuais na heap para Array<T>, objetos monolith e ponteiros.
  2. Ambiente e Frames de Chamada: Escopo léxico estrito baseado em marcadores de frame (_current_frame_base e _globals_count), impedindo vazamento de escopo entre funções chamadoras e variáveis globais.
  3. Semântica por Valor: forge y: T = x e y = x copiam o bloco do monolith (obj_clone()/memcpy no bloco que y já tem, como o store %T do nativo); parâmetros de vein recebem o monolith por referência, como o ponteiro do nativo.
  4. Despacho Dinâmico de Métodos: Resolução automática de métodos definidos em blocos impl Type com injeção automática de self.
  5. Ponteiros reais (F2): ponteiro é endereço (VAL_INT com tipo *T). *p/*p = v usam mem_load/mem_store pela classe de memória do tipo apontado (MC_*: largura, sinal, f32, obsidian, *T, monolith, variante), com o tipo estático do typeck pré-calculado por nó em annotate_nodes (o mesmo tipo que o llvmgen usa); a leitura/escrita é o próprio código nativo do interpretador (fracture { *p8 = v as u8 }). &x de variável troca a entrada por VAL_BOXED: o valor passa a viver num slot de 8 bytes (box_var), lido/escrito por env_load/env_store e liberado em env_pop_one (_boxed_live mantém o caminho rápido sem custo quando não há nenhum). as replica o NK_CAST do llvmgen (eval_cast). monolith vive em memória crua com o layout de llvmgen.struct_layout (a mesma função calcula o tamanho do ofs_alloc no nativo e os offsets no interpretador; compute_layouts), e o VAL_OBJECT guarda o endereço do bloco; campo Array guarda o handle interpretado como -(h+1).
  6. Builtins Integrados: Resolução imediata de funções de entrada/saída (echo), strings (ofs_str_*), vetores (ofs_array_*) e matemáticas (ofs_pow, ofs_sqrt). A lista (is_builtin) é só um caminho rápido, não o limite do que pode ser chamado.
  7. Rift (`extern vein`/`rift vein`): no carregamento (collect_declarations → resolve_calls → ffi_check_symbols), cada extern chamada vira um endereço via dlsym(RTLD_DEFAULT, sym) (com bind), depois de abrir libm e OFS_FFI_LIBS; símbolo ausente é o erro do linker (undefined reference), código 1. Veins de stdlib/runtime/*.ofs (faixas de linha marcadas por expand_attaches com ast_mark_runtime_lines) usam a versão nativa linkada no ofscc. A chamada (call_extern) converte os argumentos pelo tipo declarado (inteiros/ponteiros/obsidian como i64, crystal como double), grava num buffer e chama __ofs_ffi_dispatch, que o llvmgen define no próprio ofscc (emit_ffi_dispatch, quando o módulo declara essa extern): um switch com uma chamada de tipo LLVM exato por classe de assinatura (ffi_sig/ffi_sig_supported: até 4 args i64|double com retorno i64|double, até 12 só inteiros, variádicas de 1 a 3 fixos + até 4 extras; 155 casos). Por isso o ofscc precisa ser linkado com -rdynamic (exporta o runtime e o dispatcher para o dlsym). Na F2, &x, monolith (o bloco) e Array vão à função nativa como endereço: o Array é a coluna de valores do interpretador, que já é um ofs_array nativo (arr_native_ptr), com o comprimento sincronizado na volta (ffi_sync_arrays); um Array devolvido pela função nativa vira um array interpretado que usa o mesmo bloco (arr_adopt). Callbacks nativos → OFS: o módulo que declara extern vein __ofs_cb_table recebe do llvmgen (emit_cb_trampolines) 16 funções __ofs_cb_K(i64 x 6) que chamam __ofs_cb_enter(K, ...), definida no fim do interpreter.ofs; fault_addr de uma vein interpretada liga a vein a um slot (cb_slot_for) e devolve o endereço de __ofs_cb_K (achado por dlsym, para um ofscc gerado por compilador antigo continuar ligando); cb_enter empilha os argumentos pelo tipo de cada parâmetro, roda a vein e devolve o resultado como i64, preservando os registradores do interpretador (reentrante: funciona dentro de uma chamada nativa feita pelo interpretador). Slots esgotados, mais de 6 parâmetros ou crystal/f32 no callback são erro claro (código 1).

Fase 4B: Gerador de LLVM IR (geração nativa)

Arquivo: ofs/ofscc/llvmgen.ofs (74 KB, 2.509 linhas)

O backend de compilação da OFS gera diretamente LLVM Intermediate Representation (IR), dispensando transpiladores para C ou dependências do Clang. É utilizado pelo comando ofs build.

Mapeamento de tipos (OFS → LLVM IR)

stone      → i64
crystal    → double
obsidian   → i8* (ponteiro para sequência UTF-8)
bool       → i1
void       → void
u8, u16, u32, u64 → i8, i16, i32, i64
i8, i32    → i8, i32
Array<T>   → %struct.Array* (vetor dinâmico do Stack Magma)

Estratégia de emissão de LLVM IR

  1. Target Datalayout & Triple — Configuração da arquitetura de destino (x86_64 ELF ou Windows PE32+)
  2. Declarações Externas — Protótipos das rotinas do Stack Magma (ofs_alloc, ofs_str_concat, ofs_array_push, etc.)
  3. Definições de Funções — Blocos básicos rotulados (entry:, etc.), alocações de variáveis (alloca), instruções SSA (load, store, add, icmp, br, call)
  4. Constantes de String — Globais imutáveis @.str.N = private unnamed_addr constant [...]

Exemplo: forge x = 42

LLVM IR Gerado: 

%x = alloca i64, align 8
store i64 42, i64* %x, align 8

Exemplo: vein add(a: stone, b: stone) -> stone { return a + b }

LLVM IR Gerado: 

define i64 @add(i64 %a, i64 %b) {
entry:
  %0 = add i64 %a, %b
  ret i64 %0
}

Alvos (OFSCC_TARGET)

Sem a variável, o IR sai com o triple do host (x86-64 Linux/Windows/macOS), idêntico ao de antes. OFSCC_TARGET=android emite aarch64-unknown-linux-android26 (ou passe um triple completo). O runtime magma usa só a libc, então para o Android basta gerar o IR do magma.ofs com o mesmo triple e compilar com o clang do NDK; a .so é linkada com -Wl,-init,__ofs_init_globals porque não há main(). Ver ANDROID.md.

Um extern vein que o próprio módulo define não é mais declarado de novo (antes: invalid redefinition).

Endereço de função (fault_addr, fault_call)

fault_addr(nome): o typeck troca o argumento pelo símbolo mangled (ns.fn → ns__fn) e exige que seja uma vein (SYM_FN); o llvmgen resolve bind de extern/rift e emite ptrtoint ptr @simbolo to i64. fault_call(endereco, args...) emite inttoptr + call i64 %p(...) com os tipos LLVM dos argumentos. Ver LANGUAGE_REFERENCE.md.

Guia de Bootstrap e Auto-Hospedagem do OFS

O compilador OFS é completamente auto-hospedado (*self-hosted*) e determinístico. O processo de bootstrap compila o compilador utilizando a si próprio, sem depender de ferramentas C++ ou runtimes externos.

Início Rápido

Para realizar o bootstrap do compilador nativo no repositório: 

bash ofs/bootstrap/scripts/bootstrap-minimal.sh

Após o bootstrap, o binário do compilador estará disponível em ofs/dist/ofs (ou ofs/dist/ofscc).

Para compilar um programa: 

ofs/dist/ofs build ofs/examples/hello.ofs -o hello
./hello

O que é Bootstrap?

O processo de bootstrap ocorre quando um compilador é capaz de compilar o seu próprio código-fonte. Esse marco valida formalmente a expressividade sintática, a maturidade da biblioteca padrão e a completude do sistema de tipos da linguagem.

  • Lisp (1962): Primeira linguagem auto-hospedada.
  • C (1972): Bootstrapped e estabelecido como padrão de sistemas.
  • Rust (2011): Compilador escrito em Rust.
  • Go (2015): Compilador migrado inteiramente para Go.
  • OFS (2024–2026): Compilador e runtime nativo auto-hospedados.

Etapas do Processo

Fase 1: Compilador Inicial

O diretório ofs/dist/ contém o binário base do compilador (ofscc / ofs), pronto para inicializar o ciclo de construção.

Fase 2: Recompilação

O script compila os arquivos do compilador (ofs/ofscc/*.ofs) utilizando o binário existente, gerando um novo executável compilador intermediário.

Fase 3: Validação de Determinismo

O novo compilador compila novamente o código-fonte do compilador. A saída binária da passagem 2 é comparada byte a byte com a passagem 3 (v2 === v3). Caso os checksums coincidam perfeitamente, o determinismo da compilação está garantido.

Análise de Desempenho do OFS

Objetivo

O objetivo da otimização é reduzir custos concretos de execução e compilação do compilador e do runtime sem alterar a semântica da linguagem, sem comprometer a integridade de memória e sem introduzir regressões silenciosas. O tempo total de build deve permanecer competitivo com toolchains nativas equivalentes por eliminação de trabalho redundante, e não por remoção de recursos da linguagem.

Fluxo de Compilação

O pipeline de compilação é estruturado nas seguintes etapas: 

Código-fonte OFS
  -> Resolução e expansão de módulos (attach)
  -> Análise léxica (lexer)
  -> Análise sintática (parser)
  -> Verificação de tipos (type checker)
  -> Geração de código intermediário LLVM IR (llvmgen.ofs)
  -> Compilador estático LLVM (llc -filetype=obj)
  -> Linkagem nativa com runtime nativo (ld / ld.lld)
  -> Executável binário nativo (ELF / Mach-O / PE)

Cada etapa é mensurada de forma isolada: otimizações no binário final gerado não reduzem necessariamente o tempo do lexer, e melhorias no lexer não alteram o consumo de CPU do programa resultante.

Pontos Críticos e Oportunidades de Otimização

1. Leitura de Caracteres no Lexer

A função ofs_str_char_at realiza validação de limites usando o comprimento da string. Para chamadas genéricas na biblioteca padrão, essa verificação garante segurança de acesso. No entanto, o lexer interno já mantém o controle estrito de _pos em relação a _len. O uso da variante ofs_str_char_at_known evita varreduras redundantes de comprimento (strlen) a cada caractere lido, mantendo a complexidade estritamente linear $O(N)$ no processamento de arquivos-fonte extensos.

2. Alocação de Substrings

Durante a tokenização, o lexer extrai fatias de texto para representar identificadores, números e literais. A estratégia otimizada consiste em:

  • Armazenar tuplas de posição e comprimento (início, tamanho) apontando para o buffer original do arquivo durante a análise sintática.
  • Materializar strings na memória heap apenas quando um nó da árvore sintática ou a tabela de símbolos exigir persistência explícita.
  • Empregar alocadores baseados em arena por arquivo de compilação, permitindo liberação em lote ao término da unidade de tradução.

3. Concatenação de Cadeias de Caracteres

Operações sequenciais de concatenação em loops geram cópias repetidas de prefixos na heap. No gerador de código LLVM, a rotina cg_emit grava diretamente no arquivo de saída, contornando a criação intermediária de buffers temporários.

4. Tabelas de Símbolos e Consultas de Escopo

Para programas pequenos e médios, listas lineares de símbolos oferecem boa localidade de cache e simplicidade determinística. Para bases de código de grande porte, a utilização de tabelas hash ou estruturas indexadas por escopo reduz o custo assintótico de busca de variáveis e tipos.

Metodologia de Medição

  1. Conjunto controlado de testes sintáticos e léxicos com fontes variando entre 10 KB e 1 MB.
  2. Isolamento de tempos por fase: frontend (lexer, parser, tipos), emissão de LLVM IR, e linkagem nativa.
  3. Medição de métricas reais de sistema via chamadas wait4: tempo de usuário (CPU), tempo de sistema e pico de memória residente (RSS).
  4. Verificação estrita de integridade via checksum da saída gerada para garantir que nenhuma otimização introduza alterações semânticas.

Desempenho de programas gerados (sincronizado com a versão em inglês)

Os trabalhos se dividem entre vazão do compilador e tempo de execução do programa gerado. Pontos já medidos em 14/06/2026 (mediana de sete processos): a geração de IR da carga pequena foi de 8,11 ms para 7,54 ms, e a compilação do ofscc.ofs de 4.610,40 ms para 3.694,08 ms; os estágios dois e três do bootstrap emitiram IR idêntico.

Ordem planejada: reparar e ampliar os testes do lexer self-host; medir lexer, parser, tipos e IR separadamente; testar fontes de 10 KB, 100 KB e 1 MB; introduzir fatias de token ou arena; criar um construtor de strings nativo (já existe strbuf no stdlib); medir tabelas de símbolos indexadas; avaliar LTO e flags do LLVM.

Link e runtime

O runtime distribuído é compilado com -ffunction-sections e -fdata-sections; o launcher usa --gc-sections (ELF), dead_strip (Mach-O) e OPT:REF (PE/COFF). Na carga de 14/06/2026 isso reduziu o executável de 28.224 para 16.056 bytes sem mudar o checksum, e o cache de caminhos do CRT, llc e ld reduziu o build mediano de 320,81 ms para 208,78 ms.

  • alloc caiu de 116 ms / 97 MB para 17 ms / 5,1 MB (C: 7 ms): arrays locais são liberados no fim do escopo e a alocação é inline. sort caiu de 86 para 15 ms (C: 7 ms): a[i] e a[i] = v são inline no código gerado.
  • Ganha de Python em fib (22x), loop (27x), strings (18x), sort (11x) e alloc (9x).
  • Inicialização de 3 ms (Python: 12 ms) e binário vazio de 36.624 bytes (Rust: cerca de 10 MB). A memória base é maior que a de C: 5,0 MB contra 2,2 MB.
  • O modo interpretado (ofs run) agora roda todos os benchmarks dentro do limite de memória (o vazamento de cerca de 3 KB por chamada foi corrigido; o interpretador foi reescrito com registradores e tabelas da AST). Continua bem mais lento que o nativo e, em geral, que Python: 6,6x mais lento em fib, 1,6x em loop, 2,2x em strings, 5,6x em sort e 5,0x em alloc. Use ofs run para scripts e desenvolvimento; use ofs build para desempenho.
  • Compilar o próprio compilador (self-host) caiu de 197 MB para 45 MB de RAM.

Para reproduzir: bash bench/run.sh. Os números completos ficam em `bench/RESULTADOS.md`.

Consistência entre ofs run e ofs build

O interpretador e o gerador LLVM compartilham lexer, parser e verificador de tipos, mas a execução ainda diverge: ofs run é um subconjunto (sem extern fora da lista de builtins e sem ponteiros). O plano é chegar à paridade; até lá, ofs build é a referência.

Referência OES

OES (Obsidian Effect Scripts) é a linguagem de efeitos, estilos visuais e movimento do ecossistema OFS.

O desenvolvedor escreve arquivos .oes. A ferramenta oesc da biblioteca padrão compila as regras para CSS padrão (ofs run ofs/tools/oesc.ofs, com OESC_INPUT/OESC_OUTPUT), e o navegador consome a folha de estilos gerada. O código OES é a fonte de verdade do sistema de design.

Forma Tipada e Escopo Explícito

Além da sintaxe tradicional baseada em indentação, a forma tipada permite categorizar tokens e aninhar contextos responsivos dentro de regras de estilização: 

gem destaque: Color = "#a978ff"
gem espacamento: Size = "16px"

paint .botao
  fill(destaque)
  curve("8px")
  transition("transform .2s ease")

  veil("(max-width: 700px)") {
    grid-cols("1fr")
    space(espacamento)
  }
end

Regras Sintáticas

  • A diretiva gem define tokens de design como variáveis CSS (--nome: valor;).
  • gem nome: Tipo = "valor" declara tokens tipados na sintaxe explícita.
  • A diretiva paint abre um bloco de estilização para um seletor específico.
  • Propriedades visuais são declaradas de forma indentada dentro do bloco seletor.
  • Blocos delimitados por chaves {} e fechamento end podem ser usados para escopo léxico explícito.
  • A interpolação $nome referencia um token via var(--nome).
  • veil declara consultas de mídia (*media queries*).
  • guard declara regras condicionais de suporte (*feature queries* @supports).
  • strata define camadas de cascata (*cascade layers* @layer).
  • pulse define sequências de animação (*keyframes*).

Camadas Visuais Nativas

O ecossistema OFS oferece duas abordagens complementares para o desenvolvimento de interfaces nativas:

  1. Modo Imediato (`canvas`, `window`, `ui`): Renderização direta e procedural sobre buffers de pixels raster, com controle de loop de eventos via polling.

ODL / OES / OLL / OAL

Referência OAL (v1)

OAL (Obsidian Android Language, .oal) descreve o que é próprio do Android num app OFS: o manifesto, as telas de toque, os estilos, as ações e o ciclo de vida. A lógica continua em .ofs. É irmã da ODL (documento → HTML), da OES (estilo → CSS) e da OLL (UI de desktop), e também faz o papel do CSS/OES no Android (bloco style). 

app.oal ──oalc──► AndroidManifest.xml
                └► app_oal.ofs ──ofscc (aarch64)──► libapp.so ──► APK
  • Compilador: ofs/tools/oalc.ofs (OALC_INPUT, OALC_OUT_DIR, OALC_TARGET=android|desktop).
  • Runtime: ofs/stdlib/oal_runtime.ofs (núcleo neutro) + oal_android.ofs (backend). O usuário não importa a OAL: o arquivo gerado já liga o runtime e o android.ofs.
  • Build: ofs build --target android app.oal [-o app.apk] [--install] [--serial ID] (ver ANDROID.md).

Regras gerais

  • Uma declaração por linha; a hierarquia é dada pela indentação (2 espaços ou tab).
  • Comentários: // ... ou # ... em linha própria.
  • Textos entre aspas "..." (com \", \n). Fora de aspas, um valor é uma expressão OFS (biblioteca.resumo()).
  • chave=valor sem espaços em volta do = (title=item.nome, corner=bottom_left).
  • Palavras em português também valem: tela, barra, botao, texto, titulo, lista, grade, cartao, linha, vazio, retrato, paisagem, estilo, usa, ao.
  • Erros saem como oalc: linha N: ... e nada é gerado.

ODL / OES / OLL / OAL

Arquitetura da Stack Web OFS

A stack web do OFS é composta por três camadas bem delimitadas:

CamadaExtensãoFinalidade
ODL.odlEstrutura semântica e conteúdo textual do documento
OES.oesTokens visuais, layout responsivo e animações
OFS.ofsLógica nativa de processamento, geração estática e servidor HTTP

ODL e OES são linguagens compiladas pelo próprio toolchain do OFS, e não meros atalhos sintáticos para HTML e CSS manuais. No entanto, HTML5 e CSS padrão continuam sendo os formatos de saída distribuídos para navegadores.

1. Geração de Sites Estáticos

O toolchain compila os arquivos de código-fonte ODL e OES diretamente para artefatos consumíveis por qualquer servidor ou CDN: 

ODLC_INPUT=page.odl ODLC_OUTPUT=public/index.html ofs run ofs/tools/odlc.ofs
OESC_INPUT=theme.oes OESC_OUTPUT=public/theme.css ofs run ofs/tools/oesc.ofs

A saída gerada pode ser hospedada em plataformas estáticas convencionais, como GitHub Pages, Cloudflare Pages ou servidores Nginx/Apache.

2. Servidor Nativo Integrado (webserver)

A biblioteca padrão fornece um servidor HTTP de alta performance escrito e executado nativamente em OFS: 

attach {webserver}

core main() {
    forge corpo = "<h1>Servidor Nativo OFS</h1><p>Execução sem dependências externas de runtime.</p>"
    webserver.serve_html_forever(8080, corpo)
}

O programa compilado em OFS gerencia os sockets de rede e entrega os artefatos compilados sob demanda.

3. Interoperabilidade com o Ecossistema Web

O compilador ODL possui diretivas específicas para integração direta com código web existente:

  • mark / markdown: Processamento de conteúdo formatado em Markdown nativo.
  • raw / html: Inclusão direta de fragmentos de HTML bruto sem filtros de escape.
  • wire / script: Inclusão de scripts JavaScript convencionais (<script src="...">).
  • spark / module / node: Inclusão de módulos JavaScript ES (<script type="module" src="...">).
  • pulse / js: Execução de blocos inline de JavaScript (<script>...</script>).
  • server / php: Emissão de blocos de processamento server-side (<?php ... ?>).
  • raw / css no OES: Injeção direta de blocos CSS para migração gradual.

4. Extensão do VS Code e Recarregamento em Tempo Real (*Go Live*)

A extensão oficial do Visual Studio Code ativa o modo *Go Live* ao detectar arquivos .odl ou códigos .ofs que importam webui ou webserver.

Ao iniciar o *Go Live*:

  1. O documento .odl é compilado para HTML.
  2. Arquivos de estilo .oes no mesmo diretório são compilados para CSS.
  3. Um servidor HTTP de desenvolvimento local é inicializado.
  4. O servidor monitora alterações em arquivos .odl, .oes, scripts e ativos gráficos, disparando a recompilação e o recarregamento automático do navegador via SSE (*Server-Sent Events*).

5. Compatibilidade com Navegadores

Navegadores não interpretam arquivos .odl e .oes diretamente em tempo de execução. O ecossistema OFS adota o modelo consolidado na indústria (semelhante ao TypeScript, JSX e Sass):

  1. O código-fonte do projeto é mantido exclusivamente em .odl e .oes.
  2. As ferramentas de build compilam os arquivos em HTML5, CSS e JS compatíveis.
  3. Servidores e navegadores consomem os artefatos finais gerados.
  4. Para fins de depuração e inspeção, os servidores nativos expõem os tipos MIME text/odl e text/oes.

6. Escopo Técnico Atual

  • As linguagens ODL e OES compilam código-fonte estruturado para páginas estáticas e folhas de estilo.
  • A importação reversa de HTML/CSS armazena trechos complexos em blocos de texto bruto (raw).
  • A lógica de roteamento HTTP em programas OFS permanece desacoplada da declaração estrutural dos documentos.
  • Os componentes atuais são orientados à geração e emissão estática em tempo de compilação ou inicialização.

OFS no Android (aarch64)

O OFS gera apps Android nativos 100% em OFS: o APK leva uma lib<nome>.so compilada do seu código e da stdlib, sem Java, sem Gradle e sem nenhum arquivo .c. Só as bibliotecas do sistema (libc/bionic, libandroid, liblog) são chamadas, via extern vein/rift vein, como a libc no desktop.

O que a CLI faz (src/packaging/linux/ofs, função android_build):

  1. .oal → oalc → AndroidManifest.xml + <nome>_oal.ofs (ver OAL_REFERENCE.md);
  2. OFSCC_TARGET=android ofscc → LLVM IR com target triple = "aarch64-unknown-linux-android26" do app e do runtime magma (o runtime fica em cache);
  3. clang do NDK → lib<nome>.so com -shared -Wl,-init,__ofs_init_globals -u ANativeActivity_onCreate -Wl,-z,max-page-size=16384 -landroid -llog -lm;
  4. aapt2 link + zip da lib/arm64-v8a/ + zipalign -P 16 + apksigner (chave ~/.android/debug.keystore ou uma gerada no cache).

O nome da .so vem de android.app.lib_name no manifesto. Arquivos intermediários ficam em build/android/<nome>/ ao lado do fonte (ou em OFS_ANDROID_BUILD).

Como o app roda (stdlib android.ofs)

  • Entrada: android.ofs exporta vein ANativeActivity_onCreate(...), que o NativeActivity acha por dlsym. Ela preenche activity->callbacks com o endereço de veins OFS usando fault_addr (ver LANGUAGE_REFERENCE.md).
  • Uma thread só: tudo roda na thread principal do Android, sem pthread. O runtime magma não é thread-safe, então isso é intencional.
  • ciclo de vida: callbacks onStart/Resume/Pause/Stop/Destroy, onWindowFocusChanged, onNativeWindow*, onInputQueue*, onContentRectChanged, onConfigurationChanged, onLowMemory;
  • entrada: AInputQueue_attachLooper no looper da thread principal, com callback OFS;
  • frames: AChoreographer_postFrameCallback (API 24+), reagendado só quando há pedido (android.request_frame() ou android.continuous = true).
  • Trabalho longo deve ser dividido em pedaços, um por EV_FRAME.
  • Contrato: o programa define vein android_event(ev: stone) -> void e lê o estado em android.*:
attach {F:android.ofs}

vein android_event(ev: stone) -> void {
    if (ev == android.EV_FRAME) {
        if (android.lock()) {
            android.fill_rect(0, 0, android.buf_w, android.buf_h, 1052704)
            android.unlock_post()
        }
    }
    if (ev == android.EV_TOUCH_DOWN) { android.request_frame() }
    if (ev == android.EV_BACK) { android.finish() }
}

Entrada de texto pelo teclado do sistema (android_input.ofs)

Limites atuais

  • Só arm64-v8a (aarch64) e API 26+. Sem x86/armv7.
  • Render em software (ANativeWindow_lock), sem OpenGL/Vulkan.
  • Áudio: só WAV (PCM/MS‑ADPCM); sem Ogg/MP3; sem reamostragem de qualidade (passo inteiro 16.16).
  • Sem onSaveInstanceState (o app salva o próprio estado no on pause).
  • Os offsets de structs C (ANativeActivity, ANativeWindow_Buffer, ARect, struct stat/statfs, tabela do JNIEnv) estão fixos para aarch64.
  • Inteiros C de 32 bits chegam como stone com o topo indefinido: use android.s32().
  • fault_call só passa inteiros e ponteiros (sem float/double).
  • O ofs/dist/magma.o e o ofscc instalados ainda são de antes do alvo Android: até o próximo release, a CLI compila o ofscc do fonte.

  • `android_webview.ofs`: webview.open(base_url, html) abre uma WebView (JS, DOM storage, acesso a arquivos, mídia sem gesto) num android.app.Dialog em tela cheia imersiva; poll() (o botão voltar fecha o Dialog), eval(js), title(), pause(on), close(). A partir daí a NativeActivity não reserva mais a superfície nem a fila de entrada: set_content_view(view) (ou o setContentView de um adaptador Java) desenha normalmente e recebe toque/teclado pelo Java. O OFS deixa de receber EV_WINDOW_* e toques; o ciclo de vida continua chegando. Testado no Android 11 (Moto G8 Power). No NativeActivity.java do AOSP o onCreate faz takeSurface(this)/takeInputQueue(this) e só depois chama o ANativeActivity_onCreate; o ViewRootImpl lê esses callbacks ao anexar a janela, então o null vale.
  • dex_load_class(dex, pasta_libs, "pacote.Classe"): DexClassLoader (pai: o class loader da activity) e loadClass; devolve referência global da classe ou 0 (motivo em jni_error). dex aceita vários arquivos separados por :. O .dex deve estar na área interna do app e, no Android 14+, ser somente leitura (set_read_only(caminho)). pasta_libs é o caminho de busca do System.loadLibrary desse loader.
  • jni_scall_cls(classe, nome, assinatura, a..d): método estático numa jclass já obtida (ex.: de dex_load_class).
  • jni_take_error(): se há exceção Java pendente, guarda o toString() em jni_error, imprime a pilha no logcat (System.err) e limpa.
  • intent_extra(chave): getIntent().getStringExtra(chave) ("" se não houver).
  • self_intent(chaves, valores) / restart_process(chaves, valores): Intent para esta mesma activity com extras String e FLAG_ACTIVITY_NEW_TASK|CLEAR_TASK; restart_process faz startActivity e encerra o processo (Process.killProcess(myPid)): o sistema abre a activity num processo novo (~60 ms no Moto G8). Usado pelo M.O.O.N para entrar e sair do "modo motor" (um motor por processo).

ODL (Obsidian Document Language) e OES (Obsidian Effect Scripts) são linguagens web independentes do OFS. A saída para o navegador continua compatível com HTML e CSS, mas o código-fonte usa o vocabulário do OFS: page, skin, flow, deck, stage, band, gem, paint, veil, and pulse.

A toolchain do OFS as compila nativamente. Os navegadores recebem artefatos HTML, CSS e JavaScript gerados.
