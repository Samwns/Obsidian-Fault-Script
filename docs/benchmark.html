Gargalos atuais

O acesso de caractere do lexer foi otimizado sem alterar a API publica. As proximas areas sao materializacao de tokens, alocacoes temporarias e indices de simbolos.

Leitura de string no lexer

O lexer usa uma leitura interna de byte depois de validar a posicao contra o tamanho da fonte. A API publica continua verificando limites.

Substrings e alocacoes

Tokens e escapes criam novas strings com ofs_str_substr e concatenacao. Reduzir copias exige slices ou arena.

Buscas lineares

Tabelas de simbolos, nomes de strings, campos e variaveis usam arrays com busca linear. Projetos grandes aumentam o custo dessas consultas.

Tamanho em loops

Loops que chamam ofs_array_len, node_extra_len ou ofs_str_len em cada iteracao podem guardar o tamanho quando a colecao nao muda.

Otimizacao de compilacao

O objetivo e reduzir trabalho repetido sem remover tipos, ODL/OES, stdlib ou verificacoes publicas. Build de desenvolvimento e build de release devem ter politicas diferentes.

Modo dev

Gerar LLVM IR e linkar sem otimizacoes pesadas para feedback local rapido.

Cache incremental

Cachear attaches, AST, metadados de tipos e objetos por hash de arquivo.

Slices e arena

Guardar tokens como inicio+tamanho sobre a fonte e liberar uma arena por modulo.

Hash flat

Trocar consultas lineares frequentes por tabelas hash pre-dimensionadas onde o perfil indicar ganho.

Medicao por fase

Separar tempo de attach, lexer, parser, type checker, LLVM IR, otimizacao e link.

Objetos reutilizaveis

Evitar linker completo quando somente check ou ir for pedido.

Interpretacao

CPU mede o tempo do workload; memoria mostra o pico RSS; inicializacao mede abrir e encerrar um programa minimo; compilacao mede a geracao do executavel; artefato mostra o tamanho do arquivo final.

Os resultados mudam com processador, sistema operacional, compilador, flags e codigo medido. O site mostra maquina e data junto dos valores para manter a leitura reproduzivel.
