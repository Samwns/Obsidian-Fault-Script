Getting Started

Getting Started with OFS

OFS (Obsidian Fault Script) is a hybrid, self-hosted programming language featuring an integrated AST interpreter for instant execution (ofs run) and an LLVM backend for high-performance native binary compilation (ofs build).

The ecosystem includes the compiler, a standard library, command-line tools, and domain-specific web languages (ODL and OES).

1. Installation

Pre-compiled Packages

Official packages and installers are available across major platforms:

  • Debian / Ubuntu:
  sudo dpkg -i ofs-debian-ubuntu-x64-installer-v*.deb
  • Fedora / RHEL / openSUSE:
  sudo rpm -Uvh ofs-fedora-x64-installer-v*.rpm
  • Arch / Manjaro:
  sudo pacman -U ofs-arch-x64-installer-v*.pkg.tar.zst
  • macOS (Apple Silicon / ARM64):
  • Run the installer script provided in the GitHub release assets.
  • Windows (x64):
  • Run the official executable installer: ofs-windows-x64-installer-v*.exe.
  • VS Code:
  • Install the official extension ofs-vscode-extension.vsix for syntax highlighting, diagnostics, and automatic live reload (*Go Live*).

Building from Source (Bootstrap)

To build the compiler from source within the repository: 

git clone https://github.com/Samwns/Obsidian-Fault-Script.git
cd Obsidian-Fault-Script
bash ofs/bootstrap/scripts/bootstrap-minimal.sh

The resulting compiler binary is written to ofs/dist/ofs (or ofs/dist/ofscc).

Termux (Android)

OFS runs on the phone itself, inside Termux (aarch64).

Install (in Termux): 

curl -fsSL https://raw.githubusercontent.com/Samwns/Obsidian-Fault-Script/main/src/packaging/termux/install_termux.sh | bash
# or, with a local package:  bash install_termux.sh ofs-termux-aarch64.tar.gz

The installer runs pkg install -y clang, downloads the latest ofs-termux-aarch64.tar.gz release, extracts it into $PREFIX (bin/ofs and lib/ofs/) and tests ofs --version.

Use: ofs run hello.ofs (interpreted), ofs build hello.ofs -o hello && ./hello (native aarch64, linked with Termux's clang). Tools live in $PREFIX/lib/ofs/tools/ (ofs run $PREFIX/lib/ofs/tools/odlc.ofs).

Limitations: no X11 windows for now (.oll/.oal windows); building an APK on the phone (ofs build --target android) comes later.

3. First Program

Create a file named hello.ofs: 

core main() {
    echo("Hello from OFS!")
}

Direct execution via the AST interpreter: 

ofs hello.ofs
# or: ofs run hello.ofs

Or compiling to a standalone native binary: 

ofs build hello.ofs -o hello
./hello

Output: 

Hello from OFS!

4. Data Types

OFS is statically typed. The compiler infers variable types when initialized with forge.

Primitive Types

  • stone: 64-bit signed integer.
  • crystal: 64-bit floating-point number (IEEE 754).
  • obsidian: UTF-8 encoded string pointer.
  • bool: Boolean (true or false).
  • void: Indicates absence of a return value.

Fixed-Width Integer Types

  • Unsigned: u8, u16, u32, u64
  • Signed: i8, i32

Example: 

core main() {
    forge counter: stone = 10
    forge rate: crystal = 3.14159
    forge active: bool = true
    forge title: obsidian = "Obsidian"

    forge red: u8 = 255
    forge green: u8 = 128
    forge pixel: u32 = (red as u32 << 16) | (green as u32 << 8)

    echo(title)
    echo(pixel)
}

5. Functions

Functions are declared using the vein keyword. The entry point of an executable program is core main(). 

vein add(a: stone, b: stone) -> stone {
    return a + b
}

vein factorial(n: stone) -> stone {
    if (n <= 1) {
        return 1
    }
    return n * factorial(n - 1)
}

core main() {
    forge sum = add(15, 27)
    forge fact = factorial(5)
    echo(sum)
    echo(fact)
}

Functions can compose calls and invoke other functions: 

vein square(n: stone) -> stone {
    return n * n
}

vein sum_of_squares(a: stone, b: stone) -> stone {
    return square(a) + square(b)
}

core main() {
    echo(sum_of_squares(3, 4))
}

Note: Anonymous function expressions (*lambdas*) are modeled in the AST specification (NK_LAMBDA) and scheduled for an upcoming compiler release. Currently, all functions are declared as named items with vein.

6. Data Structures (monolith)

Composite types are defined with monolith, and methods are attached using impl: 

monolith Rectangle {
    width: stone
    height: stone
}

impl Rectangle {
    vein area(self: Rectangle) -> stone {
        return self.width * self.height
    }

    vein perimeter(self: Rectangle) -> stone {
        return (self.width + self.height) * 2
    }
}

core main() {
    forge r: Rectangle
    r.width = 10
    r.height = 5

    echo(r.area())
    echo(r.perimeter())
}

7. Modules and Imports (attach)

The attach keyword imports modules from the installed standard library or local files: 

attach {math}
attach {string}
attach {io}

To import local relative or absolute files, prefix the path with F:: 

attach {F:./modules/helper.ofs}

8. Control Flow

Conditionals (if / else)

core main() {
    forge x: stone = 10
    if (x > 0) {
        echo("positive")
    } else if (x < 0) {
        echo("negative")
    } else {
        echo("zero")
    }
}

Loops (while)

core main() {
    forge i: stone = 0
    while (i < 5) {
        echo(i)
        i = i + 1
    }
}

Multi-Branch Selection

Multi-branch decision logic is currently written with chained if / else if / else: 

core main() {
    forge status_code = 200
    if (status_code == 200) {
        echo("OK")
    } else if (status_code == 404) {
        echo("Not Found")
    } else {
        echo("Unknown code")
    }
}

Note: Pattern matching with match is reserved in the AST specification (NK_MATCH) and grammar, with dedicated parser and lowering support planned for an upcoming release.

Error Handling and Abort (throw)

The throw statement reports a diagnostic error message and cleanly terminates the process with exit code 1: 

vein divide(dividend: stone, divisor: stone) -> stone {
    if (divisor == 0) {
        throw "Division by zero"
    }
    return dividend / divisor
}

core main() {
    echo(divide(10, 2))
}

Note: The tremor { ... } catch (...) { ... } block structure is modeled in the grammar (NK_TREMOR), with non-terminating stack unwinding planned for the upcoming interpreter and runtime stages.

9. The Rift: native system libraries (rift / extern vein)

The Rift is the boundary through which OFS reaches native system libraries (libc, libm, X11, Android JNI, kernel32). rift vein and extern vein declare a function that lives in a native library, called through the system calling convention. There is no C code in OFS: the compiler and the runtime are written in OFS.

The system calling convention is known technically as the C ABI (abi c); it does not involve C code. 

extern vein puts(s: obsidian) -> stone
rift vein strlen(s: obsidian) -> stone bind "strlen" abi c

core main() {
    puts("Message dispatched via libc puts")
}

10. Web Stack: ODL and OES

OFS provides two native DSLs designed for authoring web applications without writing raw HTML or CSS by hand:

ODL (Obsidian Document Language)

Semantic document structure compiled into HTML5: 

page "OFS Application" "en"
skin "style.css"

flow
  deck.navigation
    title1 "Main Header"
    link.button "Documentation" "#docs"
  stage#content
    band.article
      mark "## Native Content\nFormatted with **Markdown**."
      raw "<div class=\"custom\">Raw HTML when required</div>"
  spark "app.js"

Compile ODL (the odlc tool ships with the standard library and runs on ofs itself): 

# inside the OFS repository (or with tools installed at /usr/share/ofs/tools)
ODLC_INPUT=document.odl ODLC_OUTPUT=public/index.html ofs run ofs/tools/odlc.ofs

OES (Obsidian Effect Scripts)

Visual tokens, layout rules, media queries, and keyframe animations compiled into CSS: 

gem primary "#5b34ea"
gem background "#120e24"

paint .button
  fill "$primary"
  curve "6px"
  space "8px 16px"
  edge "none"

veil "(max-width: 768px)"
  paint .grid
    grid-cols "1fr"

pulse "appear"
  rise
    opacity "0"
  rest
    opacity "1"

Compile OES (same pattern, with the oesc tool): 

OESC_INPUT=style.oes OESC_OUTPUT=public/style.css ofs run ofs/tools/oesc.ofs

Native HTTP Web Server (webserver)

The standard library includes a native HTTP server built into the runtime: 

attach {webserver}

core main() {
    forge html = "<h1>OFS Native Server</h1><p>Running without third-party dependencies.</p>"
    webserver.serve_html_forever(8080, html)
}

11. Low-Level Features

OFS provides explicit machine-level constructs:

  • fracture { ... }: Typed pointer context.
  • abyss { ... }: Unrestricted low-level operations.
  • bedrock: Standard library module for explicit memory allocations, regions, and byte-level memory.
attach {bedrock}

core main() {
    forge cell = bedrock_cell_new(42)
    echo(bedrock_cell_read(cell))
    bedrock_cell_drop(cell)
}

Getting Started

OFS — Beginner's Journey

A step-by-step practical guide to learning Obsidian Fault Script (OFS) from the ground up, starting with primitives and advancing to structures, modules, and collections.

How to Follow This Guide

  1. Read and work through one module at a time.
  2. Run each example via the terminal with ofs run file.ofs (or compile with ofs build file.ofs -o app).
  3. Experiment by changing values and verifying compiler feedback.
  4. Advance to the next module only after fully understanding the program output.

Module 1: Variables and Primitive Types

Goal: Understand core main(), variable declarations with forge, console output with echo(), and fundamental types. 

core main() {
    forge name: obsidian = "Alice"
    forge age: stone = 24
    forge rating: crystal = 9.8
    forge active: bool = true

    echo(name)
    echo(age)
    echo(rating)
    echo(active)
}

Challenge: Declare additional variables to hold a city name (obsidian) and an exchange rate (crystal).

Module 2: Conditionals and Loops

Goal: Use conditional branching (if / else) and loops (while). 

core main() {
    forge energy: stone = 3

    while (energy > 0) {
        echo(energy)
        energy = energy - 1
    }

    if (energy == 0) {
        echo("Recharge required")
    }
}

Challenge: Write a loop that counts down from 5 to 1 and then prints "Liftoff".

Module 3: Functions (vein)

Goal: Structure and reuse computational logic using the vein keyword. 

vein double(n: stone) -> stone {
    return n * 2
}

vein add(a: stone, b: stone) -> stone {
    return a + b
}

core main() {
    echo(double(21))
    echo(add(10, 32))
}

Challenge: Write a function average(a: stone, b: stone) -> stone that returns the integer arithmetic mean of two numbers.

Module 4: Fixed-Width Integers

Goal: Work with machine-sized integer types (u8, u16, u32, i8, i32). 

core main() {
    forge channel_r: u8 = 255
    forge channel_g: u8 = 128
    forge channel_b: u8 = 0

    forge pixel: u32 = (channel_r as u32 << 16) | (channel_g as u32 << 8) | (channel_b as u32)
    echo(pixel)
}

Challenge: Extract the green channel (channel_g) back out from pixel using right bit-shifts and masking (& 0xFF).

Module 5: Records (monolith) and Methods (impl)

Goal: Model composite structures and attach methods using monolith and impl. 

monolith Rectangle {
    width: stone
    height: stone
}

impl Rectangle {
    vein area(self: Rectangle) -> stone {
        return self.width * self.height
    }

    vein perimeter(self: Rectangle) -> stone {
        return (self.width + self.height) * 2
    }
}

core main() {
    forge r: Rectangle
    r.width = 10
    r.height = 20

    echo(r.area())
    echo(r.perimeter())
}

Challenge: Add an is_square(self: Rectangle) -> bool method that returns true when width equals height.

Module 6: Namespaces (namespace)

Goal: Group functions and constants under scoped identifiers to prevent collisions. 

namespace math_utils {
    vein square(x: stone) -> stone {
        return x * x
    }

    vein cube(x: stone) -> stone {
        return x * x * x
    }
}

core main() {
    echo(math_utils.square(5))
    echo(math_utils.cube(3))
}

Module 7: Modular Code with attach

Goal: Split code across separate files and import functions.

Helper file helper.ofs: 

vein greet(name: obsidian) -> obsidian {
    return "Hello, " + name + "!"
}

Main file main.ofs: 

attach {F:./helper.ofs}

core main() {
    echo(greet("OFS"))
}

Module 8: Arrays and Collections (Array<T>)

Goal: Store sequential collections of items, access values by index, and inspect array length. 

core main() {
    forge scores: Array<stone> = [85, 92, 78]
    echo(scores[0])

    scores[1] = 95
    echo(scores[1])
    echo(ofs_array_len(scores))
}

Challenge: Create an array with 4 numbers and compute their total sum using a loop.

Module 9: Structured Loops (cycle)

Goal: Iterate cleanly using C-style indexed loops and collection traversal. 

core main() {
    cycle (forge i = 0; i < 5; i++) {
        echo(i)
    }

    forge items: Array<stone> = [10, 20, 30]
    cycle (val in items) {
        echo(val)
    }
}

Challenge: Use cycle (item in list) to count how many numbers in an array are greater than 15.

1. Program structure

Every executable program needs a core main(): 

core main() {
    echo("inicio")
}

core is a reserved word: it only marks the entry point. Using it as a name (vein core(), core(1), also inside a namespace) is a compile error ("core e palavra reservada…"); rename the function (e.g. core_fn). Any syntax error stops compilation with exit code 1.

A .ofs file can contain:

  • attach { ... }
  • extern vein and rift vein
  • vein and core
  • monolith
  • impl
  • namespace
  • strata
  • global forge

Warnings (the program still builds)

[AVISO DE TIPO] shows up when a value is stored into a type with no defined conversion, e.g. forge x: stone = "abc" or forge c: crystal = true. There native code reinterprets the bits (or the address) and the interpreter keeps the value as is. It stays a warning because low-level code sometimes wants exactly that reinterpretation: use as T to make the intent explicit.

When typeck does not know the type of one side (a call without a known signature, for instance), it neither converts nor reports an error.

Variants in `echo`: echo(v) of a variant (a strata type or a literal like Green) prints the name in both modes. The numeric tag is v as stone.

4. Functions and intents

Regular functions

vein soma(a: stone, b: stone) -> stone {
    return a + b
}

Program entry

core main() {
    echo("ok")
}

Intent

vein square(x: stone) -> stone intent pure {
    return x * x
}

Accepted intents:

  • pure
  • impure
  • fractal

Function composition

Functions can call other functions and support direct recursion: 

vein quadrado(n: stone) -> stone {
    return n * n
}

vein soma_quadrados(a: stone, b: stone) -> stone {
    return quadrado(a) + quadrado(b)
}

core main() {
    echo(soma_quadrados(3, 4))
}

Note: Anonymous function expressions (inline vein(...) -> ...) are specified in the syntax tree (NK_LAMBDA) and are planned for the language's evolution roadmap. Currently, all functions must be declared with a name via vein.

5. monolith, impl and layouts

Structure

monolith Rect {
    w: stone
    h: stone
}

Methods with impl

impl Rect {
    vein area(self: Rect) -> stone {
        return self.w * self.h
    }
}

Usage: 

forge r: Rect
r.w = 10
r.h = 5
echo(r.area())

Explicit layout

Planned: layout is a reserved word, but the parser does not accept layout on a monolith yet (it reports expected '{' after monolith name). Every monolith uses the native layout today. The syntax below is the intended one. 

monolith Header layout packed {
    tag: stone
    flags: stone
}

Supported layouts:

  • native
  • packed
  • c

8. Control flow

if / else

if (x > 10) {
    echo("alto")
} else {
    echo("baixo")
}

while

while (energia > 0) {
    energia -= 1
}

cycle

C-like form: 

cycle (forge i = 0; i < 10; i++) {
    echo(i)
}

Iterative form: 

cycle (n in nums) {
    echo(n)
}

Multi-branch selection

Multi-branch selection is done with chains of if / else if: 

if (code == 200) {
    echo("ok")
} else if (code == 404) {
    echo("nao encontrado")
} else {
    echo("erro")
}

Or with match (synonym: assay), which compares the value with each case using ==; _ is the default case: 

match (code) {
    200 => { echo("ok") }
    404 => { echo("not found") }
    _ => { echo("error") }
}

Error handling and interruption (throw)

The throw statement displays a diagnostic message and ends execution with exit code 1: 

vein dividir(dividendo: stone, divisor: stone) -> stone {
    if (divisor == 0) {
        throw "divisao por zero indefinida"
    }
    return dividendo / divisor
}

core main() {
    echo(dividir(10, 2))
}

Note: The syntax tremor { ... } catch (e: obsidian) { ... } is recognized by the grammar (NK_TREMOR), with structured stack unwinding and runtime capture planned for the interpreter and runtime evolution layers.

strata (variant enumerations)

strata Status { Idle, Running, Failed }

Note: a variant is a numeric tag (v as stone) and can be stored in a strata type (forge c: Status = Idle, parameters, return values, Array<Status>). echo(c) prints the name (Idle) in both modes. The payload of Ok(7) is not stored by native code yet (see ? propagation).

? propagation

expr? unwraps a result variant:

  • Solid(v)? and Ore(v)? evaluate to v.
  • Crack(e)? and Barren? leave the current vein immediately (pending anchors run), propagating the failure. Failure variants are the ones named Crack and Barren; any other variant counts as success.

The propagated value is the same in both modes:

  • In the native build variants are payload-less i64 tags: the tag is the variant's position in declaration order across all strata of the program (with strata Outcome { Solid, Crack } declared first, Crack = 1). A vein ... -> stone that propagates Crack returns that tag, and echo prints 1 in both modes. With an obsidian return you get the tag as text; with crystal, the number; in core main it becomes the exit code.
  • In the interpreter, if the declared return type is the strata type itself (-> Outcome), the whole variant (with payload) is returned.
  • Since native code keeps no payload, x? over an expression that is not a direct constructor (e.g. f()?) evaluates to the success variant's tag, not its payload.
strata Outcome { Solid, Crack }

vein ok() -> stone {
    forge v = Solid(7)?      // 7
    return v
}

vein bad() -> stone {
    forge v = Crack("boom")? // returns 1 right here
    return v
}

core main() {
    echo(ok())   // 7
    echo(bad())  // 1
}

11. extern vein and rift vein

The Rift is the boundary through which OFS reaches the native system libraries (libc, libm, X11, Android JNI, kernel32). extern vein and rift vein declare a function that lives in a native library.

extern vein

extern vein puts(s: obsidian) -> stone

rift vein

rift vein ofs_window_create(title: obsidian, w: stone, h: stone) -> void abi c

Link metadata

rift vein text_size(s: obsidian) -> stone bind "strlen" abi c

Function address and indirect call (fault_addr, fault_call)

OFS has no "function pointer" type, but it can get the address of a vein as a stone and call an address using the system calling convention. This is useful for native library callbacks (qsort, ANativeActivity, ALooper, AChoreographer) and for native function tables (JNI). 

rift vein c_qsort(base: *stone, n: stone, size: stone, cmp: stone) -> void bind "qsort" abi c

vein crescente(a: *stone, b: *stone) -> stone {
    forge x = 0
    forge y = 0
    fracture { x = *a; y = *b; }
    if (x < y) { return -1 }
    if (x > y) { return 1 }
    return 0
}

core main() {
    forge buf = ofs_alloc(64)
    // ...fills 8 values...
    c_qsort(buf, 8, 8, fault_addr(crescente))
    forge r = fault_call(fault_addr(crescente), buf, fault_step(buf, 1))
}
  • fault_addr(nome) → stone: address of the vein. Accepts a module vein, ns.vein, and extern/rift vein (with bind, it returns the native symbol). In IR: ptrtoint ptr @simbolo to i64. Outside a vein, it is a semantic error.
  • fault_call(endereco, args...) → stone: indirect call using the system calling convention (inttoptr + call i64). Integer, pointer and obsidian arguments; the return value is read as i64 (void functions return garbage, ignore it). No float/double.
  • The vein used as a callback must have parameters compatible with the system calling convention: stone for integers (32-bit integers arrive with undefined upper bits; mask them with & 4294967295) and *stone for pointers.
  • In the interpreter (ofs run), fault_addr of an extern/rift vein returns the native address and fault_addr of an interpreted vein returns a native trampoline that re-enters the interpreter (the qsort above works the same). See "In the interpreter (ofs run): the Rift".
  • Test: ofs/tests/runtime/test_fault_addr_qsort.ofs.

Important fields:

  • bind "..." sets the actual native symbol
  • abi c selects the system calling convention
  • ... is accepted in a native variadic function

In the interpreter (ofs run): the Rift

ofs run calls the same native system library functions the native build would link, with no C code and no libffi:

  • Resolved at load time. Every extern vein/rift vein called by the program (or passed to fault_addr) becomes an address via dlsym(RTLD_DEFAULT, "symbol"), using bind when present. The interpreter first opens libm (the build links -lm) and the libraries in OFS_FFI_LIBS (libfoo.so:/path/libbar.so); if a symbol is missing it also tries libX11/libXft (ofs build links both when present). A missing symbol gives the linker's error (undefined reference to 'x') before running, with exit code 1. An extern that is declared but never called does not need to exist (as in the link).
  • OFS runtime. ofscc is linked with -rdynamic, so ofs_alloc, ofs_echo_color etc. are found too. Veins defined in stdlib/runtime/*.ofs (pulled in with attach) run the native version linked into ofscc, like the builtins, when the signature fits the Rift; OFS_RUN_RUNTIME=interp turns this off.
  • Conversion. stone, bool, integers (i8..u64, narrowed to width and sign), pointers and obsidian (the value's own char*) go as i64; crystal goes in an FP register. The return follows the declared type: char* becomes obsidian without a copy (as in native code, where obsidian is the pointer; NULL becomes null), *T becomes the address (it can go back to the native function, be compared with null, converted with as and dereferenced), monolith the block and Array the ofs_array itself.
  • Trampolines. The call goes through __ofs_ffi_dispatch, generated by llvmgen inside ofscc: one case with the exact LLVM type per signature class (up to 4 arguments with any stone/crystal mix and an integer or crystal return; up to 12 integer-only; variadics with 1 to 3 fixed and up to 4 extra). Any other class is a clear error.
  • Variadics (printf, snprintf, open...): the ones llvmgen knows by name; extras use the declared type (or the value's type), with the right convention (%al on x86-64).
  • fault_addr(extern) returns the native address and fault_call(address, ...) calls it with arguments in the value's type (as in native code). fault_step adds to a native pointer.
  • Raw memory (F2). The interpreter runs natively, so a pointer is a real address. *p and *p = v read and write with the width of the pointee type (u8/i8/u16/i16/u32/i32/u64/i64/stone/f32/f64/crystal/bool (4 bytes)/obsidian/*T), using the typeck static type (the same one llvmgen uses); narrow integers are sign-extended (iN) or zero-extended (uN), as in native code. A null p faults like native code (address 0). fault_memcpy/fault_memset use real memcpy/memset of any size; fault_step(p, i) adds i * sizeof(*p) with the static type of p.
  • `as` follows the llvmgen rule: same LLVM type only retags; ptrtoint/inttoptr (including obsidian, which is the char* itself); fptosi; sitofp from iN/stone and uitofp from uN ((255 as u8) as crystal is 255.0); fpext/fptrunc (f32 rounds); trunc if the source is wider, otherwise sext from iN and zext from uN/bool ((0 - 1) as i8 as stone is -1). forge x: u8 = 300 and x = v into a u8/i32/f32 truncate like the native store.
  • `&x`. The address of an interpreter variable is real: on the first &x the variable moves into an 8-byte raw-memory slot (the native function can read and write it: sscanf(s, "%d", &n), strtol(s, &end, 10), modf(x, &whole)), freed when the variable goes out of scope, like the native alloca. &x of a monolith is the block itself. Only variables have an address (native code has no &s.field/&a[i] either: use (&s) as stone + offset); &x of an Array variable is a clear error.
  • `monolith` with system layout. Instances live in raw memory with the llvmgen.struct_layout layout (the same as native code: fields in order, each aligned to its own size, up to 8; bool takes 4 bytes; Array and nested monolith take 8). s or &s passed to a native function (memcpy, qsort of structs...) sees the same bytes as the native build. As in native code, a monolith passed to a vein is by reference and forge y: T = x/y = x copy. An Array field holds the interpreter's array (the native function should not read it).
  • `Array` and strings. An Array passed to a native function is the native ofs_array itself ([data, len, cap, elem_size] header + data) of the interpreter's value column; the native function writes elements in place and the length is synchronized on return. Elements of a single type (integers/pointers, crystal, bool, obsidian or monolith); mixed types are a clear error. An Array returned by a native function uses the same block, without copying. obsidian already is the char*. Use ofs_array_data(a) to pass only the data (e.g. qsort).
  • Native → OFS callbacks. fault_addr(vein) of an interpreted vein binds the vein to one of 16 native trampolines (__ofs_cb_0..__ofs_cb_15, generated by llvmgen inside ofscc); the library calls the trampoline, which re-enters the interpreter, including inside a native call made by the program itself (qsort inside qsort, fault_call of another callback). The same vein reuses its slot. Up to 6 parameters that are integers, pointers, obsidian, bool or monolith (by pointer), with an integer/pointer return. More than 16 different veins, more than 6 parameters or crystal/f32 in the callback give a clear error with exit code 1 (use ofs run --native). f32 as a Rift argument is not supported yet either.
  • bedrock, fracture and abyss are plain blocks in both modes (native code changes nothing inside them); the bedrock cells and regions (stdlib) use the raw memory above.
  • Tests: ofs/tests/regress/ffi_*.ofs, tests/parity/cases/libc_*.

seal { … } and anchor { … } are the same thing (the same token): they register an action that runs when the current scope ends, on any exit (end of block, return, break/shatter, continue/erode, ? propagation). Several actions run in reverse order (the last registered runs first). seal is the thematic name ("seals the resource on the way out"); anchor keeps working. Both take a block or a single statement. 

vein copy(src: obsidian) -> stone {
    forge f = fopen(src, "r")
    seal { fclose(f) }          // runs on any return below
    anchor echo("copy done")    // same as seal; runs before fclose (LIFO)
    if (f == null) { return 1 }
    // ...
    return 0
}
  • The action is evaluated on exit, with the values of that moment.
  • return, break, continue and throw inside seal/anchor are forbidden (error E0042).
  • Same behavior in native code and in ofs run. Test: ofs/tests/regress/seal_defer.ofs.

Extern Functions

The Rift is the boundary through which OFS reaches the native system libraries (libc, libm, X11, Android JNI, kernel32). extern vein and rift vein declare a function that lives in a native library. There is no C code in OFS. (The system calling convention is technically known as the C ABI; it does not involve C code.)

Declare native system library functions through the Rift: 

extern vein ofs_pow(base: crystal, exp: crystal) -> crystal
extern vein ofs_sqrt(val: crystal) -> crystal
extern vein ofs_str_len(s: obsidian) -> stone

core main() {
    forge result = ofs_pow(2.0, 10.0)
    echo(result)  // prints 1024
}

All OFS runtime functions can be accessed via extern declarations. This enables low-level and high-level programming in the same language.

rift vein

OFS also supports rift vein as a declaration form for native functions through the Rift: 

rift vein strlen(text: obsidian) -> stone

core main() {
    echo(strlen("fault"))
}

rift vein lowers to the same native-call pipeline as extern vein, but it presents interop as an OFS-native boundary instead of framing the feature only as an "extern" declaration.

You can also add explicit interop metadata: 

rift vein text_size(text: obsidian) -> stone bind "strlen" abi c
  • bind "symbol" sets the external link symbol name.
  • abi c declares the intended ABI.
  • abi system is reserved for platform/system-boundary calls.

Interop Direction

extern vein is the current Rift surface. Today it is best suited for runtime symbols and native system libraries.

The roadmap extends this toward richer native interop layers for:

  • native object and library boundaries,
  • bridge layers to other ecosystems,
  • host/runtime bridges,
  • Python embedding or host bindings,
  • target-specific assembly escape hatches.

These are roadmap items, not all implemented features today.

Pointers (shard / fracture)

Pointer operations are only allowed inside fracture (safe), bedrock (typed low-level), or abyss (unsafe) blocks.

fracture (Safe Pointer Block)

core main() {
    forge x: stone = 10

    fracture {
        shard p: *stone = &x   // p points to x
        *p = 42                // dereference and assign
    }

    echo(x)  // prints 42
}

Key rules:

  • Pointers can only be created and used inside fracture blocks
  • The compiler type-checks all pointer operations
  • &x takes the address of x
  • *p dereferences pointer p

Pointer Types

shard p: *stone       // pointer to stone (i64*)
shard q: *crystal     // pointer to crystal (f64*)
shard s: *obsidian    // pointer to obsidian (i8**)

bedrock (Typed Low-Level Block)

bedrock is the OFS-native low-level block for typed machine-adjacent work. 

core main() {
    forge x: stone = 10

    bedrock {
        shard p: *stone = &x
        *p = *p + fault_spin_left(1, 3)
    }

    echo(x)
}

Use bedrock when you want low-level control and machine-like intrinsics while still keeping typed OFS rules.

Collections (Arrays)

Array Literals

Indexing

    echo(n)
}

// Index-based

    echo(nums[i])
}

Unsafe Memory (abyss)

The abyss block allows raw, unsafe memory operations: 

abyss {
    // Raw memory access — no type checking
    // Use with extreme caution
}

Rules:

  • Type checking is relaxed inside abyss blocks
  • Direct memory addressing is allowed
  • Only use when absolutely necessary
  • Prefer fracture for pointer operations

Directive alias: tectonic

You can use tectonic as a prefix directive for memory/effect modes. This is an alias syntax that maps to the same runtime/semantic behavior:

  • tectonic fracture { ... } -> same as fracture { ... }
  • tectonic safe { ... } -> same as fracture { ... }
  • tectonic abyss { ... } -> same as abyss { ... }
  • tectonic unsafe { ... } -> same as abyss { ... }
  • tectonic fractal { ... } -> same as fractal { ... }
  • tectonic bedrock { ... } -> same as bedrock { ... }

Example: 

core main() {
    forge x: stone = 10

    tectonic fracture {
        shard p: *stone = &x
        *p = 20
    }

    tectonic safe {
        shard q: *stone = &x
        *q = *q + 1
    }

    tectonic abyss {
        shard raw: *stone = &x
        *raw = *raw + 1
    }

    tectonic unsafe {
        shard raw2: *stone = &x
        *raw2 = *raw2 + 1
    }

    tectonic fractal {
        echo("effect-lifted mode")
    }

    tectonic bedrock {
        shard native: *stone = &x
        *native = *native + 1
    }
}

fault_* intrinsics

Inside bedrock, fracture, or abyss, OFS exposes machine-like intrinsics with OFS-native names: 

bedrock {
    forge x: stone = 0xF0F0
    echo(fault_count(x))
    echo(fault_lead(x))
    echo(fault_trail(x))
    echo(fault_swap(x))
    echo(fault_spin_left(x, 4))
    echo(fault_spin_right(x, 4))
    echo(fault_weave(0xFF00, 0xAAAA, 0x5555))
}

Available intrinsics:

  • fault_count(stone) -> population count
  • fault_fence() -> emit a machine-level memory barrier
  • fault_prefetch(*stone) -> request a machine-level prefetch for a pointer target
  • fault_trap() -> emit a machine-level trap
  • fault_lead(stone) -> count leading zeros
  • fault_trail(stone) -> count trailing zeros
  • fault_swap(stone) -> byte swap
  • fault_spin_left(stone, stone) -> rotate left
  • fault_spin_right(stone, stone) -> rotate right
  • fault_step(*stone, stone) -> typed pointer stepping in elements
  • fault_addr(vein) -> address of the vein as stone (see the Rift)
  • fault_call(endereco, args...) -> indirect call using the system calling convention (see the Rift)
  • fault_cut(value, shift, width) -> extract a bit field
  • fault_patch(base, shift, width, insert) -> replace a bit field
  • fault_weave(mask, left, right) -> blend bits from left and right using mask
  • fault_unreachable() -> marks the current path as unreachable, lowers to llvm.trap + unreachable IR
  • fault_memcpy(dst, src, len) -> bulk memory copy (lowers to llvm.memcpy); dst and src must be pointers
  • fault_memset(dst, val, len) -> bulk memory fill with val byte (lowers to llvm.memset); dst must be a pointer

Exact semantics (identical in the native build and in the ofs run interpreter):

  • Everything is 64-bit two's complement: fault_count(-1) = 64; fault_lead(0) = fault_trail(0) = 64; fault_lead(-1) = 0.
  • fault_spin_left/fault_spin_right: 64-bit rotation (llvm.fshl/llvm.fshr); the distance is taken modulo 64 (fault_spin_right(6, 65) = 3).
  • fault_weave(mask, left, right) = (left & mask) | (right & ~mask): each bit comes from left where mask is 1 and from right where it is 0.
  • fault_trap() and fault_unreachable() terminate the process with SIGILL (the interpreter does the same via raise(SIGILL)).
  • fault_fence()/fault_prefetch() are no-ops in the interpreter.
  • In the interpreter pointers are real addresses: fault_memcpy/fault_memset copy/fill any size, and fault_step, fault_addr and fault_call work as in native code (see "In the interpreter (ofs run): the Rift").
  • Test: ofs/tests/regress/fault_intrinsics.ofs.

These functions are designed to cover operations assembly already has, while also giving OFS room for its own machine-oriented vocabulary.

asm (inline assembly escape hatch) — planned

Status: planned. Inline asm is not available yet: the lexer does not recognize the asm keyword and the LLVM backend does not emit InlineAsm. The example below shows the planned design and does not compile today. Use fault_* intrinsics for now.

When no fault_* intrinsic covers your need, asm will emit a raw assembly string directly at that point in the code. It will only be allowed inside a bedrock, fracture, or abyss block. 

bedrock {
    asm "nop"     // planned
    asm "int3"    // planned
}

Restrictions:

  • Planned: the argument must be a string literal.
  • Input/output operand syntax (full AT&T-style constraints) is not yet parseable; use fault_* intrinsics when operand binding is needed.
  • Planned: a void inline-asm call in LLVM IR with the assembly string forwarded verbatim.
  • Planned: the asm expression will be lowered to LLVM InlineAsm, dispatched in semantic analysis and code generation. Not implemented yet.

OFS: A Truly Hybrid and Native Compiled Language

The Fundamental Question: Is OFS Interpreted or Compiled?

Answer: OFS is HYBRID — High-Performance Native AOT Compilation via LLVM and Instant AST Interpretation.

OFS unites the strengths of both execution models:

  1. Native Ahead-Of-Time (AOT) Compilation (`ofs build`): Directly generates LLVM IR from its self-hosted compiler frontend (ofscc), yielding machine code linked into standalone platform executables without virtual machines or embedded interpreters.
  2. Instant In-Memory AST Interpretation (`ofs run` / `ofs <file.ofs>`): Directly evaluates the typed Abstract Syntax Tree (AST) in memory using an integrated, pure-OFS interpreter backend (interpreter.ofs), providing rapid startup and zero compile latency for scripting and experimentation.

What Does the Hybrid Model Provide?

  1. Instant Feedback: With ofs run or ofs script.ofs, code executes immediately in memory without invocation delays from llc or linkers.
  2. Production Performance: With ofs build, the resulting executable runs directly on CPU hardware (x86_64, ARM64) with zero VM overhead.
  3. Unified Frontend: Both the interpreter and LLVM code generator consume the exact same lexer, parser, and static type checker, ensuring semantic consistency.
  4. 100% Self-Hosted: The entire compiler (ofscc), including lexer, parser, type checker, LLVM code generator, and AST interpreter, is written in OFS.

Native code only for now (it uses raw runtime memory; ofs run cannot reach the Rift yet).

Strings and memory. Strings have no GC or reference counting: t = s makes both variables point to the same text. The native compiler only reuses or frees memory when it proves nobody else sees the value: s = s + x / s += x on a local variable that is never copied elsewhere grow in place; the intermediate parts of a + b + c and an f(a + b) whose parameter is not stored are freed; local arrays that do not escape are freed at the end of their scope. Phase 2: Parser (AST Construction)

file: ofs/ofscc/parser.ofs (1,246 lines)

Strategy

  1. Recursive Descent for statements + declarations
  2. Pratt Parser for expressions (operator precedence)
  3. Pool-based AST — nodes stored in global Array<Node>

Grammar (Simplified)

program     ::= (fn_decl | monolith_decl | impl_decl | namespace_decl
                | strata_decl | extern_decl | attach_decl | var_decl)*

fn_decl     ::= ("vein" | "core") IDENT "(" params? ")" ("->" type)? block
params      ::= IDENT ":" type ("," IDENT ":" type)*
extern_decl ::= ("extern" | "rift") "vein" IDENT "(" params? ")" ("->" type)?
                ("bind" STRING)? ("abi" IDENT)?
monolith_decl ::= "monolith" IDENT "{" (IDENT ":" type (","|";")?)* "}"
impl_decl   ::= "impl" IDENT "{" fn_decl* "}"
namespace_decl ::= "namespace" IDENT "{" (fn_decl | var_decl | monolith_decl
                | extern_decl | impl_decl | strata_decl)* "}"
strata_decl ::= "strata" IDENT "{" (IDENT ("(" type ")")? (","|";")?)* "}"
attach_decl ::= "attach" "{" path "}"          // e.g. attach {core}, attach {F:lib.ofs}
var_decl    ::= ("forge" | "const" | "shard") IDENT (":" type)? ("=" expr)? ";"?

type        ::= IDENT | "Array" "<" type ">" | "*" type

stmt        ::= var_decl | if_stmt | while_stmt | cycle_stmt | mine_stmt
              | match_stmt | return_stmt | throw_stmt | tremor_stmt
              | anchor_stmt | unsafe_block | block | "break" | "continue"
              | "shatter" | "erode" | expr ";"?
if_stmt     ::= "if" "(" expr ")" block ("else" (if_stmt | block))?
while_stmt  ::= "while" "(" expr ")" block
cycle_stmt  ::= "cycle" "(" IDENT "in" expr ")" block          // over a collection
              | "cycle" "(" "forge" IDENT "in" expr ")" block
              | "cycle" "(" init? ";" expr? ";" expr? ")" block // C style
mine_stmt   ::= "mine" "(" IDENT "in" expr ")" block
match_stmt  ::= ("match" | "assay") "(" expr ")" "{" (pattern "=>" (block | stmt))* "}"
pattern     ::= expr | "_"                                      // "_" is the default case
return_stmt ::= "return" expr? ";"?
throw_stmt  ::= "throw" expr ";"?
tremor_stmt ::= "tremor" block ("catch" "(" IDENT (":" type)? ")" block)?
anchor_stmt ::= "anchor" stmt
unsafe_block::= ("fracture" | "bedrock" | "abyss" | "tectonic") ("fracture"|"bedrock"|"abyss")? block
block       ::= "{" stmt* "}"

expr        ::= unary (binop expr)*         // precedence: see table below
unary       ::= ("-" | "!" | "~" | "&" | "*") postfix(primary)
postfix     ::= primary ( "(" args? ")" | "[" expr "]" | "." IDENT
                        | "++" | "--" | "?" | "as" type )*
primary     ::= IDENT | INT | FLOAT | STRING | "true" | "false" | "null"
              | "(" expr ")" | "[" (expr ("," expr)*)? "]" | "echo" "(" args? ")"

Points the grammar does not show:

  • The parentheses of if, while, match/assay and cycle/mine are required. if x == 1 { } fails with expected '('. The body must be a { } block.
  • The semicolon is optional at the end of statements and declarations. It is only required inside a C-style cycle.
  • assay is just another name for match (same token). match becomes a chain of if comparing with ==; _ is the default case and => separates pattern and body. There are no destructuring patterns.
  • shatter and erode are synonyms of break and continue. mine works like cycle ... in but only accepts the item in collection form.
  • Namespace calls (ns.fn(x)) become the symbol ns__fn. impl methods become Type__method.
  • attach {path} is only valid at file level. The text between the braces is glued token by token (F: marks a file path).
  • There is no struct literal (P { x: 1 }) and no monolith ... layout ...; the parser expects { right after the monolith name. Declare the variable (forge p: P) and assign the fields.
  • core is a reserved word: it marks the entry point (core main()) and cannot be used as a name.

Type Checking Rules

  • 42 → stone
  • 3.14 → crystal
  • "hello" → obsidian
  • true/false → bool
  1. Binary operations:
  • Arithmetic (+ - * /): both operands must be numeric
  • Comparison (== != < <= > >=): return bool
  • Logical (&& ||): operands and result are bool

  • forge x: stone = 42 → explicit type

  1. Function calls:
  • Arguments count must match parameters
  • Argument types should be compatible with parameters

Phase 4A: AST Interpreter Backend (Interpretação Direta)

File: ofs/ofscc/interpreter.ofs (70KB, 2,086 lines)

The OFS interpreter backend runs the typed syntax tree (AST) directly in memory, without generating intermediate files, C code or LLVM IR. It is the default backend used by ofs <file.ofs> and ofs run <file.ofs>.

Interpreter architecture

  1. `Value` system: a universal monolith that unifies scalar values (stone, crystal, obsidian, bool, null) and virtual heap handles for Array<T>, monolith objects and pointers.
  2. Environment and call frames: strict lexical scope based on frame markers (_current_frame_base and _globals_count), so callers' variables do not leak into callees or globals.
  3. Value semantics: forge y: T = x and y = x copy the monolith block (obj_clone()/memcpy into the block y already has, like the native store %T); vein parameters receive the monolith by reference, like the native pointer.
  4. Method dispatch: methods defined in impl Type blocks are resolved automatically, with self injected.
  5. Real pointers (F2): a pointer is an address (VAL_INT with type *T). *p/*p = v use mem_load/mem_store by the memory class of the pointee type (MC_*: width, sign, f32, obsidian, *T, monolith, variant), with the typeck static type precomputed per node in annotate_nodes (the same type llvmgen uses); the load/store is the interpreter's own native code (fracture { *p8 = v as u8 }). &x of a variable turns the entry into VAL_BOXED: the value moves to an 8-byte slot (box_var), read/written by env_load/env_store and freed in env_pop_one (_boxed_live keeps the fast path free when there is none). as mirrors llvmgen's NK_CAST (eval_cast). A monolith lives in raw memory with the llvmgen.struct_layout layout (the same function computes the native ofs_alloc size and the interpreter's offsets; compute_layouts), and VAL_OBJECT holds the block address; an Array field holds the interpreted handle as -(h+1).
  6. Built-ins: direct handling of I/O (echo), strings (ofs_str_*), arrays (ofs_array_*) and math (ofs_pow, ofs_sqrt). The list (is_builtin) is only a fast path, not a limit on what can be called.
  7. Rift (`extern vein`/`rift vein`): at load time (collect_declarations → resolve_calls → ffi_check_symbols), every called extern becomes an address via dlsym(RTLD_DEFAULT, sym) (honoring bind), after opening libm and OFS_FFI_LIBS; a missing symbol is the linker's error (undefined reference), exit code 1. Veins from stdlib/runtime/*.ofs (line ranges marked by expand_attaches through ast_mark_runtime_lines) use the native version linked into ofscc. The call (call_extern) converts arguments by the declared type (integers/pointers/obsidian as i64, crystal as double), stores them in a buffer and calls __ofs_ffi_dispatch, which llvmgen defines inside ofscc itself (emit_ffi_dispatch, when the module declares that extern): a switch with one call of exact LLVM type per signature class (ffi_sig/ffi_sig_supported: up to 4 i64|double args with an i64|double return, up to 12 integer-only, variadics with 1 to 3 fixed + up to 4 extra; 155 cases). That is why ofscc must be linked with -rdynamic (it exports the runtime and the dispatcher to dlsym). In F2, &x, monolith (the block) and Array go to the native function as addresses: the Array is the interpreter's value column, which already is a native ofs_array (arr_native_ptr), with its length synchronized on return (ffi_sync_arrays); an Array returned by the native function becomes an interpreted array that uses the same block (arr_adopt). native → OFS callbacks: the module that declares extern vein __ofs_cb_table gets from llvmgen (emit_cb_trampolines) 16 functions __ofs_cb_K(i64 x 6) that call __ofs_cb_enter(K, ...), defined at the end of interpreter.ofs; fault_addr of an interpreted vein binds the vein to a slot (cb_slot_for) and returns the address of __ofs_cb_K (found via dlsym, so an ofscc built by an older compiler still links); cb_enter pushes the arguments by each parameter's type, runs the vein and returns the result as i64, preserving the interpreter registers (re-entrant: it works inside a native call made by the interpreter). Exhausted slots, more than 6 parameters or crystal/f32 in the callback are a clear error (exit code 1).

Deterministic:

  • Embedded timestamps

The OFS compiler is fully self-hosted and deterministic. The bootstrap process compiles the compiler using itself, without depending on external C++ compilers or legacy runtimes.

What is Self-Hosting / Bootstrap?

Bootstrapping occurs when a programming language's compiler compiles its own source code. This milestone formally proves that the language's grammar, type system, and standard library are expressive and robust enough for systems-level development.

  • Lisp (1962): First self-hosting programming language.
  • C (1972): Bootstrapped and established as the systems standard.
  • Rust (2011): Compiler written in Rust.
  • Go (2015): Compiler migrated completely to Go.
  • OFS (2024–2026): Compiler and native runtime self-hosted.

Process Overview

Phase 1: Seed Compiler

The repository provides a pre-compiled native compiler binary in ofs/dist/ (ofs / ofscc) to initiate the build cycle.

Phase 2: Recompilation

The script compiles all compiler source modules (ofs/ofscc/*.ofs) using the existing binary, emitting a fresh compiler executable.

Phase 3: Determinism Verification

The newly generated compiler compiles the compiler source once more. The binary output from pass 2 is compared byte-for-byte with pass 3 (v2 === v3). Identical checksums confirm deterministic build reproducibility.

OFS Performance Analysis

OFS performance work is split between compiler throughput and generated-program runtime.

The main hotspots currently identified are:

  1. substring allocation while materializing tokens;
  2. repeated string concatenation in import expansion and escaping;
  3. linear lookup tables for symbols, fields, variables, and interned strings;
  4. length calls repeated inside loops whose collections do not change.

The public ofs_str_char_at function still validates bounds. The lexer now uses an internal known-length byte read only after checking _pos against _len. In seven-process measurements on June 14, 2026, median IR generation for the small workload moved from 8.11 ms to 7.54 ms. Compiling ofscc.ofs moved from 4,610.40 ms to 3,694.08 ms. Bootstrap stages two and three emitted identical IR.

The planned order is:

  1. repair and expand lexer self-host tests;
  2. add detailed lexer, parser, type-checker, and LLVM IR timing;
  3. benchmark 10 KB, 100 KB, and 1 MB sources;
  4. introduce token slices or a compilation arena;
  5. add a native string builder (strbuf already exists in the stdlib);
  6. measure indexed symbol tables;
  7. evaluate LTO and LLVM flags.

Link and runtime optimization

The distributed runtime is built with -ffunction-sections and -fdata-sections. The launcher enables --gc-sections on ELF, dead_strip on Mach-O, and OPT:REF on PE/COFF so unused runtime functions do not remain in every application.

On the workload published on June 14, 2026, this reduced the OFS executable from 28,224 to 16,056 bytes without changing its checksum. The launcher caches CRT paths and native toolchain binaries (llc and ld) instead of slow filesystem probing on every compilation. Median build time for the same workload moved from 320.81 ms to 208.78 ms on the recorded machine.

These are distribution-pipeline improvements. They do not change syntax, type checking, or program semantics.

Goal

The goal is to reduce concrete compile-time and run-time costs of the compiler and runtime without changing language semantics, compromising memory integrity, or introducing silent regressions. Total build time should stay competitive with equivalent native toolchains by removing redundant work, not by removing language features.

Compilation Flow

OFS source
  -> module resolution and expansion (attach)
  -> lexer
  -> parser
  -> type checker
  -> LLVM IR generation (llvmgen.ofs)
  -> static LLVM compiler (llc -filetype=obj)
  -> native link with the native runtime (ld / ld.lld)
  -> native executable (ELF / Mach-O / PE)

Each stage is measured in isolation: optimizing the generated binary does not necessarily reduce lexer time, and lexer improvements do not change the CPU use of the resulting program.

Hotspots and Optimization Opportunities

1. Character reads in the lexer

ofs_str_char_at checks bounds against the string length. The lexer already tracks _pos against _len, so the ofs_str_char_at_known variant avoids a redundant strlen per character and keeps processing of large sources linear, O(N).

2. Substring allocation

The lexer slices text for identifiers, numbers and literals. The optimized strategy is:

  • keep (start, length) tuples that point into the original file buffer during parsing;
  • materialize heap strings only when a syntax node or the symbol table needs them to persist;
  • use a per-compilation-unit arena allocator, released in one step at the end.

3. String concatenation

Sequential concatenation in loops copies prefixes repeatedly. In the LLVM generator, cg_emit writes straight to the output file and avoids temporary buffers.

4. Symbol tables and scope lookup

Linear symbol lists have good cache locality for small and medium programs. For large code bases, hash tables or scope-indexed structures reduce the lookup cost for variables and types.

Measurement Methodology

  1. A controlled set of lexical and syntactic tests with sources from 10 KB to 1 MB.
  2. Per-phase timing: front end (lexer, parser, types), LLVM IR emission, native link.
  3. Real system metrics via wait4: user CPU time, system time and peak resident memory (RSS).
  4. Strict output checksum verification so no optimization changes semantics.

Use ofs run for scripts and development; use ofs build for performance.
  • Compiling the compiler itself (self-host) dropped from 197 MB to 45 MB of RAM.

The interpreter and the LLVM generator share the lexer, parser and type checker, but execution still diverges: ofs run is a subset (no extern outside the builtin list, no pointers). The plan is to reach parity; until then ofs build is the reference.

OFS Web Stack Architecture

The OFS web stack is structured across three distinct layers:

LayerExtensionPurpose
ODL.odlSemantic document structure and textual content
OES.oesDesign tokens, responsive layout rules, and keyframe animations
OFS.ofsNative processing logic, static page generation, and HTTP serving

ODL and OES are standalone languages compiled by the OFS toolchain, rather than mere aliases for handwritten HTML and CSS. However, standard HTML5 and CSS remain the browser distribution targets.

1. Static Site Generation

The toolchain compiles ODL and OES source files directly into production-ready browser assets: 

ODLC_INPUT=page.odl ODLC_OUTPUT=public/index.html ofs run ofs/tools/odlc.ofs
OESC_INPUT=theme.oes OESC_OUTPUT=public/theme.css ofs run ofs/tools/oesc.ofs

The output can be deployed to standard static hosting providers, such as GitHub Pages, Cloudflare Pages, or traditional web servers (Nginx/Apache).

2. Integrated Native Web Server (webserver)

The standard library provides an HTTP server written in OFS and executed as a standalone binary: 

attach {webserver}

core main() {
    forge body = "<h1>OFS Native Server</h1><p>Running without external runtime dependencies.</p>"
    webserver.serve_html_forever(8080, body)
}

The compiled binary manages network sockets and serves the pre-rendered artifacts on demand.

3. Web Ecosystem Interoperability

The ODL compiler provides explicit directives to interoperate with existing web technologies:

  • mark / markdown: Compiles embedded Markdown into semantic HTML.
  • raw / html: Injects raw HTML fragments without automatic escaping.
  • wire / script: Injects classic JavaScript scripts (<script src="...">).
  • spark / module / node: Injects modern ES modules (<script type="module" src="...">).
  • pulse / js: Embeds inline JavaScript code (<script>...</script>).
  • server / php: Emits server-side processing blocks (<?php ... ?>).
  • raw / css in OES: Injects direct CSS rules for gradual migrations.

4. VS Code Extension and Live Reload (*Go Live*)

The official VS Code extension enables *Go Live* development mode when opening .odl documents or .ofs programs that import webui or webserver.

When *Go Live* is started:

  1. The .odl document is compiled to HTML.
  2. Sibling .oes style files in the directory are compiled to CSS.
  3. A local development HTTP server is initiated.
  4. The server watches .odl, .oes, scripts, and graphical assets, automatically triggering compilation and browser reload via Server-Sent Events (SSE).

5. Browser Compatibility

Web browsers do not execute .odl and .oes files natively. OFS adopts the industry-standard workflow established by TypeScript, JSX, and Sass:

  1. Project source code is authored in .odl and .oes.
  2. Build tools compile the source files into standard HTML5, CSS, and JS.
  3. Hosting providers and browsers receive the compiled artifacts.
  4. For debugging and inspection, the native server exposes text/odl and text/oes MIME types.

6. Current Technical Scope

  • ODL and OES compile whitespace-delimited source code into static markup and stylesheets.
  • Reverse HTML/CSS import tools encapsulate complex legacy blocks into raw directives (raw).
  • Native HTTP routing logic remains separate from document layout definitions.
  • Components are designed for compile-time or bootstrap-time static evaluation.

Steps (src/packaging/linux/ofs, android_build):

  2. OFSCC_TARGET=android ofscc → LLVM IR (aarch64-unknown-linux-android26) for the app and the magma runtime (cached);

Runtime model (stdlib android.ofs)

  • Entry: android.ofs exports vein ANativeActivity_onCreate(...) and fills activity->callbacks with OFS vein addresses via fault_addr (see LANGUAGE_REFERENCE.md).
  • Single thread: everything runs on the Android main thread, no pthread (the magma runtime is not thread-safe). Input uses AInputQueue_attachLooper; frames use AChoreographer_postFrameCallback (API 24+), posted only on demand (android.request_frame() or android.continuous = true). Split long work across EV_FRAMEs.
  • Contract: the program defines vein android_event(ev: stone) -> void and reads state from android.* (EV_CREATE…EV_DESTROY, EV_WINDOW_*, EV_RESIZE, EV_ROTATE, EV_FRAME, EV_TOUCH_*, EV_BACK, EV_KEY, EV_FOCUS, EV_CONFIG, EV_LOW_MEMORY).
attach {F:android.ofs}

vein android_event(ev: stone) -> void {
    if (ev == android.EV_FRAME) {
        if (android.lock()) {
            android.fill_rect(0, 0, android.buf_w, android.buf_h, 1052704)
            android.unlock_post()
        }
    }
    if (ev == android.EV_BACK) { android.finish() }
}

Multitouch: every touch event refers to finger touch_id (AMotionEvent_getPointerId); extra fingers arrive as EV_POINTER_DOWN/EV_POINTER_UP, EV_TOUCH_MOVE comes once per finger, and all fingers are in ptr_count/ptr_id[]/ptr_x[]/ptr_y[].

Audio (audio_android.ofs + wav.ofs): AAudio 44.1 kHz stereo i16 stream with a data callback; audio.open, play(channel, sound, loop), stop, stop_all, set_volume, set_master, playing, pause/resume/close, pump() once per frame. Functions: lock/unlock_post, fill_rect, blit, request_frame, finish, set_orientation(ORIENT_REQ_*) (JNI setRequestedOrientation), call_activity_void_int, internal_data_path, external_data_path, log, log_tag, s32, peek/poke. Text input via the system keyboard (android_input.ofs)

No listeners: the buttons are ToggleButtons (they toggle on tap; ainput.poll() reads isChecked()), and back/tap outside closes the Dialog (isShowing()). poll() returns 0 open, 1 OK, 2 cancelled; ainput.text() reads the text. Current limits

  • arm64-v8a only, API 26+.
  • Software rendering (ANativeWindow_lock), no GL/Vulkan.
  • Audio: WAV only (PCM / MS-ADPCM), no Ogg/MP3; no onSaveInstanceState (save your state in on pause).
  • C struct offsets (ANativeActivity, ANativeWindow_Buffer, ARect, JNIEnv table) are fixed for aarch64.
  • 32-bit C ints arrive as stone with undefined upper bits: use android.s32().
  • fault_call passes integers and pointers only.
  • The installed ofs/dist/magma.o and ofscc predate the Android target; until the next release the CLI builds ofscc from source.

Generic JNI, WebView, HTTP (stdlib)

  • Generic JNI (android.ofs): jni_call(obj, name, signature, a..f) (the return kind comes from the signature: V, Z, I, J, object), jni_new(class, signature, a..d), jni_scall(class, name, signature, a..d) (static), jni_static_int_field, jni_global/jni_delete_global, jni_new_byte_array/jni_get_bytes/jni_set_bytes, jni_new_object_array/jni_set_object_elem; android.jni_failed tells whether a Java exception happened. Main thread only.
  • `android_webview.ofs`: webview.open(base_url, html) opens a WebView (JS, DOM storage, file access, media without gesture) in a full-screen immersive android.app.Dialog; poll() (Back closes the Dialog), eval(js), title(), pause(on), close(). Why a Dialog: NativeActivity takes the main window surface (takeSurface), so a View added to its window is not drawn; the Dialog has its own window and gets touch directly (not through AInputQueue). No Java subclass: the shim goes in as a <script> in the HTML (loadDataWithBaseURL("file:///folder/", html)), and the JS-to-OFS return channel is document.title (Chromium cuts titles at 4096 characters and collapses whitespace/control chars: send in chunks and with encodeURIComponent).   • `android_http.ofs`: ahttp.open(url)/read(buf)/close() and get_text(url) over HttpURLConnection (HTTPS with certificate checking and redirects; the OpenSSL of tls.ofs cannot be linked in an APK). Blocks up to ~4 s per call on the main thread (use short per-frame steps; StrictMode is relaxed). Needs permission INTERNET in the .oal. Accepts file:///... and absolute paths.

Engine mode: hosting other code/Views in the NativeActivity (stdlib android.ofs)

To run a game engine (SDL, Godot) inside the app, without installing an APK and without Java in the APK (hasCode=false):

  • release_window(): calls getWindow().takeSurface(null) and takeInputQueue(null). Call it in `EV_CREATE` (the window is attached only after onResume). From then on the NativeActivity no longer claims the surface or the input queue: set_content_view(view) (or a Java adapter's setContentView) draws normally and gets touch/keys through Java. OFS stops receiving EV_WINDOW_* and touches; lifecycle events still arrive. Tested on Android 11 (Moto G8 Power). In AOSP's NativeActivity.java, onCreate calls takeSurface(this)/takeInputQueue(this) before ANativeActivity_onCreate; ViewRootImpl reads those callbacks when the window is attached, so null wins.
  • dex_load_class(dex, libs_dir, "pkg.Class"): DexClassLoader (parent: the activity's class loader) + loadClass; returns a global class reference or 0 (reason in jni_error). dex accepts several files separated by :. The .dex must live in the app's internal storage and, on Android 14+, be read-only (set_read_only(path)). libs_dir is that loader's System.loadLibrary search path.
  • jni_scall_cls(cls, name, signature, a..d): static method on an already obtained jclass (e.g. from dex_load_class).
  • jni_take_error(): if a Java exception is pending, stores its toString() in jni_error, prints the stack to logcat (System.err) and clears it.
  • intent_extra(key): getIntent().getStringExtra(key) ("" if missing).
  • self_intent(keys, values) / restart_process(keys, values): Intent for this same activity with String extras and FLAG_ACTIVITY_NEW_TASK|CLEAR_TASK; restart_process calls startActivity and kills the process (Process.killProcess(myPid)): the system opens the activity in a fresh process (~60 ms on a Moto G8). M.O.O.N uses it to enter and leave "engine mode" (one engine per process).
